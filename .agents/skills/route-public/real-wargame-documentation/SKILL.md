# Ведение документации Real-wargame

Этот навык обязателен для любой задачи Codex или OpenCode, которая меняет
документацию: описание подпроекта, статусы, журналы, навигацию, правила работы
или файлы, создаваемые генератором документации.

## 1. Сначала прочитать

Перед изменениями прочитай в таком порядке:

1. `AGENTS.md`.
2. `docs/ai/repo-context.json`.
3. `docs/subprojects/index.json`.
4. `docs/subprojects/<active-id>/STATUS.md` активного подпроекта.
5. Релевантный навык из `docs/ai/SKILLS_INDEX.md`.

Для работы с подпроектом дополнительно прочитай его `SUBPROJECT.md` и
`JOURNAL.md`. Для архитектурной AI-задачи прочитай
`docs/ai/AI_DEVELOPMENT_APPROACH.md`; для runtime-задачи — документы
производительности и соответствующий навык.

## 2. Приоритет канонических источников

Канонические источники истины:

- `docs/ai/repo-context.json` — общие факты проекта, ветки, доставка, навигация;
- `docs/subprojects/*/subproject.json` — состояние и поля каждого подпроекта.

Все остальные документы — производные. Если документ расходится с каноническим
источником, канонический источник имеет приоритет. Исправляй источник, а не
производный документ.

## 3. Ручные и генерируемые файлы

Редактируются вручную (канонические):

- `AGENTS.md`;
- `docs/ai/repo-context.json`;
- `docs/subprojects/<id>/subproject.json`;
- `docs/subprojects/<id>/SUBPROJECT.md`;
- `docs/subprojects/<id>/JOURNAL.md`;
- записи в `docs/subprojects/<id>/journal/`;
- профильные документы в `docs/ai/`, `docs/workflow/`, `docs/architecture/`
  и `docs/performance/`.

Генерируются из канонических источников и не редактируются вручную:

- `docs/ai/CURRENT_STATE.md`;
- `docs/subprojects/index.json`;
- `docs/subprojects/INDEX.md`;
- `docs/subprojects/<id>/STATUS.md`.

Если generated-файл выглядит неверно, исправляй источник и запускай генератор,
а не правь результат напрямую.

## 4. Правила подпроектов

Для нового подпроекта используй шаблон из `docs/subprojects/_template/`.

В `subproject.json` поддерживай как минимум:

- `id`, совпадающий с именем папки;
- `title`, `status`, `updated_at`;
- `goal`, `current_focus`, `next_step`;
- `canonical_launcher`;
- непустые `must_read_first`, `main_files`, `suggested_verification`;
- `safety_rules`;
- `last_verified_commit`, если он предусмотрен текущей схемой.

Статус подпроекта выбирай только из разрешённого списка схемы. Активный
подпроект должен совпадать с `activeSubprojects` в `repo-context.json`.
Ссылки и пути, перечисленные в метаданных, должны существовать.

`SUBPROJECT.md` объясняет назначение и рабочий контекст. `JOURNAL.md` хранит
краткую историю значимых событий. `STATUS.md` является производным текущим
состоянием и создаётся генератором.

## 5. Журнал

Обязательно веди журнал: одна короткая запись на значимое событие.

Формат записи:

```text
что изменилось → почему → результат
```

Не фиксируй каждый микрошаг. Не вставляй сырые логи, телеметрию и полные
отчёты. Если используются отдельные файлы в `journal/`, добавь их в индекс
`JOURNAL.md`, чтобы валидатор не выдавал предупреждение о неиндексированном
файле.

## 6. Команды документации

Команды проекта:

```text
npm run docs:generate   — перегенерировать production-документы из источников
npm run docs:check      — проверить целостность сгенерированных документов
npm run docs:smoke      — smoke-проверка генератора и валидатора
npm run docs:sync       — docs:generate, затем docs:check
```

`docs:sync` — основной быстрый путь: генерация и проверка. Для отдельной
диагностики используй `docs:smoke`, `docs:generate` и `docs:check` по отдельности.

Инструмент контекста подпроектов:

```text
python scripts/subproject_context.py <id> --brief
python scripts/subproject_context.py <id> --opencode
python scripts/subproject_context.py <id> --files
```

## 7. Содержание документов

- Пользовательские инструкции пиши простым русским языком.
- Канонические имена файлов, полей JSON, команд и путей сохраняй в
  каноническом английском виде.
- Соблюдай UTF-8.
- Даты в метаданных записывай как `YYYY-MM-DD`.
- Ссылки должны быть кликабельными и вести на существующий файл или источник.
- Не создавай отдельные документы, если информацию можно добавить в
  существующий канонический источник.
- Архитектурные решения фиксируй в соответствующем архитектурном документе,
  а не только в журнале.
- Состояние подпроекта фиксируй в `subproject.json`, а не вручную в
  `STATUS.md`.

## 8. Проверки и честный отчёт

Минимальная проверка документационной задачи:

- `npm run docs:sync`;
- просмотр diff канонических и generated-файлов;
- проверка ссылок и индекса журнала;
- профильная проверка, если изменены workflow, архитектура, AI или runtime.

Не заявляй о проверке, генерации, публикации или синхронизации, которые не
выполнялись.

## 9. Запреты

Не делай без отдельного разрешения:

- ручное редактирование generated-файлов;
- запись в `main`, слияние или включение auto-merge;
- изменение документов вне разрешённого объёма (scope creep);
- публикацию секретов, `.env`, токенов и приватных путей;
- массовое переписывание документации без необходимости;
- исправление несвязанных проблем;
- выдумывание статусов, ссылок, commit SHA или результатов проверок.

## 10. Рассинхронизация локальной копии и GitHub

Если локальная копия расходится с GitHub main или с текущей веткой, не
смешивай старые и новые правила. Определи источник истины для текущей задачи,
явно сообщи о конфликте и продолжай только после выбора актуального набора
правил. Не применяй старые поля или статусы только потому, что они остались
в локальном файле.

## 11. Минимальный шаблон отчёта

```text
Цель:
Изменённые канонические файлы:
Изменённые generated-файлы:
Активный подпроект:
Выполненные проверки:
Невыполненные проверки и причина:
Рассинхронизации/риски:
```

## 12. Route W/X

Если задача передаётся через внешний маршрут Route W или Route X, до отправки
промта Codex заранее добавляет `Required Skills Manifest`: перечисли все
навыки, которые могут понадобиться, для каждого укажи имя, внешнюю ссылку на
`SKILL.md` (желательно raw URL с фиксацией на commit), причину, статус
`required`/`conditional` и порядок чтения.

Внешний исполнитель обязан прочитать required-навыки, conditional — при
наступлении условия, и указать в итоговом отчёте/терминальном блоке поля
`skills_read`, `skills_skipped` и `skills_unavailable`. Если обязательный
навык недоступен, он должен остановиться и сообщить причину (блокер) — нельзя
молча выдумывать или применять правила неуказанных навыков. Приватные локальные
пути, секреты, `.env` и непубличное содержимое навыков в ссылки не включай.
