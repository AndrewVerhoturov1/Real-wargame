# Протокол оркестрации Real-Wargame (Codex Orchestration Protocol)

Короткий канонический протокол совместной работы: пользователь, Codex и Web Chat над `AndrewVerhoturov1/Real-wargame`. Обязательный контракт для всех ролей — репозиторный `AGENTS.md`.

## 1. Роли

- **Пользователь (user)** — ставит задачу, смотрит результат, даёт явные решения и GO. Не обязан работать с Git или терминалом.
- **Web Chat** — обычный владелец продукт-кода: реализует фичи и фиксы на одной feature-ветке, пишет тесты, гоняет focused checks и готовит чек-лист живого теста. После GO перенос принятого exact commit выполняется по текущему рабочему процессу; Codex может выполнить этот перенос как оператор.
- **Codex** — оркестратор и независимый ревьюер/тестировщик/оператор: принимает задачу, выбирает режим, готовит и передаёт задачу Web Chat, получает exact commit, проверяет его (GitHub, MCP, локальные проверки, браузер), отправляет конкретные замечания и после GO помогает переносить результат. Codex не заменяет Web Chat как автора продукт-кода.

Роли не жёсткие по инструменту: «Web Chat» здесь означает агента-исполнителя продукт-кода, а «Codex» — оркестратора. Задача всегда имеет одного исполнителя фичи и одного оркестратора.

## 2. GitHub — постоянная общая память

GitHub (`AndrewVerhoturov1/Real-wargame`) — единственное постоянное состояние между сессиями и агентами.

- Ветка `real-wargame-preview` — рабочая и приёмочная ветка.
- Ветка `main` — стабильная ветка.
- Feature-ветки `feature/YYYYMMDD-short-kebab-slug` — временная реализация задачи.
- Точный commit (SHA) — единица передачи и ревью.

Никакая необходимая передача не живёт только локально у агента: ветка, exact commit, отчёт и замечания обязаны быть достижимы через GitHub. Локальные worktree — это только рабочие копии, а не общая память.

## 3. Режимы работы

### Простой режим (simple mode)

Пользователь работает напрямую с одним Web Chat по каноническому пути:

```text
docs/workflow/WEB_CHAT_FEATURE_DELIVERY.md
```

Это режим по умолчанию, когда задача обычная продуктовая и не требует дополнительной координации.

### Режим оркестрации (orchestrated mode)

Codex получает задачу и ведёт её через Web Chat:

```text
пользователь → Codex (оркестратор)
→ подготовка задания для Web Chat (ветка, base_commit, ожидаемый результат, запреты)
→ Web Chat реализует на feature-ветке и возвращает exact commit
→ Codex проверяет exact commit независимо (ревью, тесты, браузер)
→ конкретные замечания или передача результата пользователю
→ live-test пользователя
→ явный GO пользователя
→ перенос exact accepted commit в real-wargame-preview
```

Выбор режима делает оркестратор по сложности задачи и наличию Web Chat-сессии. Простой режим не требует оркестратора.

## 4. Ветки и worktree

- Одна задача — одна feature-ветка от точного текущего HEAD `real-wargame-preview`.
- Прямая реализация на `real-wargame-preview` запрещена.
- Продуктовые правки живут на той же feature-ветке до принятия.
- Для параллельной работы агенты используют отдельные локальные worktree (`git worktree`). Worktree не заменяет ветку и не создаёт общую память — только фича-ветка и exact commit передаются.
- Никогда не правь продукт-код сразу в `main` или `real-wargame-preview`.

## 5. Точный SHA обязателен

- Перед началом: `base_commit` = точный HEAD `real-wargame-preview` (полный 40-символьный SHA).
- После реализации: `current_commit` = точный pushed SHA feature-ветки.
- Ревью и проверки выполняются только по заявленному exact SHA.
- В отчётах SHA идут после практического результата, но всегда присутствуют.

## 6. Передача задачи Web Chat

Handoff Web Chat содержит:

```text
repository: AndrewVerhoturov1/Real-wargame
base_branch: real-wargame-preview
base_commit: <exact SHA>
feature_branch: feature/YYYYMMDD-short-kebab-slug
goal: что нужно сделать
allowed_changes: где можно менять
forbidden_changes: что менять нельзя (main, preview, секреты, деплой)
required_output: ожидаемый результат, exact commit, checks, чек-лист живого теста
```

Формат результата Web Chat — `docs/orchestration/RESULT_TEMPLATE.md`.

## 7. Передача результата обратно

Web Chat возвращает не «текст в чате», а достижимое через GitHub состояние:

- feature-ветка pushed;
- `current_commit` (exact SHA);
- `base_commit` (от какого SHA сделана);
- список изменённых файлов;
- фактически выполненные проверки;
- что не проверялось;
- ручной чек-лист живого теста;
- `preview_touched: no`, `main_touched: no`.

## 8. Цикл ревью и исправлений

1. Codex получает exact SHA, выкачивает его (fetch/checkout) и сверяет: ветка и SHA совпадают с заявленными.
2. Проверяет независимо: diff, структуру, focused checks (если возможно), при необходимости браузер/скриншоты.
3. Отправляет только конкретные, выполнимые замечания (что, где, почему, что ожидается).
4. Web Chat правит на той же feature-ветке и возвращает новый exact commit.
5. Цикл повторяется до готовности или до решения пользователя.

Codex не гоняется за каждым коммитом: проверяет заявленный exact SHA, а не «последнее, что видно».

## 9. Когда нужен Issue, а когда нет

**Issue не нужен** для обычной ограниченной задачи: достаточно feature-ветки, exact commit и отчёта. Это стандартный путь.

**Issue нужен**, когда есть хотя бы одно из:

- задача большая и должна жить несколько сессий/агентов как единая единица работы;
- нужно публично зафиксировать решение, альтернативы или обсуждение;
- нужна связь нескольких веток/PR/коммитов с одной целью;
- требуется напоминание или долговременный трекер, недостижимый через ветки.

Не создавай Issue на каждую мелкую задачу и не вводи Issue как обязательный шаг процесса.

## 10. Явные GO-ворота пользователя

Три действия требуют явного слова пользователя. Передача или push сами по себе ничего из этого не разрешают:

```text
1. любые изменения main            → отдельный явный GO
2. перенос в real-wargame-preview  → явный GO для exact accepted commit
3. внешний деплой (Vercel / GitHub Pages) → явный запрос деплоя
```

Связка «перенос + деплой» разрешается только если пользователь явно попросил оба действия вместе. Push никогда не деплоит.

## 11. Сохранение существующих различий

Протокол не стирает существующие границы:

- feature-ветка ≠ real-wargame-preview;
- focused checks ≠ CI ≠ браузерная проверка;
- commit/push ≠ Vercel-деплой;
- код готов ≠ задеплоен ≠ пройден живой тест ≠ есть визуальное доказательство;
- деплой и visual-QA — отдельные разрешения;
- Issue нужен не всегда.
