# Полигон — редактор эксперимента

## Назначение

«Полигон» — подпроект Real Wargame для подготовки и проведения воспроизводимых тактических экспериментов. Центральная карта является общим рабочим пространством, вокруг которого собираются редакторы карты, участников, программы эксперимента и последующего анализа результатов.

Автономные HTML-прототипы нужны для проверки пользовательского интерфейса и рабочих сценариев до переноса решений в основное приложение. Они не заменяют игровые модели, реестры и правила симуляции.

## Что уже готово

### 1. Редактор юнита

Рабочий прототип создания и настройки участника: выбор, перемещение, поворот, позы, профили, архетип и подробные параметры.

В текущей версии редактор дополнен настройками тактического знака: роль бойца, действие, принадлежность к отделению, направление корпуса и отдельное направление оружия.

### 2. Отображение пехоты на карте

Пехота отображается простыми условными знаками, а не человеческими фигурами. Состояние читается через геометрию и небольшие дополнительные метки:

- стоя — круг;
- на корточках — скруглённый треугольник;
- лёжа — вытянутый прямоугольник;
- оружие — отдельный знак для винтовки Мосина, ППШ, ДП и пистолета;
- направление корпуса и оружия;
- движение, прицеливание, стрельба, подавление, ранение, смерть и командир;
- области отделений;
- ближний, средний и дальний уровни детализации.

### 3. Редактор карты

Рабочий прототип авторинга карты. К v44 в нём собраны поле, рельеф, поверхности, растительность, линейные объекты, здания и предметы, а также история действий, запекание и выгрузка результата.

### 4. Программа

Рабочий прототип программы эксперимента: дорожки, шаги, действия, условия, ветвления, циклы, параллельные ветви и привязки к карте/участникам.

### 5. Метрики

Принят UX-прототип полного цикла настройки и анализа измерений:

- специализированный каталог потоков данных;
- необязательные фильтры участников/целей/состояний;
- Program Anchors как стабильные границы периода сбора;
- левая панель с карточками измерений и состояниями сбора;
- отдельный Отчёт, который не меняет raw telemetry и measurement definition;
- верхние режимы Отчёта: `Обзор`, `Измерения`, `Хронология`;
- экспорт JSON для LLM, JSONL и CSV;
- восемь аналитических блоков.

В демонстрационном Отчёте используются явно помеченные demo-data. Реальное production-подключение telemetry остаётся отдельной задачей.

### 6. Журнал

Принят Journal v4 — read-only интерфейс разбора эксперимента:

- единая левая хронологическая лента без внутренних подвкладок;
- inline-раскрытие подробностей события без сброса scroll position;
- быстрые фильтры `источник / уровень / участник` и отдельная `Тонкая настройка`;
- источники `Основные / Метрики / Основные + метрики`, где последний режим используется по умолчанию;
- использование фактически включённых measurement definitions Metrics v18 как дополнительного слоя детализации;
- глобальная timeline под шапкой во всех рабочих вкладках, по умолчанию свернутая;
- независимый фильтр точек timeline;
- read-only LIVE/HISTORY навигация по времени;
- визуальная подсветка выбранного события на карте;
- правая панель остаётся инспектором выбранного юнита и в HISTORY должна показывать его историческое состояние/знания без информации из будущего.

Journal v4 является UX/reference-контрактом. Demo-history/snapshots в standalone HTML не являются production replay system.

## Постоянный процесс проектирования UI

Эти правила относятся ко всем следующим крупным UI-этапам автономного Полигона.

1. Сначала исполнитель исследует задачу и описывает сущность интерфейса **текстом**.
2. Текстом согласуются структура, основные сценарии, внутренние вкладки, popup/modal и спорные продуктовые решения.
3. До явного пользовательского одобрения согласованной текстовой концепции HTML не создаётся и не изменяется ради нового раздела.
4. После одобрения можно реализовывать согласованный вариант и проводить визуальную проверку.
5. Большой автономный HTML Полигона нельзя выводить прямо в чат и нельзя передавать пользователю как отдельный сырой `.html`-артефакт. Передаваемая версия должна находиться внутри ZIP-архива.
6. Для новой UI-итерации используется **только последняя принятая каноническая версия целого Полигона**; старые промежуточные HTML не используются как параллельные базы.

## Что пока не готово

- `Серия` как крупная продуктовая вкладка;
- production-сбор и хранение telemetry для принятого UX Метрик;
- production Journal adapter над реальными структурированными runtime-событиями;
- replay/history provider для точного восстановления прошлых состояний;
- historical perception/memory/weapon-state adapter;
- пространственная аналитика карты в Отчёте.

## Ближайшая цель

Следующая незавершённая крупная продуктовая вкладка — `Серия`.

Для следующей UI-итерации:

1. использовать **только Journal v4** как исходный прототип;
2. сначала текстом согласовать сущность и структуру `Серии`;
3. только после явного одобрения реализовать её в принятом прототипе;
4. не ломать уже принятые редакторы, Metrics v18, Journal v4 и систему тактических знаков;
5. отдельно проектировать production wiring telemetry/replay к принятым UX, сохраняя simulation единственным источником игровой истины.
