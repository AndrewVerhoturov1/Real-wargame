# Принятая связность интерфейса Полигона v1

Принята пользователем 15 августа 2026.

## Идентичность

Канонический UX/reference-артефакт этой итерации должен быть загружен пользователем вручную под именем:

`polygon-interface-linkage-v1.html`

Целевой путь в ветке `real-wargame-preview`:

`docs/subprojects/polygon-prototype/prototypes/polygon-interface-linkage-v1.html`

Финальный объединённый HTML построен трёхсторонним слиянием:

- общая база — `polygon-series-v1.1-memory-tab-v2.html`;
- новая правая панель — `polygon-series-v1.1-memory-tab-v3.html`;
- слой связности — `polygon-interface-linkage-check.html`.

Итоговая версия сохраняет изменения `memory-tab-v3` и добавляет поверх них сквозную связность интерфейса.

Проверочная идентичность файла, переданного пользователю как `polygon-series-v1.1-memory-v3-interface-linkage.html`:

- размер: `2 292 772` байта;
- SHA-256: `4f33f19578698947cd629a88c6963c325895995fdd78a5380966ae1ef2fa1cfd`.

По явной инструкции пользователя сам HTML этой записью в репозиторий **не добавляется**. После ручной загрузки следует проверить имя, размер и SHA-256.

## Цель итерации

Эта итерация не вводит новую вкладку и не перестраивает Полигон визуально. Её задача — сделать существующие разделы единым интерфейсом одного эксперимента.

Главный принцип:

> если сущность создана, выбрана или настроена в одном разделе, все другие относящиеся к ней разделы должны воспринимать её как ту же сущность, показывать источник/контекст и позволять перейти к нему.

Standalone HTML остаётся UX/reference-контрактом. Отсутствие production simulation runner, backend, telemetry storage или canonical runtime state само по себе не является дефектом этого прототипа.

## Универсальная ссылка на сущность

Для перекрёстных переходов принят единый визуальный примитив:

- обычный текст без отдельной карточки;
- цветовой акцент;
- штриховое/пунктирное подчёркивание;
- усиление акцента при hover;
- `pointer` cursor;
- клик открывает соответствующую вкладку/редактор и выбирает источник.

Не добавлять рядом отдельные кнопки `Открыть`, стрелки и тяжёлые карточки без отдельной причины.

Примеры связанных сущностей:

- `Осторожное движение`;
- `ППШ-41`;
- `Шаг 14 «Отступление»`;
- `Боец №17`.

## Редактор юнита: роль и архетип

Старое двусмысленное использование термина `Архетип` разделено на две независимые сущности.

### Роль

Тактическая/штатная функция бойца:

- Стрелок;
- Пулемётчик;
- Командир;
- Наблюдатель;
- другие роли по мере развития игры.

### Архетип бойца

Поведенческий/подготовительный профиль из Общих редакторов:

- Новобранец;
- Регулярный;
- Ветеран;
- Осторожный;
- другие архетипы.

Изменение роли не должно автоматически менять архетип и наоборот.

Редактор юнита также должен показывать связанные профили внимания, восприятия, движения и оружие как ссылки на их authoritative UI-источник.

## Обратные ссылки «Используется»

В Общих редакторах для переиспользуемой сущности принят компактный блок `Используется`.

Минимальные категории:

- `Бойцы: N`;
- `Программа: N`;
- `Лаборатория: N`.

Каждая категория ведёт к реальным ссылкам/местам использования. Это не отдельная большая панель зависимостей, а лёгкий способ понять влияние изменения профиля.

### Удаление используемой сущности

Запрещено молча удалять сущность, которая используется другими объектами.

Перед удалением показать предупреждение с количеством и местами использования. Сложный wizard замены в этой версии не требуется.

## Лаборатория: источник и provenance

Laboratory override должен явно показывать:

1. источник параметра;
2. базовое/нормальное значение из этого источника;
3. экспериментальное значение;
4. эффективное значение или понятную дельту.

Пример пути источника:

`Профили движения → Осторожное движение → Скорость`.

Название источника является ссылкой и открывает соответствующий Общий редактор.

Запрещено подставлять выдуманное нейтральное baseline-значение, когда настоящий владелец параметра доступен интерфейсу.

### «Применить глобально»

В UX это действие означает:

- экспериментальное значение становится новым базовым значением authoritative UI-источника;
- временный Laboratory override после этого очищается;
- пользователь видит, что источник действительно изменился.

Production runtime wiring остаётся отдельной задачей.

## Программа ↔ Журнал

Принята двусторонняя причинная связь между предписанием эксперимента и фактическим событием.

### Журнал → Программа

Событие, вызванное программным шагом, должно показывать точный источник, например:

`Причина: Шаг 14 «Отступить при потерях >30%»`.

Название шага является ссылкой. Клик:

1. открывает `Программа`;
2. выбирает нужный шаг;
3. прокручивает/фокусирует его.

### Программа → Журнал

У шага Программы показывается обратная ссылка вида:

`Срабатывания в Журнале: N`.

Клик открывает Журнал, отфильтрованный по этому шагу.

Смысл разделения сохраняется:

- Программа — что должно произойти;
- Журнал — что действительно произошло.

## Связанные сущности Журнала

Когда сущность уже существует в объектной модели прототипа, её название в Журнале должно использовать общий linked-entity стиль.

Минимально связываются:

- боец;
- второй/целевой боец;
- оружие;
- Метрика;
- шаг/причина Программы.

Журнал остаётся компактной лентой; каждое событие не превращается в большую карточку ссылок.

## Метрики ↔ Серия

`Метрики` являются единственным UX-владельцем definitions того, что измеряется.

`Серия` не должна содержать независимый параллельный каталог фиксированных показателей вроде `hits / accuracy / losses / suppression`, если они не являются выбранными Metrics definitions текущего эксперимента.

Принято:

- пользователь создаёт/выбирает измерения во вкладке `Метрики`;
- Серия потребляет именно этот выбранный набор;
- названия Метрик в отчёте Серии кликабельны и ведут обратно в `Метрики`;
- Серия отвечает за число прогонов, seed, выполнение, сравнение, распределения, outliers и выбор конкретного прогона.

## Контекст исторического прогона

Старый/исторический прогон должен сохранять достаточный UX-контекст, чтобы понимать, как он был получен.

Минимально показываются:

- ID серии/прогона;
- seed;
- использованная Программа;
- Laboratory changes или их количество/сводка;
- использованные Метрики.

Не требуется создавать отдельный большой новый analysis UI. Требование — не потерять производящий контекст старого результата.

## Сохранение эксперимента

Пользовательский контракт команды `Сохранить эксперимент` охватывает концептуально весь эксперимент:

- карту;
- юниты;
- Программу;
- Лабораторию;
- Метрики и относящиеся к эксперименту настройки.

Обратная команда `Открыть эксперимент` должна восстанавливать тот же состав.

Операции только с картой должны называться отдельно:

- `Экспортировать карту`;
- `Импортировать карту`.

Standalone реализация может оставаться простой, но видимый UX не должен называть map-only JSON «сохранением эксперимента».

## Что сознательно не добавлено

Эта итерация **не** вводит:

- специальную сущность/подсветку «лес» или новую общую spatial-selection систему;
- большой глобальный блок `Связанные объекты`;
- тяжёлые карточки ссылок;
- отдельные кнопки `Открыть` возле каждого reference;
- масштабную переделку Серии;
- новую вкладку;
- production backend/runtime архитектуру.

## Отношение к Right Panel v1

Interface Linkage v1 строится поверх принятой Right Panel v1 и не отменяет её контракт.

Обязаны сохраниться:

- `Юнит`;
- `Инфо`;
- `Внимание`;
- `Память`;
- world-bound оверлеи;
- субъективность Внимания/Памяти;
- ограничения исторического `viewTime`;
- performance/runtime boundaries из `ACCEPTED_RIGHT_PANEL_V1.md`.

Новые правки правой панели из `memory-tab-v3` являются частью объединённого финального файла и не должны откатываться при переносе Interface Linkage.

## Ручная приёмка

Перед объявлением HTML текущей канонической базой проверить минимум:

1. Все основные вкладки открываются, правая панель `Юнит / Инфо / Внимание / Память` сохранена.
2. Выбор бойца на карте и в Редакторе юнита относится к одной сущности.
3. `Роль` и `Архетип бойца` независимы.
4. Ссылки профилей из бойца открывают соответствующий Общий редактор.
5. `Используется` показывает обратные ссылки и предупреждение перед удалением используемого объекта.
6. Laboratory override показывает реальный источник, baseline и experimental value.
7. Журнал ведёт к точному шагу Программы, а шаг — обратно к своим событиям Журнала.
8. Серия показывает выбранные пользовательские Метрики, а не параллельный каталог.
9. Исторический прогон показывает seed и производящий контекст.
10. Сохранение/открытие эксперимента сохраняет карту, юниты, Программу, Лабораторию и Метрики.
11. Переименование используемого профиля не превращает его в новую несвязанную сущность.
12. Новые элементы правой панели `memory-tab-v3` не потеряны.

## Production boundary

Этот принятый HTML подтверждает UX и взаимодействие разделов, но не доказывает наличие production:

- ExperimentRunner;
- telemetry aggregation/storage;
- deterministic replay;
- canonical backend storage;
- runtime override engine;
- production SSOT для профилей и ссылок.

При переносе в игру использовать существующие authoritative registries/storage/runtime contracts. Не копировать standalone JS/localStorage как production architecture.

## Следующая база

После ручной загрузки и проверки `polygon-interface-linkage-v1.html` он становится единственной базой следующей автономной UI-итерации Полигона.

Не начинать новые изменения от чистого Series v1.1 или отдельного Right Panel v1, если задача должна включать уже принятую связность интерфейса.
