Metrics v18 перенесена в `real-wargame-preview`.

Коммит, в котором окончательно зафиксировано exact-хранение принятой v18 через проверяемый delta-пакет:

Перенос не вводил production/runtime-реализацию telemetry: принят и перенесён UX/reference-прототип и его документационный/восстановительный контракт.

## Точное хранение в репозитории

Из-за ограничения remote GitHub connector на передачу одного крупного бинарного blob полный HTML v18 не записан в repository как один `.html` или `.gz`. Вместо этого repository хранит **точный проверяемый delta-пакет от уже принятого v44 к v18**:

`docs/subprojects/polygon-prototype/prototypes/metrics-v18/`

База:

- `polygon-map-editor-unified-v44-infantry-integrated-v2(1).html`;
- SHA-256: `0db5984d9d1f76149c31135b4a16f7e657f957c5512039853b9607353979b1d6`.

Delta:

- git patch, сжатый XZ, затем Base64;
- разбит на 12 небольших текстовых частей `parts/v44-to-metrics-v18.patch.xz.b64.part-*`;
- SHA-256 сжатого patch: `56f71c833a6feedbe82f40710d147b7838f1ca64d198274c913728f69be8baca`.

Скрипт:

`docs/subprojects/polygon-prototype/prototypes/metrics-v18/rebuild_metrics_v18.py`

проверяет SHA базового v44, собирает и проверяет delta, применяет его и затем проверяет SHA восстановленного v18. Локальная контрольная реконструкция дала побайтное совпадение с принятым HTML v18.

## Что принято в «Метриках»

### Конструктор измерений

Конструктор строится по принципу:

`поток данных → участники → необязательные ограничения состояния → период сбора`.

Расчёты, группировки и визуализация не задаются на этапе сбора. Конструктор определяет, какие структурированные исходные данные должны попасть в JSON, а анализ выполняется позже в Отчёте.

Специализированы группы:

- Огонь;
- Подавление;
- Обнаружение;
- Ранения и поражение;
- Состояние бойца;
- Движение;
- Маршрут и приказы;
- Позиция и укрытие;
- Действия;
- Пулемётный расчёт;
- Для разработчика.

Дополнительные фильтры по участникам, целям, источникам, угрозам и состояниям по умолчанию выключены и раскрываются только по запросу пользователя.

### Якоря программы

Период измерения может начинаться и заканчиваться на якорях Программы. Якорь прикрепляется к конкретному входу/выходу узла или к конкретному выходу ветвления и имеет стабильный ID.

### Левая панель

Добавленные измерения отображаются карточками. Карточка показывает:

- что измеряется;
- для кого;
- период;
- состояние сбора;
- объём собранных записей/событий.

Аналитические результаты в карточке не вычисляются. Измерение можно настроить, дублировать, отключить без удаления или удалить.

### Отчёт

Отчёт является отдельным аналитическим слоем над собранной telemetry. Его верхняя навигация в принятой v18 содержит только:

- `Обзор`;
- `Измерения`;
- `Хронология`.

Отдельные верхние вкладки `Карта` и `Данные` удалены. Пространственная аналитика отложена. Доступ к данным остаётся через экспорт, а табличное представление — через аналитический блок.

Экспорт сохраняет варианты:

- JSON для LLM;
- исходные данные JSONL;
- CSV текущего аналитического среза.

### Аналитические блоки

Пользователь может собирать Отчёт из восьми типов блоков:

1. Сводка;
2. Изменение во времени;
3. Распределение;
4. Сравнение;
5. Зависимость X → Y;
6. Хронология;
7. Таблица данных;
8. Цепочка событий.

Блоки имеют собственные фильтры, разбивки, статистику и период анализа и не изменяют исходное определение Метрики или raw telemetry. Один блок архитектурно может использовать несколько measurement-источников.

## Проверки переноса

В отчёте переноса v18 зафиксированы следующие проверки:

- v18 Report contract — PASS;
- v17 blocks regression — PASS;
- JavaScript syntax — PASS;
- восстановление v44 → v18 с точным ожидаемым SHA — PASS;
- локальное byte-for-byte совпадение восстановленного v18 с принятым HTML — PASS;
- runtime-код в итоговом переносе не менялся.

`npm run docs:sync`, `tsc` и production build в том окружении не запускались из-за отсутствия рабочего shell-checkout; этот факт не следует интерпретировать как выполненную проверку. Visual QA на этапе переноса также не запускалась.

## Постоянные правила дальнейшей UI-разработки

Принятие v18 не отменяет общий процесс Полигона:

- новый крупный UI сначала описывается и согласуется с пользователем **текстом**;
- до явного одобрения текстовой концепции HTML для нового UI не создаётся и не изменяется;
- большой автономный HTML Полигона передаётся пользователю только внутри ZIP-архива.

## Граница готовности

Это **принятый автономный UX-прототип и контракт интерфейса данных**, а не новый источник истины симуляции.

В демонстрационном Отчёте используются явно помеченные demo-data для проверки интерфейса. Реальное подключение сборщика telemetry к production simulation является отдельной задачей.

Не считать реализованными только на основании этого прототипа:

- production-хранилище telemetry;
- runtime-сбор всех перечисленных потоков;
- пространственную аналитику карты;
- серию прогонов;
- журнал экспериментов.
