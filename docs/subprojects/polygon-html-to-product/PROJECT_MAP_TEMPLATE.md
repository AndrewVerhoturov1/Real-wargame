# Шаблон карты состояния проекта «Перенос Полигона»

## Цель

Эта схема нужна не для технической документации, а для пользователя: за несколько секунд должно быть понятно:

1. где сейчас находится подпроект;
2. что уже принято;
3. что выполняется прямо сейчас;
4. кто отвечает за каждое направление;
5. какие задачи идут параллельно;
6. что заблокировано и почему;
7. какая следующая точка объединения результатов.

Codex может рисовать её любым удобным инструментом — mind map, flowchart, Mermaid, Excalidraw-подобной схемой или другим поддерживаемым форматом. Важна структура ниже, а не конкретный движок рисования.

---

## 1. Два слоя одной карты

Карта всегда состоит из двух связанных слоёв.

### Слой A — дорога проекта

Горизонтальная цепочка крупных принятых этапов:

```text
[Подготовка и решения]
        ↓
[UI Shell + первый LIVE Unit]
        ↓
[Info / Attention / Memory LIVE]
        ↓
[Program ↔ Journal LIVE]
        ↓
[History / viewTime]
        ↓
[Metrics]
        ↓
[Laboratory]
        ↓
[Series / Replay / Persistence]
        ↓
[Full Save/Open + Unit Editor]
        ↓
[Сквозная приёмка]
        ↓
[GO → transfer в real-wargame-preview]
        ↓
[отдельный запрос → deployment]
```

Эта строка отвечает на вопрос: **«Как далеко мы вообще продвинулись?»**

Не нужно превращать её в сотни технических задач. Здесь только крупные этапы, понятные владельцу продукта.

### Слой B — дорожки исполнителей

Под дорогой проекта располагаются четыре горизонтальные рабочие дорожки:

```text
АРКА     | UI shell / визуальная оболочка / контейнеры
ПУЛЬС    | selection / UnitModel / LIVE Unit / команды
ЛИНЗА    | Info / Attention / Memory
ХРОНИСТ  | Program-Journal / History / Metrics / Lab / Series / persistence
```

Каждая конкретная работа располагается одновременно:

- под своим крупным этапом;
- на дорожке своего исполнителя.

Так пользователь одновременно видит **что делаем** и **кто это делает**.

---

## 2. Обязательный маркер «МЫ ЗДЕСЬ»

На карте всегда должен быть ровно один основной маркер:

```text
        ★ МЫ ЗДЕСЬ
```

Он ставится не на отдельный технический commit, а на текущую **точку проекта**.

Пример начального состояния:

```text
Подготовка ✓
    ↓
★ МЫ ЗДЕСЬ
UI Shell + первый LIVE Unit
    ↓
Right Panel LIVE
    ↓
...
```

Если несколько параллельных работ активны, основной маркер остаётся на ближайшей общей точке интеграции, а сами активные задачи получают статус `В РАБОТЕ`.

Для текущей организации первой общей точкой является:

```text
АРКА + ПУЛЬС
→ первый настоящий LIVE Unit
```

ЛИНЗА и ХРОНИСТ при этом могут находиться дальше по своим исследовательским дорожкам.

---

## 3. Минимальная карточка любой задачи

Каждый узел карты должен содержать максимум пять полезных полей:

```text
Название
Статус
Исполнитель
Результат / выход
Зависимость или следующий переход
```

Если задача уже имеет принятый GitHub-результат, дополнительно мелким техническим текстом указывается exact commit SHA.

Пример:

```text
┌──────────────────────────────┐
│ LIVE Unit contract           │
│ В РАБОТЕ                     │
│ ПУЛЬС                        │
│ Выход: read/write contract   │
│ → первый LIVE Unit           │
│ SHA: ...                     │
└──────────────────────────────┘
```

Не помещать в основную карту списки файлов, длинные API, тестовые команды и технические объяснения. За деталями пользователь должен иметь возможность перейти в соответствующий документ/commit.

---

## 4. Единые статусы

На всей карте используется один небольшой набор состояний.

```text
○ НЕ НАЧАТО
● В РАБОТЕ
✓ ПРИНЯТО
◇ ЖДЁТ ЗАВИСИМОСТЬ
! БЛОКЕР / НУЖНО РЕШЕНИЕ
↺ НА ДОРАБОТКЕ
```

Codex может использовать цвета, если выбранный инструмент их поддерживает:

- серый — не начато;
- синий — в работе;
- зелёный — принято;
- жёлтый — ждёт зависимость/решение;
- красный — блокер;
- фиолетовый или оранжевый — доработка.

Но форма/текст статуса обязательны: карта должна оставаться понятной и без цвета.

---

## 5. Отдельные пользовательские решения — как ворота

Решения владельца продукта нельзя прятать внутри технической задачи. Они рисуются отдельными воротами между этапами:

```text
◆ РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ
```

Примеры:

- Unit Editor: authoring / LIVE / два режима;
- replay: rerun или recorded history;
- persistence первой версии;
- scope Metrics;
- поддерживаемые типы Memory;
- классы `Apply Globally`;
- явный GO на transfer;
- отдельное разрешение на deployment.

Если этап упирается в такое решение, стрелка должна приходить именно в ворота, а не выглядеть как техническая ошибка исполнителя.

---

## 6. Параллельность показывается дорожками, а не размножением этапов

Не рисовать четыре отдельные карты проекта.

Правильный принцип:

```text
                   [ЭТАП 1]        [ЭТАП 2]        [ЭТАП 3]

АРКА        ───────[задача]────────[задача]──────────────

ПУЛЬС       ───────[задача]────────[задача]──────────────

ЛИНЗА       ────────────────[задача]────────[задача]─────

ХРОНИСТ     ───────[исслед.]───────────────[задача]─────
```

Стрелка между дорожками означает реальную зависимость или точку интеграции.

Пунктирная линия может означать «можно выполнять параллельно, прямой зависимости нет».

---

## 7. Точки интеграции должны быть заметнее обычных задач

Карта должна подчёркивать не только работу отдельных исполнителей, но и моменты, когда их результаты превращаются в один продукт.

Использовать узлы вида:

```text
◎ ИНТЕГРАЦИЯ
```

Основные ожидаемые интеграции первой фазы:

### Интеграция 1

```text
АРКА: готовый UI shell
        +
ПУЛЬС: selection + LIVE Unit contracts
        ↓
◎ ПЕРВЫЙ LIVE UNIT
```

### Интеграция 2

```text
АРКА: right-panel containers
        +
ЛИНЗА: product data contracts
        ↓
◎ INFO / ATTENTION / MEMORY LIVE
```

### Интеграция 3

```text
АРКА: Program/Journal containers
        +
ХРОНИСТ: causal identity
        ↓
◎ PROGRAM ↔ JOURNAL LIVE
```

Дальше аналогично для History, Metrics, Laboratory и Series.

---

## 8. Верхняя панель состояния карты

Над самой схемой Codex должен выводить короткий блок состояния, обновляемый вместе с картой:

```text
ПОДПРОЕКТ: Перенос Полигона в продукт
ТЕКУЩИЙ ЭТАП: <крупный этап>
МЫ ЗДЕСЬ: <ближайшая общая точка>
АКТИВНЫ: <АРКА / ПУЛЬС / ...>
ГЛАВНЫЙ БЛОКЕР: <нет / коротко>
СЛЕДУЮЩАЯ ИНТЕГРАЦИЯ: <название>
ПОСЛЕДНИЙ ПРИНЯТЫЙ SHA: <commit или «нет»>
```

Это самая полезная часть для быстрого чтения состояния без изучения всей mind map.

---

## 9. Что Codex обновляет после каждого handoff

После получения и проверки результата исполнителя Codex должен:

1. найти соответствующий узел на карте;
2. изменить его статус;
3. записать exact commit SHA принятого результата;
4. отметить новый blocker, если он появился;
5. открыть следующую задачу, если зависимость снята;
6. при необходимости передвинуть `★ МЫ ЗДЕСЬ`;
7. обновить верхний блок состояния;
8. не отмечать задачу `ПРИНЯТО`, пока exact SHA не проверен оркестратором.

Таким образом карта является визуальным представлением проверенного GitHub-состояния, а не памятью чатов.

## 10. Начальный каркас для текущей фазы

На старте следующей фазы карта может выглядеть концептуально так:

```text
                         ДОРОГА ПРОЕКТА

[Анализ и план ✓]
        │
        ▼
[Shell + LIVE Unit] ★ МЫ ЗДЕСЬ
        │
        ├──────────────► [Right Panel LIVE]
        │                         │
        └──────────────► [Program ↔ Journal]
                                  │
                                  ▼
                              [History]
                                  │
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
                [Metrics]     [Laboratory]   [Series]
                    └─────────────┼─────────────┘
                                  ▼
                           [Full Save/Open]
                                  ▼
                            [Приёмка]

                         ДОРОЖКИ ИСПОЛНИТЕЛЕЙ

АРКА     ● UI Shell ────────────────┬──────── UI integration ────────
                                    │
ПУЛЬС    ● LIVE Unit contract ──────┴─► ◎ ПЕРВЫЙ LIVE UNIT

ЛИНЗА    ● Info/Attention/Memory audit ─────► future right-panel slices

ХРОНИСТ  ● Program↔Journal identity ─► History/Metrics/Lab/Series foundations
```

Это только логический шаблон. Codex должен перестраивать геометрию под выбранный инструмент, сохраняя смысл, статусы, четыре именных дорожки и один основной маркер текущего положения.

---

## 11. Правило простоты

Если схема перестала помещаться на один экран и пользователь не может за 10–15 секунд ответить на вопросы «где мы?», «кто работает?» и «что дальше?», схема слишком подробная.

В таком случае:

- оставить на главной карте только крупные этапы и текущие задачи;
- завершённые детали сворачивать в один узел;
- технические подзадачи переносить в отдельную drill-down схему;
- никогда не удалять четыре именных дорожки и `★ МЫ ЗДЕСЬ`.

Главная карта — это **панель навигации по проекту для пользователя**, а не замена `WORK_PLAN.md`.
