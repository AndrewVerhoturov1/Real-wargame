# Полигон — функциональная волна редакторов 2026-08-18

Статус: **канонический план следующего функционального этапа окна «Редакторы»** после визуального переноса принятого HTML-прототипа.

## 1. Исходная точка

```text
repository: AndrewVerhoturov1/Real-wargame
base_branch: real-wargame-preview
planning_base_commit: bd25f5debc312db7021b1515a525697ad248fff1
planning_base_tree: 7dd8f092da7ae78eb41aac6c1d6edb71bebe4a9f
prototype_artifact: polygon-series-v1.1-memory-v3-interface-linkage(1).html
prototype_version: polygon-map-editor-unified-v44-infantry-integrated-20260815-memory-v3-interface-linkage-v1
```

Перед каждым реальным кодовым стартом исполнитель обязан заново получить актуальный `HEAD` `real-wargame-preview` и работать в отдельной feature-ветке, если оркестратор явно не задаёт согласованный stacked-base на точном принятом SHA соседнего исполнителя.

## 2. Главный приоритет

**Принятые решения HTML-прототипа имеют приоритет над старым поведением продукта.**

Порядок источников решения:

1. явные решения пользователя;
2. принятый HTML-прототип;
3. архитектура продукта — определяет, как правильно реализовать решение;
4. старое поведение продукта — используется только там, где пользователь и прототип ничего не определили.

Нельзя сохранять старое поведение только потому, что оно уже реализовано. Если прототип требует `X`, а продукт делает `Y`, это фиксируется как продуктовый разрыв и планируется доработка `Z`.

При этом нельзя переносить технические костыли HTML: DOM как источник истины, временные глобальные объекты, fake data, prototype-only `localStorage` и другие непроизводственные механизмы.

## 3. Параллельная визуальная линия

Визуальная часть идёт отдельно и не считается функциональной реализацией.

Текущий известный кандидат:

```text
branch: feat/20260817-polygon-editors-visual-parity
candidate_commit: 13a70b76bd5087b87c0767970eb378ba192a1b49
changed_file: src/combat-lab/game-editors/polygon-global-editor-feature-grid.css
logic_or_data_changes: none
```

На момент фиксации этого документа кандидат заявляет:

- геометрию общего окна как в принятом HTML;
- правильную левую навигацию без ошибочных пиктограмм;
- строки меню 34 px;
- визуальную структуру «Профилей маршрута»;
- responsive-переходы 1250 / 900 px;
- скрытие «Данных бойца» и «Графа поведения» с поверхности Полигона;
- честно недоступный пункт «Типы поверхностей» из-за отсутствия product capability.

Но для exact SHA `13a70b76...` ещё не следует считать пройденными `npm run verify:preview`, post-change browser QA и screenshot comparison, пока это не подтвердит оркестратор.

### Зависимость СТЫКА от визуальной линии

СТЫК не должен строить функциональный слой поверх случайного промежуточного CSS-состояния.

Его кодовый старт допускается только после одного из двух вариантов:

1. визуальная ветка принята и перенесена в актуальный `real-wargame-preview`; **или**
2. оркестратор явно выдаёт СТЫКУ точный принятый visual SHA как stacked-base.

Текущий `13a70b76...` является известным кандидатом, а не вечным hard-coded base.

## 4. Три именованных исполнителя

### СТЫК — подключение готового

**Роль:** новый интерфейс → уже существующие реальные product owners и механизмы.

СТЫК не придумывает новую игровую механику и не переписывает доменные системы, если требуемая операция уже существует.

Его задача — добиться, чтобы принятый интерфейс работал через настоящие registry/store/command/save contracts продукта.

Prompt:

`docs/subprojects/polygon-html-to-product/prompts/07_STYK_EDITOR_BINDING.md`

### КУЗНЕЦ — реальные продуктовые разрывы

**Роль:** всё, что нельзя честно решить одной привязкой интерфейса к уже готовой операции.

Работа разделена на две фазы.

**Фаза A — сейчас:** полный план. Product code запрещён.

**Фаза B — только после завершения СТЫКА и отдельного GO:** реализация согласованных доработок на свежей базе.

Prompt:

`docs/subprojects/polygon-html-to-product/prompts/08_KUZNETS_EDITOR_GAPS.md`

### ПОЧВА — новая функция «Типы поверхностей»

**Роль:** спроектировать самостоятельную продуктовую функцию Surface Types, которой сейчас в продукте нет как authoritative owner.

До фразы пользователя `КОНЦЕПЦИЯ УТВЕРЖДЕНА` — только исследование и обсуждение. После утверждения — документация и план. Product code — только после ещё одного отдельного GO.

Prompt:

`docs/subprojects/polygon-html-to-product/prompts/09_POCHVA_SURFACE_TYPES_CONCEPT.md`

## 7. Три отдельные незавершённые игровые механики маршрута

Они уже заложены в профили маршрута, но их runtime не считается подготовленным:

1. `exposureWeight` — нет подтверждённого полноценного субъективного фактора видимости/экспозиции противника;
2. `enemyDistanceWeight` — нет подтверждённого полноценного субъективного расстояния до противника в route cost;
3. `territoryWeights.friendly / neutral / enemy` — территориальная стоимость заявлена как будущая механика.

Решение этой волны:

- **не реализовывать эти три механизма сейчас**;
- не создавать synthetic/fake effect;
- после СТЫКА КУЗНЕЦ должен сделать в интерфейсе честное состояние `не подготовлено / пока не работает` в принятом визуальном языке;
- сохранить сами поля и их будущий смысл;
- полноценную игровую реализацию вынести в отдельные последующие задачи.

## 8. Известные продуктовые разрывы, которые обязан перепроверить КУЗНЕЦ

Это не автоматический приказ сразу менять код. Это минимальный обязательный список для фазы A.

### 8.1 Встроенные GameplayTuning-профили

Прототип разрешает прямую настройку встроенных:

- Архетипов бойцов;
- Профилей восприятия;
- Ранений и подавления.

Текущий общий product editor исторически использует политику «встроенные значения неизменяемы, создайте копию». КУЗНЕЦ должен спроектировать Polygon-specific решение, сохраняющее принятый смысл прототипа без разрушения authoritative defaults/versioning.

### 8.2 Опубликованные записи Combat Catalog

Прототип допускает tuning опубликованной записи в Полигоне. Текущий catalog editor исторически делает published revision read-only и требует новую revision.

Нужна явная продуктовая политика для Polygon tuning. Нельзя молча оставить старый read-only UX как целевой.

### 8.3 Environment Profiles

Прототип требует:

`draft -> Save / Cancel -> dirty guard`.

Текущий Environment editor исторически сохраняет изменения автоматически. Для Полигона это реальный конфликт поведения, а не визуальная мелочь.

### 8.4 Межредакторные ссылки и «Используется»

Прототип предполагает переходы по реальному `id/profileId` и блок «Используется» для связанных сущностей.

СТЫК использует существующие authoritative open routes там, где они есть. Если общего reverse-reference / where-used contract в продукте нет, КУЗНЕЦ планирует его как реальный общий механизм. Запрещено вычислять использование через DOM, stringify debug state или fake списки.

### 8.5 Сброс отдельных полей

Если product owner уже предоставляет нормативное/default значение и безопасную write-операцию, это зона СТЫКА: новый UI просто реализует принятую кнопку `↺`.

Если owner не предоставляет достаточный контракт для однозначного сброса, КУЗНЕЦ фиксирует и проектирует недостающий product seam. Нельзя заводить второй параллельный набор defaults внутри presentation-слоя.

## 9. Что не является отдельной большой доработкой

По текущему исследованию не нужно автоматически создавать отдельные core-задачи для:

- Тактических позиций;
- Профилей движения;
- большинства полей Профилей маршрута;
- основной модели Профилей внимания;
- основной модели Направленного рельефа.

Сначала СТЫК должен доказать, что эти возможности действительно можно подключить к принятому интерфейсу через существующий product contract.

## 10. Общие запреты

Для всей волны:

- не создавать fake editor ради визуального совпадения;
- не создавать fake data или второй gameplay truth;
- не вычислять LOS/AI/runtime в UI;
- не переносить prototype `localStorage` как product storage;
- не дублировать registry/store;
- не менять `main`;
- не переносить изменения в `real-wargame-preview` без отдельного пользовательского GO;
- не делать deploy без отдельного пользовательского запроса;
- не считать визуальный candidate автоматически функционально принятым.

## 11. Оркестраторские точки передачи

### Для СТЫКА

Оркестратор передаёт:

- exact current product/base SHA;
- exact accepted visual SHA или подтверждение, что visual result уже в preview;
- prompt `07_STYK_EDITOR_BINDING.md`;
- результаты аналитики редакторов;
- запрет на самостоятельное расширение scope.

### Для КУЗНЕЦА, фаза A

Можно запускать сразу от текущей документационной/продуктовой базы. Результат — **только полный план разрывов**.

### Для КУЗНЕЦА, фаза B

Запуск только после:

1. exact результата СТЫКА;
2. независимой проверки результата СТЫКА;
3. свежего base decision оркестратора;
4. отдельного пользовательского GO на product code КУЗНЕЦА.

### Для ПОЧВЫ

Можно запускать этап 1 сразу. Он обсуждает архитектуру непосредственно с пользователем и обязан остановиться до кода.

## 12. Критерий завершения этой волны документации

Документационная волна считается подготовленной, когда:

- роли СТЫК / КУЗНЕЦ / ПОЧВА не пересекаются;
- каждый имеет отдельный prompt;
- текущий visual candidate записан как параллельная зависимость, а не как функциональный результат;
- три отложенных route runtime mechanics явно исключены из текущей реализации;
- Surface Types не маскируются под Environment Profiles;
- порядок пользовательских и оркестраторских GO зафиксирован.
