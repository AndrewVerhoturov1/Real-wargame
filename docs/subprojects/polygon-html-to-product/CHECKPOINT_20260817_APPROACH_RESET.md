# Полигон — checkpoint и новый подход поэлементного переноса

Дата: 2026-08-17

## Статус решения

Пользователь решил сохранить текущий результат подпроекта в `real-wargame-preview` как **технический checkpoint**, после чего сменить подход к дальнейшей реализации интерфейса.

Критически важно: перенос этого состояния в `real-wargame-preview` **не является визуальной приёмкой** и не означает, что текущий UI считается финальным или удовлетворительным.

Пользователь прямо указал, что текущий визуальный результат его пока не устраивает. Следующая итерация должна начинаться уже с нового подхода, а не с продолжения бесконечной pixel-polish текущей архитектуры.

## Новый принятый подход (зафиксирован 2026-08-17)

Пользователь принял подход **поэлементного переноса Полигона**:

1. Полигон переносится по одному элементу/вертикальному срезу: вкладка, карта или другой конкретный элемент.
2. Для каждого элемента параллельно работают два исполнителя:
   - **визуальный** — переносит вёрстку, графику, отступы, цвета, размеры, шрифты и иконки из утверждённого HTML-прототипа пиксель в пиксель; функциональные связи пока не подключает;
   - **аналитик** — сравнивает прототип и продукт, определяет, что уже есть, что частично есть, чего нет, настоящих владельцев данных, точки подключения и назначение каждой кнопки.
3. Затем запускаются отдельные исполнители:
   - подключающий уже готовые функции;
   - доделывающий отсутствующие/неполные возможности;
   - реализующий новые запланированные функции прототипа;
   - при необходимости дополнительных исполнителей может быть несколько.
4. Весь функциональный объём HTML-прототипа, включая запланированные возможности, остаётся целью подпроекта.
5. Результаты прежней six-X шестёрки сохраняются как исторические исследования и технический контекст; они **не считаются автоматическим основанием для объединения кода**.
6. Текущий checkpoint — техническая база, но **визуально не принят**.
7. Запрещены автоматический перенос в `real-wargame-preview`, изменения `main`, merge и deploy без отдельного явного разрешения пользователя.

Канонический процесс и критерии перехода элемента:

`docs/subprojects/polygon-html-to-product/ELEMENT_MIGRATION_WORKFLOW.md`

## Что технически сохраняется

Checkpoint сохраняет уже выполненную инженерную работу, чтобы не потерять рабочие контракты и продуктовые связи:

- живая product map внутри нового shell Полигона;
- реальный `PixiUnitRenderer` и новая token/LOD-подача юнитов;
- map selection → настоящий `unitId` → `UnitModel` → LIVE Unit;
- штатный write/readback для поддерживаемых действий над выбранным юнитом;
- LIVE правая панель на реальных product owners, включая `Инфо`;
- интеграция существующего `GameEditorRegistry` / product editors в Polygon shell;
- entity context menu и маршрутизация в реальные панели/редакторы;
- presentation-слои Map Editor, Unit Editor и Global Editors, созданные в текущей попытке визуального сближения;
- контракты и smoke-проверки, добавленные этой волной.

Это полезная техническая база, даже если текущая композиция интерфейса будет существенно пересмотрена.

## Что НЕ считается принятым

После transfer нельзя трактовать следующие пункты как пользовательскую приёмку:

- текущую визуальную композицию центральной карты;
- текущую компоновку Map Editor;
- текущую компоновку Unit Editor;
- текущий Global Editors workspace;
- внутреннюю верстку отдельных редакторов;
- текущую стилизацию и плотность правой панели `Инфо`;
- соответствие текущего продукта HTML-прототипу «pixel-perfect»;
- сам подход «оборачивать существующие product editors presentation-слоями до полного сходства» как окончательно выбранную архитектуру.

Текущие presentation-решения следует считать **экспериментальным checkpoint**, а не новой дизайн-системой проекта.

## Что было вне текущего scope и остаётся незавершённым

Перенос checkpoint не расширяет scope автоматически. В частности, не считаются завершёнными только потому, что ветка попадёт в preview:

- содержимое левых вкладок `Программа`, `Лаборатория`, `Серия`, `Метрики`, `Журнал`;
- полный UI остальных правых вкладок (`Внимание`, `Память` и другие);
- полный Unit Editor authoring;
- experiment/history/telemetry/replay/Save/Open объём;
- любые отсутствующие product capabilities, которые HTML-прототип показывал как концепт.

## Новое правило после checkpoint

После переноса в `real-wargame-preview`:

1. не продолжать автоматически текущую pixel-parity стратегию;
2. не считать старые визуальные acceptance-формулировки разрешением на дальнейшую полировку того же решения;
3. использовать зафиксированный подход поэлементного переноса из `ELEMENT_MIGRATION_WORKFLOW.md`;
4. новую работу начинать от актуального `real-wargame-preview` HEAD отдельной feature-веткой;
5. технические owners и live contracts переиспользовать, если новый подход не требует иного;
6. presentation-код текущего checkpoint можно менять, упрощать или удалять в новой итерации, если это нужно для нового дизайна;
7. `main` не затрагивать без отдельного пользовательского решения.

## Handoff следующему исполнителю

Первое действие следующего исполнителя — не «доделать pixel-perfect», а начать **поэлементный перенос** по зафиксированному процессу `ELEMENT_MIGRATION_WORKFLOW.md`: выбрать конкретный элемент, запустить параллельно визуального исполнителя и аналитика, затем исполнителей подключения готовых функций, доделывания недостающего и реализации новых запланированных функций.

До этого момента текущий checkpoint является сохранённой рабочей базой, а не целевым дизайном.
