# Поэлементный перенос Полигона — канонический процесс

Статус: текущий принятый подход пользователя.
Дата фиксации: 2026-08-17.
Последнее уточнение: 2026-08-18 — специализированная функциональная волна окна «Редакторы».

## 1. Принцип

Полигон переносится из утверждённого HTML-прототипа в продукт **по одному элементу/вертикальному срезу**: вкладка, карта или другой конкретный элемент. Весь функциональный объём HTML-прототипа, включая запланированные возможности, остаётся целью подпроекта.

Для любого конфликта между принятым прототипом и старым product behavior действуют явные решения пользователя и принятый прототип. Архитектура продукта определяет правильный способ реализации, но не должна молча менять утверждённый пользовательский смысл.

## 2. Два параллельных исполнителя на каждый элемент

1. **Визуальный** — переносит вёрстку, графику, отступы, цвета, размеры, шрифты и иконки из утверждённого HTML-прототипа пиксель в пиксель; функциональные связи пока не подключает.
2. **Аналитик** — сравнивает прототип и продукт и определяет:
   - что уже есть;
   - что частично есть;
   - чего нет;
   - настоящих владельцев данных;
   - точки подключения;
   - назначение каждой кнопки.

## 3. Затем отдельные исполнители

Общий процесс после визуального и аналитического этапов:

- подключающий уже готовые функции;
- доделывающий отсутствующие/неполные возможности;
- реализующий новые запланированные функции прототипа;
- при необходимости дополнительных исполнителей может быть несколько.

### 3.1 Специализация для текущего элемента «Редакторы»

Для окна общих редакторов 2026-08-18 роли зафиксированы конкретно:

1. **СТЫК** — подключает новый принятый интерфейс к уже существующим настоящим product owners и операциям. Не создаёт отсутствующую игровую механику.
2. **КУЗНЕЦ** — отвечает за реальные product gaps. Сейчас выполняет только planning phase; product code ждёт завершения СТЫКА и отдельного пользовательского GO.
3. **ПОЧВА** — проектирует новую функцию «Типы поверхностей». До `КОНЦЕПЦИЯ УТВЕРЖДЕНА` только исследует и обсуждает архитектуру с пользователем; code запрещён.

Канонический контракт текущей editor-волны:

`docs/subprojects/polygon-html-to-product/EDITORS_FUNCTIONAL_WAVE_20260818.md`

Промты:

```text
docs/subprojects/polygon-html-to-product/prompts/07_STYK_EDITOR_BINDING.md
docs/subprojects/polygon-html-to-product/prompts/08_KUZNETS_EDITOR_GAPS.md
docs/subprojects/polygon-html-to-product/prompts/09_POCHVA_SURFACE_TYPES_CONCEPT.md
```

### 3.2 Параллельная visual dependency для «Редакторов»

Текущая visual-parity работа идёт отдельно. Известный кандидат на момент фиксации:

```text
feat/20260817-polygon-editors-visual-parity
@ 13a70b76bd5087b87c0767970eb378ba192a1b49
```

Он presentation-only и не считается функциональным результатом. СТЫК начинает код только после того, как оркестратор определил точный принятый visual base: либо visual result уже перенесён в `real-wargame-preview`, либо СТЫКУ явно выдан accepted stacked SHA.

### 3.3 Три route-механики, исключённые из текущей реализации

Для `Профилей маршрута` текущая editor-волна **не реализует**:

```text
exposureWeight
enemyDistanceWeight
territoryWeights.friendly / neutral / enemy
```

Они остаются будущими gameplay/runtime задачами. После СТЫКА КУЗНЕЦ в своей code phase только честно обозначает их в интерфейсе как `не подготовлено / пока не работает`, без fake effect.

### 3.4 Surface Types — отдельная capability

«Типы поверхностей» не подменяются `Environment Profiles` и не создаются как fake editor ради одиннадцатого пункта. ПОЧВА сначала проектирует настоящую доменную модель и её связь с картой, движением, восприятием, защитой, инженерными работами и persistence.

## 4. Критерии перехода элемента

Элемент считается готовым к интеграции только при выполнении всех условий:

- визуальный результат проверен против HTML;
- аналитическая карта функций/владельцев закончена;
- готовые функции подключены через настоящих владельцев данных;
- пробелы классифицированы;
- новые функции имеют отдельный объём и критерии приёмки;
- результат не содержит дублирующего состояния и не меняет соседние элементы без договора.

Для окна «Редакторы» дополнительно:

- СТЫК доказал wiring готовых product capabilities;
- КУЗНЕЦ отделил `BINDING_ONLY` от настоящих `PRODUCT_GAP`;
- три отложенных route runtime mechanics не выданы за работающие;
- Surface Types остаётся отдельной capability до утверждения концепции ПОЧВЫ.

## 5. Отношение к прежней работе

Результаты прежней six-X волны сохраняются как исторические исследования и технический контекст. Они **не являются автоматическим основанием** для объединения кода.

Текущий checkpoint — техническая база, но **визуально не принят**.

## 6. Запреты

Без отдельного явного разрешения пользователя запрещены:

- автоматический перенос в `real-wargame-preview`;
- изменения `main`;
- merge;
- deploy.

Для editor-волны дополнительно запрещено:

- создавать fake Surface Types editor/data;
- переносить prototype-only localStorage/DOM state как product architecture;
- писать product code КУЗНЕЦА до завершения СТЫКА и нового GO;
- писать product code ПОЧВЫ до утверждения концепции и отдельного GO.
