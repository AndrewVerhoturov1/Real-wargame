# План работы по переносу Полигона из HTML-прототипа в продукт

## 0. Назначение документа

Этот документ превращает выводы `MIGRATION_SYNTHESIS.md` в рабочую последовательность задач.

Цель — перенести принятый интерфейс Полигона в продукт Real Wargame так, чтобы новый UI работал поверх настоящих продуктовых владельцев данных и команд, а не переносил внутрь продукта временную архитектуру HTML-прототипа.

Рабочий принцип:

```text
принятый UX прототипа
→ минимальный UI/adapter слой
→ существующие владельцы Real Wargame
→ проверка реального результата
```

План подготовлен от документационного состояния feature-ветки:

```text
feature/20260815-polygon-html-to-product
62faf35d5e11e49e08b523f84e038a407fae1f8d
```

Перед первой кодовой задачей и перед каждой новой независимой кодовой веткой необходимо заново получить точный текущий HEAD `real-wargame-preview`. SHA выше не является автоматически разрешённой кодовой базой будущей реализации.

Основные источники:

- `SUBPROJECT.md`;
- `STATUS.md`;
- `MIGRATION_VISION.md`;
- `MIGRATION_SYNTHESIS.md`;
- `UX_GAP_AUDIT.md`;
- `PRODUCT_OWNER_MAP.md`;
- `RUNTIME_GAP_AUDIT.md`;
- принятые документы Interface Linkage v1, Right Panel v1, Journal v4, Metrics v18, Laboratory v1, Series v1;
- `AGENTS.md`;
- `.agents/skills/real-wargame-orchestration/SKILL.md`.

## 1. Что считаем конечным результатом

Перенос считается завершённым не тогда, когда новый интерфейс визуально похож на HTML, а когда принятые пользовательские сценарии работают на настоящих системах продукта.

Конечное состояние:

- новый Полигон имеет принятую общую компоновку;
- карта, выбранный юнит, правая панель и рабочие вкладки используют одну и ту же продуктовую идентичность сущностей;
- `Юнит`, `Инфо`, `Внимание`, `Память` читают данные у настоящих владельцев;
- изменения состояния идут через штатные команды и write-boundaries продукта;
- Program и Journal связаны причинно на устойчивых ID;
- History показывает прошлое без изменения LIVE-состояния и без утечки знаний из будущего;
- Metrics является владельцем определений измерений;
- Series использует выбранные Metrics и хранит контекст каждого прогона;
- Laboratory временно переопределяет настоящие параметры, не создавая второй каталог;
- Save/Open сохраняет согласованный эксперимент, а не только отдельную сцену;
- старый HTML остаётся эталоном UX, но не runtime-зависимостью продукта;
- demo/mock/localStorage-состояние HTML нигде не становится источником истины.

## 2. Неподвижные ограничения

На всех этапах действуют следующие правила.

1. **Не переносить HTML как приложение.** Переносится пользовательский контракт, а не его внутренняя модель данных.
2. **Один объект — один настоящий владелец.** UI не хранит параллельную копию игрового состояния.
3. **Чтение и изменение разделены.** Панель читает состояние, а изменение выполняется штатной командой или утверждённым product write-path.
4. **Не вычислять в UI то, что принадлежит симуляции.** Особенно LOS, perception, attention, memory, combat state и исторические данные.
5. **Не создавать временные mock-механизмы ради заполнения интерфейса.** Если product capability отсутствует, функция либо ждёт foundation-задачу, либо получает явно урезанный честный объём.
6. **Не переносить `window.*`, demo arrays, synthetic results, prototype IDs и локальные router-функции как продуктовый API.**
7. **Не смешивать стартовое описание эксперимента и живой runtime.** Особенно в Unit Editor.
8. **Каждая кодовая задача начинается с точного текущего `real-wargame-preview` SHA.**
9. **Продуктовый код реализуется на feature-ветке.** Не писать непосредственно в `real-wargame-preview` или `main`.
10. **Перенос в `real-wargame-preview` — только после явного GO пользователя.**
11. **Деплой — отдельное разрешение пользователя.** Push и transfer не означают deployment.
12. **После каждого вертикального среза должен существовать проверяемый пользовательский сценарий, а не только набор новых компонентов.**

---

## 3. Общая стратегия

Не делать сначала весь новый каркас, затем все вкладки и только после этого подключать данные.

Работа идёт вертикальными срезами:

```text
маленький законченный пользовательский сценарий
→ настоящий owner
→ настоящая команда/чтение
→ тест
→ визуальная проверка
→ следующий сценарий
```

Первый обязательный доказательный срез:

```text
карта
→ выбор настоящего юнита
→ правый «Юнит» LIVE
→ изменение позы штатной командой
→ обновление того же UnitModel
→ переход к связанному общему профилю
```

Если этот путь не получается сделать без локальной UI-копии состояния, дальнейший перенос приостанавливается до исправления границы. Нельзя размножать неправильный шаблон на остальные вкладки.

# Часть I. Подготовка к реализации

## Этап 1. Зафиксировать продуктовые решения

### Цель

Отделить решения владельца продукта от вопросов, которые исполнитель может закрыть чтением кода.

### Решения

Нужно зафиксировать семь решений.

#### 1. Unit Editor

Выбрать один вариант:

- редактор стартового состояния эксперимента;
- управление живым runtime;
- два явно разделённых режима `До запуска` и `LIVE`.

Это не блокирует узкий первый LIVE-срез, но блокирует полный Unit Editor.

#### 2. Replay

Определить, что означает `Воспроизвести прогон` в первой версии:

- повторный расчёт из замороженных входов и seed;
- воспроизведение сохранённой исторической дорожки.

#### 3. Persistence

Определить обязательный уровень сохранения первой версии:

- только текущая сессия;
- локальное долговременное хранение;
- файл;
- другое утверждённое хранилище.

Отдельно решить, обязаны ли Series и все RunRecord переживать перезапуск приложения.

#### 4. Metrics v18

Выбрать:

- весь принятый динамический конструктор сразу;
- поэтапный вариант с ограниченным набором реальных потоков данных.

#### 5. Memory

Определить, достаточно ли первой версии только реально подтверждённых runtime-типов памяти или обязательны также `intel` и `presumed front`.

#### 6. Laboratory / Apply Globally

Определить, для каких классов параметров разрешено постоянное изменение authoritative baseline.

#### 7. Технические настройки

Решить, куда уходят текущие технические worker/diagnostic controls:

- скрываются из основного UX;
- остаются в отдельном расширенном/служебном режиме.

### Результат этапа

Короткий decision record без проектирования реализации.

### Критерий завершения

Для каждого решения есть один выбранный вариант либо явно указано, на каком более позднем этапе решение станет обязательным.

## Этап 2. Разрешить точную кодовую базу

### Цель

Не реализовывать план от устаревшей версии продукта.

### Действия

- получить удалённый HEAD `real-wargame-preview`;
- записать полный 40-символьный SHA;
- сравнить его с базой трёх аудитов;
- проверить только затрагиваемые первым срезом product boundaries;
- создать новую feature-ветку реализации от этого точного SHA;
- не переносить на неё документационную feature-ветку автоматически, если это не требуется правилами подпроекта.

### Обязательная перепроверка первого среза

На точной базе подтвердить:

- как выбирается живой `unitId`;
- где читается выбранный `UnitModel`;
- какая команда меняет позу;
- как UI узнаёт фактическое состояние после команды;
- как открывается authoritative profile/editor;
- кто хранит selection context;
- что reset/new run не оставляет старую UI-копию.

### Результат этапа

Handoff с полями:

```text
repository
base_branch
base_commit
feature_branch
goal
allowed_changes
forbidden_changes
required_checks
```

### Критерий завершения

Ни одна точка подключения первого среза не основана только на старом аудите: каждая повторно подтверждена на exact base.

# Часть II. Первый рабочий вертикальный срез

## Этап 3. Контракт выбора юнита

### Цель

Сделать один источник выбранного юнита для карты и правой панели.

### Требования

- пользователь выбирает настоящего бойца на карте;
- выбранное значение — существующий product `unitId`;
- новая оболочка не создаёт второй глобальный `selectedUnit` со своей доменной жизнью;
- смена selection обновляет все подключённые представления;
- уничтоженный/удалённый/сброшенный unit корректно снимает или меняет selection;
- после reset/new run старый объект не остаётся выбранным скрыто.

### Не делать

- универсальный resolver всех будущих сущностей;
- локальный реестр копий юнитов;
- преобразование selection через текстовые имена.

### Проверка

```text
выбрать A → справа A
выбрать B → справа B
reset/new run → старый A/B не остаётся источником данных
```

### Критерий готовности

Map и Unit inspector гарантированно говорят об одном product `unitId`.

## Этап 4. Правый `Юнит` — только LIVE-чтение

### Цель

Создать первую настоящую вкладку принятого Right Panel v1.

### Сначала составить read-contract

Для каждого отображаемого поля зафиксировать:

```text
UI field
→ product owner
→ read path
→ update/revision trigger
→ состояние при отсутствии данных
```

### Первая версия показывает только подтверждённые реальные данные

Приоритет:

- идентичность/роль выбранного бойца;
- текущее состояние и готовность;
- здоровье/раны в доступном реальном объёме;
- мораль;
- подавление;
- усталость;
- текущая поза;
- текущий приказ отдельно от текущего действия, если product model действительно даёт это разделение;
- оружие;
- боеприпасы;
- готовность оружия;
- ссылки на существующие authoritative profiles.

Если какое-то принятое поле Right Panel не имеет подтверждённого источника, оно не заполняется demo-значением.

### Критерий готовности

Все значения правой панели можно трассировать до настоящего product owner.

## Этап 5. Первое настоящее изменение — поза

### Цель

Доказать write-path нового Полигона.

### Сценарий

```text
выбрать бойца
→ увидеть текущую позу
→ выбрать допустимую новую позу
→ отправить штатную команду
→ дождаться результата product runtime
→ заново прочитать UnitModel
→ карта и правый инспектор показывают один фактический результат
```

### Разрешённый объём

Только позы, для которых на exact base подтверждён штатный product command.

### Запрещено

- менять поле `pose` напрямую ради мгновенного UI-эффекта;
- хранить optimistic domain state как окончательное состояние;
- считать команду успешной только потому, что кнопка нажалась;
- изменять одновременно стартовый definition бойца, если это отдельно не утверждено.

### Failure semantics

UI должен различать минимум:

- команда принята и состояние изменилось;
- команда недоступна/отклонена;
- выбранный unit больше не существует;
- runtime ещё не перешёл в ожидаемое состояние.

### Критерий готовности

Результат в UI определяется повторным чтением владельца, а не локальной записью интерфейса.

## Этап 6. Связанный профиль

### Цель

Проверить Interface Linkage v1 на самом простом реальном примере.

### Сценарий

```text
Unit inspector
→ клик по связанному профилю
→ существующий authoritative editor
→ профиль уже выбран
→ понятный возврат к исходному юниту/контексту
```

### Требования

- использовать существующий `GameEditorRegistry` и настоящих владельцев профилей;
- linked entity выглядит как переход, а не как отдельная копия параметров;
- не создавать внутри Полигона второй editor того же профиля;
- не строить пока универсальную навигацию на все будущие сущности, если для первого среза достаточно узкого typed contract.

### Критерий готовности первого вертикального среза

Одновременно проходят все условия:

- выбор карты и инспектора синхронен;
- инспектор читает реальный `UnitModel`;
- поза меняется штатной командой;
- результат читается обратно из runtime;
- профиль открывается у настоящего owner;
- reset/new run не оставляет скрытой копии состояния;
- нет demo/mock fallback;
- нет HISTORY-данных;
- нет изменения `real-wargame-preview`, `main` и deployment без отдельного разрешения.

### Цель

Показать субъективные знания бойца без подмены их объективной картиной мира.

### Первая версия

Подключать только реально подтверждённые runtime-типы.

# Часть V. HISTORY

## Этап 12. History provider

### Цель

Создать продуктовую основу для чтения прошлого.

### Контракт должен отвечать на вопрос

```text
что было истинным в момент T
и что конкретный субъект знал в момент T
```

Это две разные категории данных.

### Минимальная область

Историческое чтение должно покрывать необходимые для принятого UX данные:

- состояние юнита;
- положение/сцена;
- события;
- perception/attention в нужном объёме;
- subjective memory;
- weapon/ammo state, если показываются в историческом Unit inspector.

### Жёсткое правило

HISTORY не должен менять LIVE runtime.

LIVE может продолжаться, пока пользователь просматривает прошлое, если это соответствует текущему режиму запуска.

### Future leakage

На момент `viewTime=T` нельзя показывать знания, события или выводы, появившиеся позже T.

### Критерий готовности

Один и тот же selected historical time согласованно меняет карту, Journal и правую панель, не влияя на живую симуляцию.

---

## Этап 13. Глобальная timeline и LIVE/HISTORY

### Цель

После появления history provider реализовать принятую общую временную навигацию.

### Сценарий

```text
LIVE
→ выбрать событие или время
→ HISTORY(T)

```

### Критерий готовности

`viewTime` — часть общего UI-контекста просмотра, но не новый владелец истории.

# Часть VI. Metrics v18

## Этап 14. Telemetry contract

### Цель

До полноценного конструктора Metrics определить, какие реальные потоки данных продукт может измерять.

### Для каждого stream зафиксировать

```text
identity
schema
participants/entities
Program anchors
state constraints
collection period
storage policy
aggregation policy
versioning
```

### Правило

Definitions принадлежат Metrics. Series их использует, но не создаёт второй каталог метрик.

### Критерий готовности

Каждая настройка конструктора Metrics соответствует реальному telemetry stream или явно недоступна.

## Этап 15. UI Metrics

### Последовательность

- выбор потока;
- выбор участников;
- ограничения состояния;
- период сбора;
- привязка к Program anchors;
- сохранение measurement definition;
- отчёт по собранным данным;
- экспорт.

### Не делать

- demo/raw telemetry;
- фиктивные графики;
- независимые Series metrics.

### Критерий готовности

Одна сохранённая metric definition реально производит данные в запуске и может быть использована Series.

# Часть VII. Laboratory

## Этап 16. Descriptor/resolution layer

### Цель

Сделать Laboratory оболочкой над настоящими владельцами параметров.

### Каждый поддерживаемый параметр обязан иметь

```text
stable descriptor
owner
baseline read
experimental override write
scope/target
precedence
reset/clear
validation
optional persistent write — только если разрешён Apply Globally
```

### Начальная опора

Использовать уже работающий узкий accuracy override как пример продуктовой цепочки, но не считать его универсальным engine автоматически.

### Критерий готовности

Laboratory не хранит второй baseline catalog.

## Этап 17. UI Laboratory

### Принятый сценарий

```text
параметр
→ источник
→ baseline
→ experimental value

→ сбросить
```

`Apply Globally` показывается только для параметров, где утверждён настоящий постоянный writable owner.

### Критерий готовности

После удаления override effective value снова определяется authoritative baseline без ручной синхронизации UI.

# Часть VIII. Series

## Этап 18. SeriesRecord / RunRecord и persistence

### Цель

Отделить существующее вычислительное ядро batch-runner от полноценной продуктовой истории Серий.

### SeriesRecord должен хранить необходимый контекст

- идентичность серии;
- замороженное определение эксперимента;
- выбранные Metrics definitions;
- Laboratory overrides;
- runtime identity/version;
- список RunRecord;
- агрегаты отчёта;
- состояние завершения/остановки.

### RunRecord

Минимум:

- run ID;
- seed;
- result/status;
- metric values;
- runtime identity;
- ссылки на frozen inputs;
- данные, нужные выбранной replay-семантике.

### Критерий готовности

Пользователь может открыть завершённую Series и получить тот же список запусков, который был сохранён согласно принятой persistence-политике.

---

## Этап 19. Series UI

### Три состояния

1. setup;
2. execution;
3. report.

### Setup

- один замороженный эксперимент;
- количество прогонов;
- выбранные Metrics;
- понятная seed policy;
- без вынесения worker/package деталей в основной UX.

### Execution

- прогресс;
- stop/cancel;
- pause только если product runtime действительно поддерживает согласованную паузу Series;
- никакой синтетической генерации результатов.

### Report

- агрегаты;
- полный список всех запусков;
- фильтры;
- `Необычные` как объяснимый набор outliers;
- открытие конкретного RunRecord;
- переход к replay/rerun согласно принятой семантике;
- возврат в тот же Series report context.

### Критерий готовности

Series является оболочкой над настоящими batch runs и Metrics, а не отдельной статистической демонстрацией.

# Часть IX. Сохранение эксперимента

## Этап 20. Versioned experiment envelope

### Цель

Определить, что именно означает `Сохранить эксперимент`.

### Envelope должен согласованно включать

- сцену/карту;
- юнитов/участников и их стартовое состояние;
- Program;
- Laboratory overrides/configuration;
- Metrics definitions/settings;
- необходимые version/identity данные.

Map-only import/export остаётся отдельной явно названной функцией.

### Решение реализации

После проверки существующих контрактов выбрать одно:

- расширить `CombatLabExperimentV1`;
- оставить его вложенной частью и создать один новый versioned envelope над ним.

Выбор делается по совместимости и ответственности владельцев, а не ради совпадения с HTML-структурой.

### Критерий готовности

Round-trip:

```text
настроить эксперимент
→ сохранить
→ открыть заново
→ получить тот же смысл сцены + Program + Lab + Metrics
```

# Часть X. Полный Unit Editor

## Этап 21. Реализовать принятое решение по Unit Editor

Этот этап намеренно стоит после доказанного LIVE-среза.

### Если выбран authoring-only

Редактор меняет только стартовое состояние следующего запуска и явно показывает, что живой runtime не изменяется.

### Если выбран LIVE-only

Редактор использует только разрешённые runtime-команды и не меняет silently experiment definition.

### Если выбраны два режима

UI явно разделяет:

```text
До запуска
LIVE
```

Смена режима не должна быть скрытой.

### Критерий готовности

Пользователь всегда понимает, изменяет ли он будущий эксперимент или живого бойца.

# Часть XI. Интеграция и приёмка

## Этап 22. Единый linkage contract

После того как несколько реальных связей доказаны узкими контрактами, обобщить только повторяющуюся часть.

### Должны поддерживаться необходимые переходы

- Unit ↔ authoritative profile/editor;
- Program ↔ Journal;
- Journal ↔ entity;
- Journal/Program ↔ Metrics anchor, где применимо;
- Metrics ↔ Series;
- Series ↔ RunRecord;
- RunRecord ↔ replay/rerun;
- Laboratory parameter ↔ source;
- backlinks `Используется` для реально поддерживаемых reusable entities.

### Правило

Сначала несколько доказанных typed links, потом обобщение. Не создавать универсальный router заранее на основе prototype string IDs.

---

## Этап 23. Удаление временных и устаревших путей

Только после того, как соответствующая новая продуктовая функция принята.

Проверить и убрать либо изолировать:

- старые UI-пути, которые дублируют новый Полигон;
- диагностические панели из основного UX, если принято такое решение;
- временные adapters, ставшие ненужными;
- mock/demo fallback;
- prototype navigation glue;
- локальные копии domain state;
- независимые каталоги Metrics/Parameters, если новый authoritative путь их заменил.

Не удалять рабочий механизм только потому, что новый UI уже нарисован. Сначала доказать эквивалентность или замену пользовательского сценария.

## Этап 24. Сквозная приёмка

### Обязательные пользовательские сценарии

#### LIVE Unit

```text
карта → юнит → инспектор → команда → фактическое состояние → профиль
```

#### Info

```text
курсор → информация точки → pin → сохранение точки при движении курсора
```

#### Attention/Memory

```text
выбранный субъект → только его perception/knowledge → согласованная карта/панель
```

#### Program ↔ Journal

```text
шаг → породившееся событие → назад к шагу/сущности
```

#### HISTORY

```text
LIVE → T1 → историческая карта/юнит/память → другой T2 → LIVE
```

При этом LIVE runtime не меняется и future leakage отсутствует.

#### Metrics

```text
definition → реальный сбор → отчёт
```

#### Laboratory

```text
baseline → override → effective → clear → baseline
```

#### Series

```text
freeze experiment → N runs → all-runs report → outlier → replay/rerun → возврат в report
```

#### Save/Open

```text
scene + Program + Lab + Metrics → save → reload → same experiment meaning
```

### Техническая проверка каждой завершённой feature-задачи

Минимально по правилам репозитория:

```text
npx tsc --noEmit
релевантный focused smoke
npm run build
```

Документационные проверки запускаются, если менялась документация.

Browser/visual QA выполняется только через предусмотренный репозиторием screenshot/visual-QA маршрут.

### Финальный критерий переноса

Новый Полигон считается продуктовым, когда:

- все принятые функции либо реализованы, либо имеют явно принятое ограничение версии;
- для каждого domain value известен настоящий owner;
- нет второго UI-owned состояния игры;
- нет prototype runtime dependency;
- HISTORY не изменяет LIVE;
- subjective knowledge не получает данные из будущего;
- Metrics owns measurement definitions;
- Series потребляет эти definitions;
- Laboratory работает поверх product owners;
- Save/Open имеет согласованный round-trip;
- сквозные сценарии проходят на реальном продукте.

# Часть XII. Параллельная работа исполнителей

## Что можно делать параллельно после фиксации exact base

Параллельные исследовательские/контрактные дорожки:

- Unit read-contract;
- Unit write-contract;
- map `Инфо` read API audit;
- Attention/Memory coverage audit;
- Program/Journal causal identity;
- Metrics telemetry contract;
- Laboratory descriptor/resolution contract;
- Series persistence/replay contract;
- сквозная acceptance matrix.

Эти работы не должны одновременно менять один и тот же product owner без координации.

## Что нельзя запускать раньше foundation

Не начинать UI-реализацию:

- HISTORY до history provider;
- полного Journal v4 до причинных event IDs и history strategy;
- Metrics v18 до telemetry contract;
- полного Laboratory до descriptor/resolution layer;
- полной Series history/replay до SeriesRecord/RunRecord и replay policy;
- full Save/Open до определения envelope;
- полного Unit Editor до решения authoring/LIVE.

## Рекомендуемый порядок product-code исполнителей

↓

Нужно отдельное явное разрешение на deployment.
