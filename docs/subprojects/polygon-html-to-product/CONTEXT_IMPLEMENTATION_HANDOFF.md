## 1. Зачем была нужна эта работа

В продукте правая кнопка мыши уже занята боевым управлением. До этой работы существовали как минимум два связанных пути:

- `TacticalOrderRadialInput` — короткий приказ движения, удержание правой кнопки и радиальные тактические приказы;
- `BoardInputController` — существующий путь правого клика/перетаскивания, включая направление движения;
- `MapInputOwnership` — арбитраж владельцев ввода.

При этом новый Полигон по принятому UX должен уметь вызывать единое меню прямо по сущности на карте: бойцу или объекту карты.

Главная сложность состояла в том, что нельзя было просто повесить ещё один `contextmenu` listener и забрать правую кнопку. Это сломало бы существующий quick move, right-drag и radial orders.

Поэтому КОНТЕКСТ встроен в уже существующую модель жеста и не создаёт второй механизм команд.

## 2. Итоговый контракт правой кнопки

После этой реализации право на действие определяется одновременно по:

1. цели под курсором;
2. длительности жеста;
3. факту перетаскивания;
4. текущему режиму приложения;
5. наличию выбранных боевых юнитов.

### Таблица арбитража

| Цель / режим | Жест | Владелец | Результат |
|---|---|---|---|
| настоящий `unit` или `map-object` | короткий RMB без drag | КОНТЕКСТ внутри существующего `tactical-orders` lease | открыть entity context menu, **не выдавать move order** |
| настоящий `unit` или `map-object`, есть выбранные юниты | RMB drag от 4 px | существующий tactical flow | сохранить quick move/right-drag facing |
| настоящий `unit` или `map-object`, есть выбранные юниты | удержание до существующего hold threshold | существующий `TacticalOrderRadialInput` | открыть прежнее radial tactical order menu |
| сущность, выбор боевых юнитов отсутствует | короткий RMB | КОНТЕКСТ | открыть entity context menu |
| пустая земля, есть выбранные юниты | RMB | существующий tactical flow | прежние quick move/right-drag/radial orders |
| пустая земля, выбор отсутствует | RMB | существующий `BoardInputController` | прежнее поведение карты |
| editor mode | RMB | существующий editor/input owner | КОНТЕКСТ не вмешивается |
| AI Lab открыт | RMB | существующий AI Lab/input owner | КОНТЕКСТ не вмешивается |
| активен turn tool | RMB | существующий turn-tool path | КОНТЕКСТ не вмешивается |

Ключевое правило:

> короткий правый клик непосредственно по настоящей сущности открывает меню сущности и подавляет только тот pending tactical release, который иначе превратился бы в move в ту же точку. Hold и drag не отбираются у боевого управления.

## 3. Что именно реализовано

### 3.1. Общий descriptor цели

Добавлен presentation-only descriptor `EntityContextTarget`.

Поддерживаются два вида реальных целей:

- `unit`;
- `map-object`.

Descriptor содержит только то, что нужно меню для маршрутизации:

- тип цели;
- стабильный `id`;
- координату якоря на карте;
- отображаемое русское имя.

В descriptor **не копируется mutable gameplay state**. Отдельного store для контекстного меню нет.

### 3.2. Hit-test настоящих сущностей

Для бойца используется существующий product helper:

`findUnitAtGridPosition(...)`.

Для объектов карты используется существующая каноническая геометрия:

`isPointInsideMapObject(...)` и `getMapObjectCenter(...)`.

Отдельный renderer, spatial truth или параллельная модель объектов не создавались.

Hit-test выполняется только на дискретном `pointerdown` правой кнопки. Он не запускается на каждом `pointermove` и не добавлен в ticker.

### 3.3. Единое DOM-меню

Добавлен `EntityContextMenu`.

Меню:

- не использует browser-native context menu;
- открывается возле точки клика;
- ограничивается границами viewport;
- закрывается по `Escape`;
- закрывается по клику вне меню;
- поддерживает keyboard navigation стрелками между доступными действиями;
- умеет показывать disabled action, если authoritative owner перехода ещё не подключён;
- снимает listeners при destroy.

### 3.4. Порог drag

Для разведения короткого клика по сущности и боевого right-drag введён маленький presentation threshold:

`ENTITY_CONTEXT_DRAG_THRESHOLD_PX = 4`.

Он не меняет семантику приказа движения и не вводит новую систему направления. Его задача только ответить на вопрос: «это ещё короткий клик для entity menu или пользователь уже начал drag?»

После превышения порога КОНТЕКСТ больше не претендует на короткий entity click, а существующий tactical gesture продолжает работу.

## 4. Действия меню бойца

Для `unit` меню подготавливает следующие действия:

### `Выбрать`

Это уже реально подключённое действие.

Используется существующий штатный API:

`selectUnit(state, unitId)`.

Новый selection store не создавался.

### `Юнит`

Точка интеграции с ПУЛЬСОМ:

`pulse.right-panel.unit`.

Назначение: после выбора того же настоящего `unitId` открыть правую вкладку `Юнит`.

КОНТЕКСТ не реализует содержимое этой вкладки и не владеет `UnitModel`.

### `Внимание`

Точка интеграции с ЛИНЗОЙ:

`linza.right-panel.attention`.

КОНТЕКСТ только передаёт identity выбранного бойца. Расчёт attention state и его отображение остаются зоной ЛИНЗЫ/authoritative owner.

### `Память`

Точка интеграции с ЛИНЗОЙ:

`linza.right-panel.memory`.

КОНТЕКСТ не создаёт память бойца и не вычисляет её в UI.

### `Редактировать`

Точка интеграции с РЕДАКТОРАМИ:

`editors.open`.

После подключения owner этот пункт должен открывать существующий authoritative editor/open route, а не отдельный редактор внутри меню.

---

## 5. Действия меню объекта карты

Для `map-object` подготовлены:

### `Инфо`

Точка интеграции с ЛИНЗОЙ:

`linza.right-panel.info`.

Меню передаёт identity и anchor существующего объекта. Оно не вычисляет LOS, cover, perception или другие данные объекта само.

### `Редактировать`

Точка интеграции:

`editors.open`.

Действие должно использовать существующий editor-open path только там, где текущий режим и штатные write-boundaries разрешают редактирование.

В LIVE режиме меню не становится обходом редакторских ограничений.

## 6. Почему часть пунктов сейчас disabled

На базе, от которой стартовал КОНТЕКСТ, единый принятый callback/API для всех новых переходов ПУЛЬС/ЛИНЗА/РЕДАКТОРЫ ещё не был интегрирован в этот input installer.

Поэтому выбран безопасный контракт через внедряемые callbacks:

- `selectUnit`;
- `openPanel(target, view)`;
- `openEditor(target)`.

`selectUnit` имеет штатный fallback к существующему API продукта.

`openPanel` и `openEditor` **не имеют fake fallback**. Пока соседний owner не передал реальный callback, соответствующая кнопка отображается недоступной.

Это сознательная архитектурная граница: лучше показать «переход пока не подключён», чем создать второй механизм навигации или начать искать случайные DOM-элементы по селекторам.

## 7. Точки интеграции с соседними исполнителями

### ПУЛЬС

ПУЛЬС остаётся владельцем:

- единой identity выбранного бойца;
- selection/right-panel seam;
- вкладки `Юнит` и её LIVE readback;
- штатных команд изменения состояния бойца.

КОНТЕКСТу от ПУЛЬСА нужен только стабильный вызов вида:

`openPanel(target, 'unit')`.

### ЛИНЗА

ЛИНЗА остаётся владельцем содержимого:

- `Инфо`;
- `Внимание`;
- `Память`.

КОНТЕКСТу нужен только navigation seam:

- `openPanel(target, 'info')`;
- `openPanel(target, 'attention')`;
- `openPanel(target, 'memory')`.

### РЕДАКТОРЫ

РЕДАКТОРЫ остаются владельцем authoritative editor-open API.

КОНТЕКСТу нужен только адаптер:

`openEditor(target)`.

После интеграции этот адаптер должен вести в существующий `GameEditorRegistry` / штатный editor route, где это допустимо для конкретной сущности.

## 8. Что КОНТЕКСТ намеренно НЕ делает

Эта реализация не создаёт заново:

- command runtime;
- tactical-order semantics;
- pathfinding;
- move order API;
- right-drag facing semantics;
- radial order semantics;
- attention commands;
- Info/Memory computation;
- selection store;
- map renderer;
- unit renderer;
- Unit Editor logic;
- новую сущность «точка карты» только ради меню.

КОНТЕКСТ — presentation/router слой вокруг существующих owners.

## 9. Изменённые product-файлы

### `src/input/EntityContextTarget.ts`

Отвечает за read-only resolution настоящей сущности под точкой карты и создание минимального descriptor.

### `src/input/EntityContextGesture.ts`

Содержит минимальную чистую логику различения короткого entity-click и drag.

### `src/ui/EntityContextMenu.ts`

DOM-представление меню и маршрутизация действий через callbacks владельцев.

### `src/entity-context-menu.css`

Компактное оформление меню в текущей тёмной визуальной системе tactical UI.

### `src/input/TacticalOrderRadialInput.ts`

Главная точка интеграции с существующим RMB flow:

- определяет entity target на pointer down;
- хранит только временного кандидата короткого клика;
- при drag отдаёт жест существующей боевой логике;
- при hold оставляет radial order;
- при коротком клике по entity подавляет quick move и открывает entity menu;
- освобождает существующий `MapInputOwnership` lease штатным teardown.

### `tests/entity-context-menu.spec.ts`

Подготовлен браузерный regression test контракта меню и арбитража правой кнопки.

## 10. Производительность

КОНТЕКСТ не добавляет постоянной нагрузки в игровой цикл.

Нет:

- нового ticker;
- polling;
- scan мира на каждом кадре;
- scan мира на каждом движении мыши;
- отдельного renderer pass.

Entity hit-test выполняется один раз при начале потенциального контекстного жеста.

Для map object сейчас выполняется обратный проход по `state.map.objects` на дискретном RMB `pointerdown`. Это не hot pointer-move path. Если в будущем количество объектов станет настолько большим, что и дискретный поиск станет заметным, resolver следует перевести на уже существующий spatial index, а не создавать собственный индекс КОНТЕКСТА.

## 14. Что должен сделать следующий интегратор

После принятия результатов ПУЛЬСА, ЛИНЗЫ и РЕДАКТОРОВ не нужно переписывать КОНТЕКСТ.

Нужно подключить реальные callbacks к уже подготовленному `EntityContextMenuRoutes`:

```text
selectUnit(unitId)
openPanel(target, 'unit' | 'info' | 'attention' | 'memory')
openEditor(target)
```

После подключения обязательно повторно проверить весь RMB contract:

1. entity + short RMB → entity menu, без move;
2. entity + no selection + short RMB → entity menu;
3. entity + selected units + right-drag → прежний move/facing;
4. entity + selected units + hold → прежнее radial menu;
5. empty ground + selection → прежний tactical flow;
6. empty ground + no selection → прежний BoardInput flow;
7. editor mode → КОНТЕКСТ не перехватывает управление;
8. AI Lab → КОНТЕКСТ не перехватывает управление;
9. turn tool → КОНТЕКСТ не перехватывает управление;
10. `Выбрать` меняет штатную selection identity;
11. `Юнит / Инфо / Внимание / Память` открывают соседний owner без копии данных;
12. `Редактировать` идёт через authoritative editor-open route;
13. `Escape`, outside click и teardown корректно закрывают меню;
14. меню корректно clamp-ится у всех краёв viewport.

## 15. Краткий итог

КОНТЕКСТ добавил единый механизм контекстного меню для настоящих сущностей карты, не ломая существующее управление правой кнопкой.

Главный архитектурный результат:

```text
entity short RMB
→ EntityContextMenu
→ existing owner navigation

entity drag / hold
→ existing TacticalOrderRadialInput
→ existing command runtime

empty ground RMB
→ existing tactical / BoardInput flow
```

Никакого второго command runtime, selection store или вычислительного владельца данных меню не появилось.

Следующая точка интеграции:

`РЕДАКТОРЫ + КОНТЕКСТ + ПУЛЬС/ЛИНЗА navigation`.
