# Перенос Полигона из HTML-прототипа в продукт

## Цель

Перенести принятый пользовательский интерфейс режима «Полигон» из HTML-прототипа в штатную реализацию Real Wargame.

При переносе нужно сохранить:

- видимое поведение интерфейса;
- пользовательские сценарии;
- связи между разделами;
- смысл действий пользователя;
- принятые правила интерфейса.

Внутренняя реализация должна использовать существующую архитектуру продукта и настоящих владельцев данных. Продуктовая реализация в этом подпроекте ещё не начата.

## Текущее состояние

`polygon-prototype` уже содержит принятые контракты v44 infantry-integrated, Metrics v18, Series v1, Journal v4, Right Panel v1 и Interface Linkage v1. Переданный HTML объединяет принятую связность с правой панелью, Вниманием/Памятью и существующими разделами Полигона.

Новый подпроект создан для следующей, отдельной работы: сопоставить этот пользовательский контракт с штатными владельцами данных и точками интеграции Real Wargame. Карта соответствий, продуктовые изменения и проверки поведения ещё не выполнены.

## Основные этапы переноса

1. Инвентаризировать пользовательский контракт HTML: разделы, состояния, переходы и сквозные связи.
2. Составить карту соответствий «UI → штатный владелец данных → существующий код/документ».
3. Разобрать границы и конфликты с `polygon-prototype`, боевой симуляцией и связанными подпроектами.
4. Переносить интерфейс вертикальными срезами через настоящие владельцы данных.
5. Проверить сценарии, связи разделов, исторические состояния и ограничения субъективных данных.
6. Провести приёмку и только после отдельного разрешения координировать перенос результата в `real-wargame-preview`.

Этапы не считаются выполненными только потому, что соответствующий экран есть в HTML.

## Зависимости

- `docs/subprojects/polygon-prototype/` — принятый UX-контракт и его история;
- владельцы данных карты, юнитов, Программы, Лаборатории и Метрик;
- будущие штатные владельцы Серии, Журнала, Внимания, Памяти и сквозной связности;
- архитектурные правила Real Wargame: симуляция владеет состоянием, UI только отображает и отправляет действия;
- правила генерации документации `docs:sync` и проектный рабочий процесс веток.

## Риски и открытые вопросы

- Синтетические прогоны, demo events и mock-данные HTML не доказывают наличие production telemetry, хранения результатов или воспроизводимого runtime.
- Временные `window`/global API и локальное состояние HTML нельзя переносить как архитектуру.
- Нужно определить границу между переносом интерфейса Полигона и работами по production perception/memory.
- Следы старых вариантов интерфейса не должны вернуть исключённые из принятого контракта вкладки или параллельных владельцев данных.
- Необходимо заранее установить, где хранятся исторические знания бойца и как защищается граница `viewTime` без утечки будущих данных.
- До продуктовых изменений не определены все штатные владельцы Series/Journal и production-слой сквозных ссылок.

## Ближайший следующий шаг

После отдельного разрешения пользователя на первого Q-исполнителя подготовить матрицу:

`UI-контракт → штатный владелец данных → существующий код/документ → пробел или риск`.

Это исследовательско-проектировочный шаг. Он не должен менять продуктовый код и не должен копировать внутреннюю архитектуру HTML.

## Правила подпроекта

- Не начинать продуктовую реализацию в рамках подготовки.
- Не считать HTML источником истины симуляции.
- Не вводить новые mock-владельцы данных.
- Не менять `main` или `real-wargame-preview` без отдельного разрешения.
- Не выполнять деплой.
