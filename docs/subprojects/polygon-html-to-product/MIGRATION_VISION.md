# Видение переноса HTML-прототипа Полигона в продукт

## Общая идея

Новый Полигон не следует делать ни как полную переделку существующего продуктового Полигона, ни как полностью независимую систему с нуля.

Основной подход:

> Создать новый пользовательский интерфейс Полигона, ориентируясь на принятый HTML-прототип, но подключить его к уже существующим системам Real Wargame.

Принятый `Interface Linkage v1` рассматривается как эталон того, **как Полигон должен выглядеть, как пользователь должен с ним работать и как разделы должны быть связаны между собой**.

При этом внутреннее устройство автономного HTML не является продуктовой архитектурой и не должно переноситься буквально.

HTML отвечает на вопрос:

> Как должен работать Полигон с точки зрения пользователя?

Существующий код Real Wargame отвечает на другой вопрос:

> Какая игровая система действительно владеет этими данными и выполняет это действие?

Новый Полигон должен соединить эти две стороны.

---

## Что создаётся заново

Заново создаётся прежде всего верхний пользовательский слой Полигона:

- общая компоновка;
- шапка;
- левая рабочая панель;
- правая панель;
- вкладки;
- переходы между разделами;
- общий механизм выбора сущностей;
- контекстные меню;
- всплывающие редакторы;
- работа интерфейса с центральной картой;
- историческая навигация;
- взаимодействие между Программой, Метриками, Журналом, Лабораторией, Серией и инспекторами;
- состояния интерфейса.

Старый интерфейс не является фундаментом, который нужно постепенно переделывать до состояния прототипа.

**Новая оболочка строится чисто, внутри существующей архитектуры Real Wargame.**

Это позволяет не наследовать накопившиеся ограничения и временные решения старого интерфейса.

---

## Что не создаётся заново

Не нужно параллельно создавать вторую игру внутри Полигона.

Нужно максимально использовать существующие системы Real Wargame:

- симуляцию;
- юнитов;
- карту и игровой мир;
- состояние бойцов;
- оружие;
- игровые профили;
- восприятие;
- внимание;
- память;
- маршруты;
- программу поведения эксперимента;
- существующие реестры настроек;
- команды управления;
- существующие средства запуска эксперимента;
- имеющиеся структуры событий, измерений и результатов.

То есть целевая схема выглядит так:

```text
новый интерфейс
        │
        ▼
тонкий слой связи / адаптеров / команд
        │
        ▼
существующие системы Real Wargame
```

а не так:

```text
новый интерфейс
+
новая модель бойца
+
новая память
+
новое оружие
+
новая программа
+
новая симуляция
```

---

## Главный принцип: один объект — один настоящий владелец

У каждой сущности в игре должен оставаться один источник истины.

Если оружие уже существует в игровом каталоге, Полигон не должен создавать собственную копию каталога оружия.

Если состояние бойца принадлежит симуляции, правая панель должна его читать, а не поддерживать собственное параллельное состояние бойца.

Если профиль внимания принадлежит игровой системе внимания, редактор Полигона должен работать через неё, а не рассчитывать отдельную модель внимания.

Если Программа определяет действия участников эксперимента, Журнал должен ссылаться на те же действия и идентификаторы, а не создавать второе независимое представление происходящего.

Интерфейс может хранить только собственное UI-состояние: раскрытые панели, активную вкладку, фильтр, положение окна и подобные вещи. Игровая истина остаётся у продуктовых владельцев данных.

---

## Роль принятого HTML

HTML остаётся **эталоном пользовательского поведения и связности интерфейса**.

По нему определяются:

- состав разделов;
- расположение и назначение элементов;
- связи между вкладками;
- пользовательские сценарии;
- переходы;
- контекстные действия;
- содержание карточек;
- состояния элементов;
- взаимодействие карты с панелями;
- информация, которая должна быть доступна пользователю.

Но демонстрационные данные, `window`-глобалы, `localStorage`, mock-объекты, synthetic RNG и внутренние расчёты standalone HTML автоматически не становятся частью продукта.

Для каждого элемента действует правило:

```text
Интерфейсу нужна информация или действие X
                 │
                 ▼
        Есть ли X уже в продукте?
           │               │
          да              нет
           │               │
           ▼               ▼
    подключить         добавить нормальный
    существующую       продуктовый механизм
    систему            у правильного владельца
```

Нельзя закрывать отсутствующую продуктовую возможность временной логикой внутри нового интерфейса и затем оставлять её как второй источник истины.

---

## Что делать с существующим продуктовым Полигоном

Существующий Полигон не нужно сразу удалять.

На время переноса он выполняет три роли.

### 1. Источник работающих механизмов

Из него нужно повторно использовать существующие службы, команды, модели данных, работу с картой, запуск симуляции, выбор объектов и другие уже рабочие продуктовые части.

### 2. Контрольная версия

Он позволяет проверять, что при переходе на новую оболочку не потеряна уже работающая возможность.

### 3. Временный запасной интерфейс

Новый Полигон можно вводить частями, постепенно вытесняя старую оболочку.

При этом старый интерфейс **не становится архитектурной основой нового**.

Также не следует создавать огромную копию продуктового Полигона в отдельной параллельной директории. Рабочая feature-ветка уже обеспечивает безопасную изоляцию изменений, а копирование всей реализации создаст две расходящиеся версии продукта.

---

## Переносить не вкладками, а законченными связями

Не стоит сначала переносить внешний вид всех вкладок, а подключение настоящих данных откладывать на потом.

Так легко получить второй автономный HTML уже внутри приложения.

Предпочтительный способ — вертикальные законченные участки.

Например:

```text
выбор бойца на карте
        ↓
редактор юнита
        ↓
настоящая продуктовая модель юнита
        ↓
правый инспектор «Юнит»
        ↓
изменение состояния через штатные команды
        ↓
обновление настоящего эксперимента
```

После завершения такого участка вся цепочка уже работает на настоящем продукте.

---

## Предлагаемый порядок переноса

### Этап 1. Новая оболочка, карта и общая навигация

Создаётся новый каркас:

```text
Шапка

Левая панель      Карта      Правая панель

Общие окна / редакторы

Глобальная временная навигация
```

Карта и игровое состояние при этом остаются продуктовыми.

Одновременно вводится общий механизм связанных выборов и переходов: выбранный юнит, объект карты, узел Программы, событие Журнала, измерение, прогон Серии и текущий момент просмотра.

### Этап 2. Редактор юнита + правый инспектор

Первый полностью рабочий вертикальный участок:

```text
Карта
↕
Выбор юнита
↕
Редактор юнита
↕
Правая вкладка «Юнит»
↕
Настоящий игровой юнит
```

Он должен доказать основной принцип архитектуры на реальном состоянии продукта.

### Этап 3. Редактор карты

Новый интерфейс подключается к настоящей модели пространства и экспериментального состояния. Собственная параллельная карта внутри Полигона не создаётся.

### Этап 4. Программа

Программа становится одной из центральных систем нового Полигона. Её узлы и шаги должны иметь устойчивую идентичность, которой смогут пользоваться Журнал, Метрики, Серия и карта.

```text
Программа
   │
   ├── Метрики
   ├── Журнал
   ├── Серия
   └── карта
```

### Этап 5. Метрики

Интерфейс определяет, что, для кого и когда измерять, а затем представляет собранную телеметрию в виде отчёта.

Если необходимые данные уже существуют — они подключаются.

Если нужной телеметрии нет — механизм добавляется на продуктовой стороне, а не имитируется внутри UI.

### Этап 6. Журнал и история

Журнал должен связывать событие, момент времени и состояние мира в этот момент.

```text
событие
↓
момент времени
↓
историческое состояние мира
↓
состояние выбранного бойца в этот момент
```

Если универсального механизма исторического состояния или replay пока нет, это отдельный продуктовый пробел, который необходимо решить на правильном архитектурном уровне.

### Этап 7. Лаборатория и общие редакторы

Лаборатория задаёт экспериментальные переопределения параметров, но не создаёт второй каталог параметров.

```text
параметр X
+
временное значение Y
+
цель / область Z
```

Сам параметр X и его базовое значение должны приходить от настоящего владельца в Real Wargame.

### Этап 8. Внимание и Память

Эти разделы должны отображать субъективные данные бойца, подготовленные симуляцией.

```text
симуляция
↓
perception / attention / memory
↓
интерфейс
↓
отрисовка
```

Интерфейс не должен самостоятельно решать, что боец видит, знает или помнит.

### Этап 9. Серия

Серия требует уже не только UI, но и настоящей продуктовой инфраструктуры массовых независимых прогонов:

```text
замороженное определение эксперимента
↓
много прогонов с отдельными seed
↓
сохранение результатов
↓
агрегация Метрик
↓
поиск интересных прогонов
↓
выбор прогона
↓
точное воспроизведение
```

Если фонового runner, хранилища результатов или детерминированного replay пока нет, эти части должны появиться как продуктовые механизмы.

---

## Целевая архитектурная картина

В результате должен существовать не «HTML-прототип, встроенный в игру», а штатный продуктовый Полигон:

```text
                 ПОЛИГОН
                    │
          пользовательский интерфейс
                    │
        ┌───────────┴───────────┐
        │                       │
   чтение состояния        команды изменения
        │                       │
        └───────────┬───────────┘
                    │
          адаптеры / product API
                    │
 ┌──────────────────┼───────────────────┐
 │                  │                   │
 ▼                  ▼                   ▼
Simulation       Registries          Experiment
 │                  │                   │
Units            Weapons            Program
Map              Profiles           Metrics
Attention        Surfaces           Journal
Perception       Terrain            Series
Memory           etc.               Laboratory
```

Полигон становится единым инструментом наблюдения, редактирования, проведения экспериментов и анализа, но не отдельной альтернативной игрой со своей копией игровых данных.

---

## Основное правило переноса

Перед переносом каждой части нужно ответить на четыре вопроса:

1. Что пользователь делает или видит здесь в принятом прототипе?
2. Какая система Real Wargame должна владеть этими данными или действием?
3. Есть ли эта система уже сейчас и где находится её штатная точка интеграции?
4. Если её нет — что именно нужно добавить в продукт, не создавая временную копию внутри интерфейса?

Рабочим основанием реализации должна стать матрица:

```text
Элемент / действие прототипа
→ требуемые данные
→ штатный владелец данных
→ существующий код
→ текущая реализация в продуктовом Полигоне
→ пробел / расхождение / риск
→ рекомендуемый способ подключения
```

---

## Краткая формула проекта

**Мы не переносим HTML в продукт как код. Мы переносим из него принятый замысел и пользовательский контракт Полигона.**

**Мы не переписываем Real Wargame ради нового интерфейса. Мы подключаем новый интерфейс к существующей игре.**

**Мы не строим новый Полигон поверх старой оболочки. Мы строим новую оболочку поверх существующего продуктового ядра.**

**Старый Полигон постепенно становится ненужным по мере того, как его реальные функции переходят под новую оболочку.**
