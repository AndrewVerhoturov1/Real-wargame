Статус документа: исследовательский аудит, без реализации.

Версия прототипа из `<meta name="prototype-version">`: `polygon-map-editor-unified-v44-infantry-integrated-20260815-memory-v3-interface-linkage-v1`.

## 1. Что именно проверялось

Цель аудита — отделить три разных вещи:

1. что принятый HTML обещает пользователю как работающую возможность;
2. какая продуктовая основа для этого уже реально существует в Real Wargame;
3. чего ещё не хватает, чтобы новый интерфейс не стал второй автономной системой поверх продукта.

HTML рассматривается только как принятый контракт пользовательского поведения. Его `window`-глобалы, `localStorage`, демонстрационные снимки, синтетические события, собственные генераторы случайных результатов и внутренние расчёты не считаются доказательством продуктовой готовности.

Статусы в таблице означают:

- **готово** — нужная продуктовая возможность уже существует в достаточном для этого пункта виде;
- **частично** — существенная рабочая основа есть, но контракт HTML шире;
- **отсутствует** — обязательный для контракта механизм прямо выделен в принятых документах как отдельная будущая продуктовая задача либо его отсутствие следует из проверенного продуктового контракта;
- **только демонстрация** — поведение есть в HTML, но оно создаётся демонстрационной логикой и не подтверждает продуктовый механизм;
- **не установлено** — по проверенным источникам нельзя надёжно сделать вывод.

При поиске продуктовых файлов поиск по репозиторию использовался только для нахождения кандидатов. Выводы по коду проверялись на точной рабочей базе `6d0f567f72c89d0f0c0401bf790b5122a9eb0ad3`.

## 2. Краткий вывод

Продуктовая основа Полигона заметно сильнее автономного HTML в нескольких важных местах: уже есть настоящее состояние симуляции, реальное Внимание и восприятие, субъективная память бойца, сериализация сцены и runtime, определение эксперимента Combat Lab, headless-прогон с фиксированным шагом, seed, digest результатов и рабочая серия прогонов через workers.

Главный риск переноса находится не в отсутствии всех механизмов, а в **разрывах между ними**. Принятый Interface Linkage v1 предполагает единый эксперимент, единое время просмотра, единые идентификаторы и согласованное состояние между Программой, Метриками, Журналом, Лабораторией, Серией, картой и инспекторами. Именно этот сквозной контракт пока не готов целиком.

Самые тяжёлые пробелы: универсальное историческое состояние `viewTime`, полноценный replay, связь динамических Метрик с реальной телеметрией и Серией, общий механизм лабораторных переопределений у настоящих владельцев параметров и полная воспроизводимость с идентичностью версии runtime.

Но в нём не зафиксировано полное состояние executor-а Программы/шагов как отдельный checkpoint-контракт; поэтому точное продолжение произвольной остановленной точки не доказано. | Снимок executor/program runtime; owner tokens; timers/retries; runtime identity; тест равенства после restore. | **высокий**, если UI обещает «сохранить бой и продолжить с той же инструкции». | Провести отдельный checkpoint/resume тест на активных шагах, ожиданиях, reload/deploy/transfer и субъективной памяти. До него статус точного resume не повышать. |
| **Согласованность experiment draft между частями текущего Combat Lab** | **готово** в текущем workspace | В продукте есть общий workspace draft service с `get/replace/announce/subscribe`, общий selection controller и один `CombatLabExperimentDraft`. Это уже предотвращает часть локальных копий состояния между существующими панелями. | Один экземпляр workspace services и один experiment draft. | **низкий** | Новый интерфейс должен подключаться к этому принципу общей службы/одного draft, а не иметь отдельный state каждой вкладки. |
| **Сквозная согласованность нового Полигона: Программа ↔ Метрики ↔ Журнал ↔ Лаборатория ↔ Серия ↔ карта ↔ инспекторы** | **частично** | Interface Linkage v1 определяет требуемое поведение, но `STATUS.md` подпроекта прямо говорит, что продуктовый перенос ещё не начат. Текущий workspace уже имеет общие experiment/selection механизмы, но принятые Metrics v18, Journal/history, Laboratory v1 и Series persistence/replay не объединены одним полным продуктовым контрактом. | Стабильные ID; единый experiment envelope; общий selection/linkage state; `viewTime`; telemetry; run identity. | **критический** при переносе «по вкладкам» | До массовой раздачи UI-задач утвердить минимальный общий linkage state: selected entity, selected program step/event/measurement/run, current experiment identity и `viewTime`, при этом сами игровые данные остаются у своих владельцев. |
| **Каноническое долговременное хранилище экспериментов/серий/результатов** | **отсутствует** как общий контракт | Combat Lab умеет browser-local сохранение до 10 недавних экспериментов и файловый импорт/экспорт. Interface Linkage отдельно говорит, что standalone/локальное хранение не доказывает canonical backend storage; Series требует отдельное хранение серий и прогонов. Единого долговременного хранилища всего Полигона в принятых контрактах нет. | Решение по scope продукта: browser-local, файлы, IndexedDB, сервер/облако или сочетание; versioning и миграции. | **средний** для первого локального среза, **высокий** для обещания истории Серий между сессиями. | Зафиксировать уровень гарантии хранения для первой версии. Не строить UI истории Серий до этого решения. |

## 4. Скрытые предположения HTML-прототипа

### 4.1. `viewTime` выглядит как простое число, но на самом деле это системная возможность

В HTML `viewTime` используется как общий ключ для карты, выбранного бойца, инспектора и Памяти. Пользователь поэтому естественно ожидает, что переход в прошлое изменит **все** связанные представления согласованно.

Для продукта это означает не «добавить ползунок», а иметь способ получить согласованный снимок мира и субъективного знания на момент `T`.

### 4.2. Кнопка replay предполагает больше, чем seed

HTML Серии пишет, что откроется сохранённый снимок эксперимента и будет использован seed. Однако сам standalone-режим replay фактически подготавливает демонстрационное состояние, а результаты Серии генерируются собственным детерминированным синтетическим генератором.

В продукте seed уже настоящий, но точный исторический replay требует ещё frozen definition и runtime identity. Поэтому перенос текста/кнопки раньше контракта replay создаст ложное обещание.

### 4.3. Серия предполагает, что каждый прогон — полноценная сохраняемая сущность

HTML позволяет фильтровать все прогоны, видеть seed любого прогона, разбирать выброс и нажимать replay. Текущий продуктовый batch engine считает все прогоны, но итоговый контракт сохраняет агрегаты и representative runs, а не полный постоянный каталог всех `RunRecord`.

### 4.4. Metrics v18 предполагает существование универсальной структурированной телеметрии

HTML показывает большой каталог измерений, временные интервалы, связи с событиями, пространственные данные и raw export. Часть этого прямо помечена как демонстрационный dataset. Реальный Combat Lab пока имеет более узкий фиксированный набор итоговых метрик.

### 4.5. Лаборатория предполагает, что любой показываемый параметр имеет настоящего владельца

Для параметров точности такая продуктовая цепочка уже существует. Для полного набора Laboratory v1 это ещё не доказано. Особенно опасно действие `Apply Globally`: без установленного authoritative owner оно либо станет фиктивным, либо начнёт писать в параллельный UI-каталог.

### 4.6. Save/Open предполагает один общий сериализуемый эксперимент

HTML экспортирует карту, юнитов, Программу, Лабораторию и Метрики одним объектом. В продукте уже есть хорошая основа `CombatLabExperimentV1`, но она пока не охватывает весь принятый контракт нового Полигона.

### 4.7. Связность вкладок предполагает общие устойчивые ID

Переходы «шаг Программы → событие Журнала → метрика → прогон Серии → бой на карте» работают безопасно только если это одни и те же идентификаторы, а не похожие записи, созданные каждой вкладкой отдельно.

## 5. Что можно реализовать независимо уже сейчас

Без решения самых тяжёлых runtime-пробелов можно делать вертикальные участки, которые работают только с текущим `LIVE`-состоянием:

- новая оболочка и навигация, если они хранят только UI-state;
- выбор реального юнита на карте и общий selection state;
- правый инспектор **Юнит** на текущем `SimulationState`;
- LIVE-вкладка **Внимание** на существующей продуктовой модели;
- первый LIVE-вариант **Памяти** только для реально существующих perception/tactical knowledge;
- редактор карты через текущую модель карты;
- Программа на существующем `CombatLabExperimentV1`/tracks;
- запуск одиночного эксперимента и существующего headless batch-runner;
- текущие подтверждённые Combat Lab metrics;
- импорт/экспорт существующего Combat Lab experiment как промежуточная продуктовая возможность.

Общее условие: ни один из этих участков не должен создавать собственную копию игровых данных внутри новой оболочки.

## 6. Что требует сначала отдельного продуктового решения

До полноценного UI соответствующей возможности сначала нужны решения по следующим контрактам:

1. **History provider / `viewTime`.** Как получить мир и субъективные данные на произвольный момент.
2. **Replay contract.** Это повторный детерминированный расчёт или воспроизведение записанной истории; как фиксируется runtime identity.
3. **Telemetry contract Metrics v18.** Какие raw streams существуют, как определение измерения подписывается на них и как результаты связываются с Серией.
4. **Laboratory descriptor/resolution contract.** Какие параметры доступны, кто ими владеет, как действуют target/area overrides и `Apply Globally`.
5. **Persistent Series/Run storage.** Какие записи сохраняются и как после перезапуска продукта открыть старую серию и выбранный run.
6. **Final experiment envelope.** Как одним versioned форматом сохраняются scene + Program + Laboratory + Metrics и другие настройки нового Полигона.

## 7. Пять наиболее опасных пробелов

### 1. Нет универсального исторического состояния `viewTime`

Это самый опасный пробел, потому что он затрагивает одновременно карту, Journal, Unit inspector, Attention и Memory. Если начать эти HISTORY-части раньше, почти неизбежно появится второй, интерфейсный источник прошлого.

### 2. Нет полного контракта воспроизводимости старого прогона

Seed, fixed step и digests уже есть, но нет обязательной identity/version runtime. После изменения симуляции старый seed может дать другой результат, хотя UI продолжит обещать «тот же прогон».

### 3. Metrics v18 шире существующей продуктовой телеметрии

Существующие боевые метрики реальны, но динамический конструктор Metrics v18 и его raw streams не подключены к общей продуктовой телеметрии. Если Серия начнёт жить на своём фиксированном каталоге, будет нарушено принятое правило «Metrics owns definitions».

### 4. Laboratory v1 пока не имеет общего продуктового механизма параметров

Узкая цепочка accuracy overrides уже хорошая, но перенос всей Лаборатории раньше descriptor/resolution contract создаст второй каталог параметров и особенно опасную фиктивную семантику `Apply Globally`.

### 5. Нет полного постоянного `SeriesRecord`/`RunRecord` для всех прогонов

Batch execution уже работает, но принятый UX Серии требует историю серий, любой run, его seed, контекст, метрики и replay. Агрегатов и representative runs для этого недостаточно.

## 8. Что блокирует первый вертикальный срез

Если следовать `MIGRATION_VISION.md`, первый вертикальный срез — это примерно:

`карта → выбор юнита → редактор/инспектор Юнит → настоящий UnitModel/SimulationState → штатное изменение → обновление всех связанных LIVE-представлений`.

**History, replay, Metrics v18, Laboratory v1 и Series persistence этот срез не блокируют.**

Перед началом кода для первого среза нужно только зафиксировать три вещи:

1. новый интерфейс использует существующий product `SimulationState` и общий workspace/selection mechanism, а не собственный массив юнитов;
2. изменения юнита идут через штатные продуктовые команды/владельцев, а не прямую запись в состояние UI;
3. первый срез работает только в `LIVE`; HISTORY явно не имитируется до появления history provider.

По проверенной базе существенная техническая основа для такого среза уже есть.

## 9. Что можно отложить

Без ущерба для первого вертикального среза можно отложить:

- произвольный `viewTime` и HISTORY;
- полноценный Journal v4;
- deterministic replay старых серий;
- постоянную историю Серий и всех RunRecord;
- паузу/восстановление длинной Серии после закрытия страницы;
- полный Metrics v18 и пространственную аналитику;
- полный Laboratory v1 и `Apply Globally`;
- `intel/front`, если для них не будет подтверждён продуктовый владелец;
- каноническое серверное/облачное хранилище, если первая версия сознательно остаётся локальной;
- точное продолжение незавершённого прогона из произвольного checkpoint.

Откладывание этих пунктов допустимо только при честном ограничении UI: недоступная продуктовая возможность не должна изображаться рабочей демонстрационной логикой.

## 10. Вопросы, которые нужно решить до раздачи кодовых задач

1. **Что считается первым продуктовым форматом эксперимента нового Полигона?** Расширяем `CombatLabExperimentV1` или вводим один верхний versioned envelope над ним?
2. **Каков минимальный общий linkage state нового интерфейса?** Какие selected IDs и `viewTime` являются UI-state, а какие идентификаторы приходят от product owners?
3. **Какой replay нужен в первой версии?** Rerun из frozen inputs или настоящий просмотр записанной временной истории?
4. **Какая identity runtime сохраняется вместе с run/series?** Commit SHA, build ID, simulation schema/version, digest каталогов или комбинация?
5. **Какие данные одного run обязаны храниться постоянно?** Только seed + digests + metrics или ещё события/контрольные точки/raw telemetry?
6. **Должна ли первая Series хранить каждый RunRecord или только representatives?** Принятый UX требует доступ к любому прогону; это нужно согласовать с объёмом хранения.
7. **Как Metrics v18 становится источником списка метрик для Series?** Нельзя сохранять текущий фиксированный batch-каталог как второй независимый каталог UI.
8. **Какой минимальный набор telemetry streams гарантируется продуктом в первой версии Metrics?**
9. **Как строится history provider?** Полные snapshots, event sourcing, checkpoints + replay или гибрид?
10. **Как исторически сохраняются perception/memory?** Нельзя восстанавливать прошлое знание бойца из текущего знания и текущей карты.
11. **Каков общий Laboratory descriptor contract?** Какие owners должны уметь read baseline, write persistent value, apply temporary override и объяснять effective source?
12. **Для каких параметров разрешён `Apply Globally`?** Что делать с параметром без постоянного writable owner?
13. **Где хранится история экспериментов и Серий первой версии?** Browser-local, файл, IndexedDB или внешний storage; какие гарантии переживают новую сессию?
14. **Что именно должно восстанавливаться командой Open?** Только authoring definition или также состояние незавершённого runtime?
15. **Как проверяется согласованность Save→Open?** Нужен тест, что карта, units, Program, Lab, Metrics и стабильные IDs после round-trip совпадают по контракту.
16. **Какие возможности сознательно объявляем `LIVE-only` в первом этапе?** Это нужно решить заранее, чтобы исполнители не заполняли HISTORY моками.

## 11. Итог для планирования

Начинать перенос можно, но **не с полного набора вкладок**. Продукт уже имеет достаточную основу для первого LIVE-вертикального среза и для повторного использования значительной части Combat Lab. Самый безопасный порядок — сначала доказать общую работу на одном настоящем юните и одном общем experiment draft, затем переносить те разделы, чьи продуктовые владельцы уже установлены.

History/viewTime, полный replay, Metrics v18, общий Laboratory v1 и постоянная Series history должны идти только после отдельных продуктовых решений. Иначе новый интерфейс быстро повторит главный недостаток standalone HTML: начнёт выглядеть как единая работающая система раньше, чем единая система реально существует.
