# Промт V2: «Типы поверхностей» — приоритет решений прототипа

Ты работаешь над отдельной новой функцией **«Типы поверхностей»** режима «Полигон» в репозитории `AndrewVerhoturov1/Real-wargame`.

Сначала полностью прочти базовый промт:

`docs/subprojects/polygon-html-to-product/SURFACE_TYPES_EDITOR_CONCEPT_PROMPT_20260817.md`

Все его требования сохраняются, но настоящий файл задаёт **обязательный порядок приоритетов** и имеет преимущество при любом противоречии.

## Нормативный порядок приоритетов

1. **Явно принятые пользователем решения HTML-прототипа — главный источник продуктового поведения и состава функции.**
2. Новые явные решения пользователя могут уточнить или заменить отдельное решение прототипа.
3. Существующая архитектура продукта определяет, **как правильно реализовать** принятое поведение, но не имеет права молча заменить его старым поведением продукта.
4. Текущее поведение продукта используется как источник решения только там, где прототип и пользователь ничего не определили.

## Главное правило конфликта

Если прототип и текущий продукт расходятся, по умолчанию считается, что **доработать нужно продукт под принятое решение прототипа**, а не наоборот.

Нельзя писать:

> «В продукте уже сделано иначе, поэтому оставим как есть».

Нужно писать:

> «Прототип требует X. Продукт сейчас делает Y. Значит, для переноса требуется доработка Z».

## Архитектура не отменяет смысл прототипа

Нельзя буквально переносить технические костыли HTML-прототипа: DOM-состояние, временные глобальные объекты, его `localStorage`, поддельные данные и иные прототипные реализации.

Но нужно сохранить **принятое пользовательское и игровое решение**. Если прямой перенос невозможен, спроектируй продуктовый механизм, который даёт тот же смысл через настоящих владельцев данных и настоящий runtime.

Пример:

- прототип требует черновик + `Сохранить` + `Отменить`;
- существующий редактор продукта записывает каждое изменение автоматически;
- вывод: автосохранение продукта не объявляется нормой, а фиксируется как разрыв; целевое поведение должно соответствовать принятому прототипу.

## Если нужной механики вообще нет

Отсутствующая механика не отменяет решение прототипа.

Например, если у Surface Type есть `digging` и `digSpeed`, а полноценного окапывания в runtime ещё нет:

1. сохрани это как требование целевой модели;
2. честно зафиксируй `runtime gap`;
3. определи будущую точку подключения;
4. не создавай поддельный эффект;
5. вынеси недостающую механику в отдельную зависимую задачу.

## Что это означает конкретно для «Типов поверхностей»

Подтверждённые решения прототипа считаются целевыми, пока пользователь явно их не изменил:

- отдельная сущность/понятие **«Тип поверхности»** должна существовать в продукте;
- восемь подтверждённых типов являются исходным фиксированным каталогом;
- стабильный `id` типа не редактируется;
- есть разделы `Основное / Движение / Маскировка / Защита`;
- должны быть представлены все подтверждённые параметры движения, маскировки, шума, защиты и инженерных свойств;
- у числовых параметров есть индивидуальный возврат `↺` к нормативному значению;
- есть восстановление всего типа;
- редактирование идёт через черновик;
- есть явные `Сохранить` и `Отменить`;
- несохранённые изменения нельзя терять молча;
- сохранённые данные должны попадать настоящим потребителям игры, когда соответствующая механика существует;
- «Типы поверхностей» и «Профили местности» должны оставаться различимыми понятиями, как это заложено в прототипе. Исследование должно определить правильную архитектурную связь между ними, а не слить их только потому, что продукт сейчас устроен иначе.

## Как обсуждать варианты с пользователем

Архитектурные варианты нужны только для ответа на вопрос **«как лучше реализовать принятое решение прототипа?»**, а не для повторного голосования по уже принятым функциям.

Не предлагай пользователю отказаться от подтверждённой функции только потому, что текущий продукт её не поддерживает.

На согласование выноси действительно архитектурные или ещё не определённые вопросы: границы владельцев данных, модель связи с Environment Profiles, единицы и формулы там, где прототип задаёт лишь пользовательский смысл, обработку отсутствующего runtime, хранение, версии и применение изменений к открытому Полигону.

## Формат каждого найденного расхождения

Для каждого отличия используй структуру:

`Решение прототипа -> что есть в продукте сейчас -> какой разрыв -> что требуется доделать -> какие владельцы/файлы затрагиваются -> нужна ли отдельная зависимая задача`.
