# РЕДАКТОРЫ — отчёт о переносе существующих редакторов в новый Полигон

Дата: 2026-08-17  
REQUEST_ID: `XROUTE-20260817-POLYGON-EDITORS-NEW-DESIGN-001`

## 1. Итог в одном абзаце

В новый интерфейс Полигона подключена уже существующая продуктовая система редакторов. Новая отдельная система редакторов не создавалась: каталог, открытие конкретного редактора, жизненный цикл встроенных редакторов и существующие переходы продолжают опираться на `CombatLabGameEditors`, `GameEditorRegistry`, `GameEditorWorkspace` и существующий API открытия редакторов.

Для пользователя это означает, что кнопка **«РЕДАКТОРЫ»** нового Полигона теперь ведёт к настоящему каталогу существующих редакторов игры, а существующие поверхности **Редактора карты** и **Редактора юнита/параметров** показываются внутри нового shell вместо скрытой старой области.

Результат **не считается полностью принятым**, потому что на exact implementation SHA не была выполнена обязательная браузерная проверка со свежими скриншотами.

## 3. Что было до этой задачи

До задачи продукт уже имел единую систему общих редакторов:

- `CombatLabGameEditors`;
- `createDefaultGameEditorRegistry()` / `GameEditorRegistry`;
- `CombatLabGameEditorCatalogue`;
- `CombatLabGameEditorOverlay`;
- `GameEditorWorkspace`;
- общий запрос открытия связанного редактора через `COMBAT_LAB_OPEN_GAME_EDITOR_EVENT` / `requestCombatLabGameEditorOpen`.

Проблема была не в отсутствии редакторов, а в том, что принятый новый shell Полигона скрывал старые workspace-hosts. Верхняя кнопка **«РЕДАКТОРЫ»** была визуально присутствующей, но отключённой, а реальные панели `scene`, `parameters` и `settings` находились в скрытом контейнере.

Поэтому правильное решение этой задачи — не переписывать редакторы, а аккуратно встроить существующие владельцы и их состояния в новый дизайн.

## 4. Какие реальные редакторы сохранены

Источник истины остаётся `createDefaultGameEditorRegistry()`. В implementation commit smoke-контракт фиксирует текущий inventory, чтобы shell-интеграция случайно не потеряла зарегистрированные редакторы.

На момент реализации registry содержит:

1. Граф поведения (`behaviorGraph`)
2. Профили маршрута (`routeProfiles`)
3. Тактические позиции (`tacticalPositions`)
4. Данные бойца (`soldierData`)
5. Архетипы бойцов (`soldierArchetypes`)
6. Профили внимания (`attentionProfiles`)
7. Профили восприятия (`perceptionProfiles`)
8. Профили движения (`movementProfiles`)
9. Вооружение (`weapons`)
10. Ранения и подавление (`conditionProfiles`)
11. Профили местности (`environmentProfiles`)
12. Направленный рельеф (`directionalTerrain`)

В production-коде новый список этих редакторов не копировался. Каталог по-прежнему строится динамически через существующий registry.

## 5. Что именно реализовано

### 5.1. Верхняя кнопка «РЕДАКТОРЫ» стала рабочей

В принятом shell кнопка существовала, но была отключена через `aria-disabled`.

Новый `CombatLabEditorShellBridge`:

- активирует эту кнопку;
- открывает существующую workspace-вкладку `settings`;
- показывает текущий настоящий каталог `CombatLabGameEditorCatalogue`;
- отражает открытое состояние через `aria-pressed`;
- позволяет вернуться назад в предыдущую рабочую вкладку.

То есть нажатие не создаёт новый каталог и не открывает отдельную копию редакторской системы.

### 5.2. Каталог общих редакторов встроен в новый shell

Существующая панель `#combat-lab-workspace-panel-settings` переносится из скрытого контейнера в видимую рабочую область нового интерфейса.

Важно: переносится **тот же DOM-host**, который уже принадлежит старому workspace. Он не клонируется и не создаётся повторно.

Поэтому сохраняются:

- текущий registry;
- текущие объекты редакторов;
- существующий lifecycle;
- существующие события открытия/закрытия;
- состояние, которое уже принадлежит этим редакторам.

При закрытии/переключении панель возвращается в исходный host.

### 5.3. Сохранено штатное открытие embedded и route-редакторов

`CombatLabGameEditorCatalogue` и `CombatLabGameEditorOverlay` не заменялись.

Встроенные редакторы продолжают открываться через существующий `GameEditorWorkspace`. Редакторы, которым нужен отдельный route, продолжают использовать свой текущий маршрут.

Особенно важно для Графа поведения: shell integration не подменяет и не переопределяет его навигацию.

### 5.4. Исправлен возврат в каталог после отдельного route

Поддержан вход вида:

```text
/combat-lab.html?tab=settings
```

Раньше новый shell мог нормализовать `settings` в другую вкладку и пользователь возвращался не в каталог. Новый bridge распознаёт `?tab=settings` и запрашивает настоящую вкладку общих редакторов.

### 5.5. Реальная поверхность Редактора карты показана в новой левой панели

Workspace-вкладка `scene` уже содержит реальные существующие владельцы карты, включая существующий `CombatLabScenePanel` и связанный map-authoring path.

Новый bridge не создаёт второй Map Editor. Он переносит существующую панель `scene` в видимую левую часть нового shell, когда активна соответствующая вкладка.

Это сохраняет существующий map state и владельцев вместо создания декоративного редактора только под новый дизайн.

### 5.6. Реальная поверхность Редактора юнита/параметров показана в новой левой панели

Workspace-вкладка `parameters` уже содержит существующие parameter panels, quick-parameter links и ссылки на профильные редакторы.

Новый bridge аналогично показывает существующий `parameters` host в новом shell.

Отдельный новый `UnitModel`-редактор не создавался. Если продуктовая возможность полного Unit Editor отсутствует или принадлежит другой задаче, эта задача её не имитирует.

### 5.7. Добавлено оформление под новый Полигон

Создан отдельный presentation-слой:

`src/combat-lab/game-editors/combat-lab-game-editor-shell.css`

Он приводит рабочую область редакторов к визуальному языку принятого Polygon shell и содержит desktop/narrow правила.

CSS меняет presentation, но не доменную логику редакторов.

## 6. Как устроен bridge и почему он не создаёт второй источник истины

Новый файл:

`src/combat-lab/game-editors/CombatLabEditorShellBridge.ts`

Bridge выполняет только presentation-функции:

```text
существующий workspace panel
→ временно переносится в видимый host нового shell
→ пользователь работает с тем же owner/state
→ при закрытии panel возвращается в исходный hidden host
```

В нём намеренно отсутствуют:

- `new GameEditorRegistry`;
- новый `createDefaultGameEditorRegistry()`;
- собственный runtime эксперимента;
- `localStorage` как новый источник истины;
- отдельный gameplay state;
- таймеры/рендер-циклы;
- fake entities или demo data.

Это принципиальная часть результата: новый интерфейс является оболочкой над настоящими существующими механизмами, а не второй параллельной системой.

## 7. Какие файлы изменены implementation commit

### `src/combat-lab/game-editors/CombatLabEditorShellBridge.ts`

Новый presentation bridge между принятым shell и существующими workspace-панелями редакторов.

Отвечает за:

- кнопку «РЕДАКТОРЫ»;
- показ `settings` в отдельной рабочей области;
- показ `scene` и `parameters` в новой левой панели;
- возврат на предыдущую вкладку;
- восстановление исходных host-ов при destroy;
- поддержку `?tab=settings`.

### `src/combat-lab/game-editors/combat-lab-game-editor-shell.css`

Новый presentation-слой редакторов в визуальном языке Polygon shell, включая адаптацию под более узкие экраны.

### `src/combat-lab/main.ts`

В существующий boot-path добавлена установка `CombatLabEditorShellBridge` после создания текущего `CombatLabGameEditors`.

Сохраняется только один вызов `createDefaultGameEditorRegistry()` — существующий.

Также добавлен корректный destroy bridge при завершении/ошибке.

### `scripts/combat_lab_game_editors_smoke.mjs`

Расширен статический smoke-контракт:

- фиксирует полный текущий inventory registry;
- проверяет наличие shell bridge и CSS;
- проверяет привязки существующих Map/Unit workspace-hosts;
- проверяет установку/destroy bridge в `main.ts`;
- запрещает появление второго registry/runtime/localStorage/timer-loop внутри bridge;
- исправляет устаревшее ожидаемое название `settings` на текущее **«Общие редакторы»**.

## 8. Что намеренно не делалось

Эта задача не меняла и не должна была менять:

- игровую модель;
- `UnitModel` и его truth;
- selection store/selection semantics;
- Pixi renderer карты;
- Pixi renderer бойца;
- тактические команды правой кнопкой;
- entity context-menu arbitration;
- данные `Инфо / Внимание / Память`;
- editor domain logic;
- содержимое зарегистрированных редакторов;
- существующие write paths редакторов;
- fake/demo данные для демонстрации отсутствующих возможностей;
- deployment.

## 9. Зависимости от соседних направлений

### КАРТА

Эта задача показывает существующую поверхность `scene`, но цельный пользовательский опыт Редактора карты зависит от итоговой интеграции настоящей карты в новый shell направлением **КАРТА**.

### ПУЛЬС

Полный сценарий «выбрать настоящего бойца → открыть/редактировать именно его» зависит от общего live selection/unit seam направления **ПУЛЬС**.

Эта задача не создаёт второй selection только для редакторов.

### КОНТЕКСТ

Будущее entity context menu должно открывать редакторы через сохранённый общий editor API (`GameEditorRegistry` / Combat Lab open request), а не через DOM-селекторы.

Текущая задача сохранила этот API неизменным и тем самым оставила точку интеграции для **КОНТЕКСТА**.

## 12. Почему итоговый Route X статус — `blocked`, а не `success`

Кодовая интеграция выполнена, TypeScript и production build прошли. Однако критерий задачи требовал свежую браузерную/скриншотную проверку exact final SHA.

Она не была выполнена, поэтому нельзя честно утверждать:

- что все панели визуально совпадают с утверждённым дизайном;
- что ничего не перекрывается на реальном desktop/narrow viewport;
- что все 12 редакторов корректно открываются из каталога именно в собранном продукте;
- что Map/Unit сценарии полностью удобны после схождения с соседними направлениями.

Следовательно текущая формулировка результата:

> **Интеграция редакторов в новый shell реализована и компилируется, но требует отдельной visual/browser приёмки перед ACCEPT.**

## 13. Что нужно проверить при следующей приёмке

На exact актуальном commit после интеграции веток необходимо:

1. Открыть новый Полигон на desktop viewport.
2. Нажать **«РЕДАКТОРЫ»** и убедиться, что появляется настоящий каталог.
3. Сверить полный набор зарегистрированных редакторов с `GameEditorRegistry`.
4. Открыть минимум 2–3 embedded editor из разных групп.
5. Открыть Граф поведения и проверить отдельную route-навигацию и возврат.

7. Открыть Unit/Parameters поверхность на реальной выбранной сущности после схождения с ПУЛЬСОМ.
8. Проверить закрытие/возврат без потери состояния.
9. Повторить на narrow viewport.
10. Проверить browser console.
11. Снять свежие screenshots exact SHA и сравнить с принятым HTML-визуальным эталоном.
