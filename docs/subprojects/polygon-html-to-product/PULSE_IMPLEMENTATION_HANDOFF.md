Дата фиксации: 2026-08-17.

Этот документ фиксирует фактически выполненную реализацию в ветке `feature/20260817-polygon-pulse-live-unit-x` и PR #285. Он нужен следующим исполнителям и проверяющим, чтобы не восстанавливать архитектурные решения по коду и не создавать параллельные механизмы.

---

## 1. Что было целью

Нужно было закрыть один вертикальный продуктовый путь:

```text
выбор бойца
→ настоящий selectedUnitId
→ настоящий UnitModel
→ правая вкладка «Юнит» LIVE
→ штатная команда смены позы
→ readback фактического состояния того же UnitModel
```

Главное ограничение: интерфейс не должен иметь собственной копии бойца, второго selection store, собственного gameplay state или прямой записи в `UnitModel`.

Результат построен поверх уже существующих владельцев состояния и команд Combat Lab.

---

## 2. Что теперь происходит при выборе бойца

ПУЛЬС не создаёт новый механизм выбора.

Канонический источник выбора остаётся существующим:

- `SimulationState.selectedUnitId` — фактический выбранный `unitId`;
- `CombatLabSelectionController` — существующий мост синхронизации, а не второй store;
- `getSelectedUnit(state)` — получение настоящего выбранного `UnitModel`.

LIVE-вкладка «Юнит» при обновлении снова вызывает `getSelectedUnit(state)`. Она не хранит отдельный `UnitModel` как собственную gameplay truth.

Практический смысл:

```text
если карта/selection выбрали бойца A
→ правая панель читает бойца A из SimulationState
→ если выбор меняется на бойца B
→ панель начинает читать бойца B из того же SimulationState
```

Отдельного «выбранного бойца для правой панели» не существует.

---

## 3. Какие реальные данные выводятся во вкладке «Юнит»

Добавлен read-only presentation слой `CombatLabLiveUnitPresentation.ts`. Он преобразует настоящий `UnitModel` в удобный для UI снимок, но не становится новым владельцем данных.

Из реального состояния юнита читаются:

- имя/идентичность;
- сторона и тип юнита;
- роль в сценарии, если она есть в существующем draft;
- эффективная боеспособность;
- здоровье;
- мораль;
- подавление;
- усталость;
- стресс/физиологические показатели поддерживаемого объёма;
- фактическая текущая поза;
- приказ игрока;
- текущее фактическое действие;
- основное оружие;
- патроны в оружии;
- ёмкость оружия/магазина;
- доступный резерв боеприпасов, когда он существует в модели;
- готовность оружия;
- ранения и состояние тела;
- кровопотеря/первая помощь поддерживаемого объёма;
- направление взгляда/ориентация;
- связанные attention/movement profile IDs;
- существующие ссылки на связанные product profiles/editors.

Если какого-то реального значения нет, presentation не придумывает заглушечное gameplay-значение. Например, при отсутствии основного оружия UI не создаёт синтетическую винтовку.

---

## 4. Как определяется «что боец делает сейчас»

Вместо отдельного UI-runtime текущая активность выводится из уже существующих runtime-состояний юнита.

Presentation выбирает наиболее значимое фактическое действие с приоритетом примерно такого вида:

1. погиб / без сознания;
2. выполняет переход между позами;
3. оказывает первую помощь;
4. перезаряжается;
5. передаёт боеприпасы;
6. разворачивает/сворачивает оружие;
7. ведёт огонь;
8. движется;
9. выполняет текущее behavior-runtime действие;
10. ожидает.

Это presentation-решение для отображения уже существующей истины. Оно не создаёт новую систему действий.

---

## 5. Смена позы: как устроена запись

Это самая важная write-boundary задачи.

Кнопки позы не делают такое:

```text
unit.behaviorRuntime.posture = ...
```

и не меняют `selectedUnitId` напрямую.

Команда уходит только через существующий интерактивный путь Combat Lab:

```text
CombatLabVisualSession.executeInteractive({
  kind: 'posture',
  unitId,
  targetPosture,
})
```

Дальше используется штатная продуктовая цепочка команды, которая в конечном счёте запрашивает разрешённый переход позы у симуляции.

UI поддерживает три позы, соответствующие принятому прототипу:

- `Стоя` — `standing`;
- `Пригнув.` — `crouched`;
- `Лёжа` — `prone`.

---

## 6. Почему нажатие кнопки не равно мгновенной смене позы

Важная семантика сохранена: `accepted` означает, что команда **принята системой**, а не что боец уже физически завершил переход.

Поэтому после нажатия UI:

1. показывает результат штатной команды (`accepted/rejected` и `reasonRu`);
2. не подменяет фактическую позу новым значением оптимистически;
3. продолжает читать реальную `behaviorRuntime.posture`;
4. после выполнения симуляцией автоматически показывает новую фактическую позу.

Это и есть требуемый readback.

Например:

```text
нажали «Лёжа»
→ команда принята
→ текущая поза ещё может быть «Стоя»
→ текущее действие показывает переход позы
→ симуляция выполняет переход
→ readback видит posture = prone
→ UI показывает «Лёжа» как фактическое состояние
```

Если команда отклонена, интерфейс показывает реальную русскую причину `reasonRu`, а не маскирует отказ локальным переключением кнопки.

## 7. Правая панель и seam для соседних направлений

Добавлен минимальный нейтральный `CombatLabRightPanelSeam.ts`.

Его задача — не владеть содержимым всех вкладок, а дать общий технический стык существующей правой панели:

- host вкладки `unit`;
- host вкладки `info`;
- host вкладки `attention`;
- host вкладки `memory`;
- существующий `SimulationState`;
- существующий selection controller из `CombatLabWorkspaceServices`;
- проверку активной вкладки;
- обновление общей шапки правой панели.

ПУЛЬС использует `unit` host.

ЛИНЗА должна использовать тот же seam для `Инфо / Внимание / Память` и **не создавать второй selection**.

Также ПУЛЬС обновляет общую шапку правой панели только когда активна вкладка `Юнит`. Это сделано специально, чтобы будущие представления ЛИНЗЫ могли владеть своей шапкой при переключении на собственные вкладки.

## 8. Связанные профили и редакторы

LIVE-вкладка не создаёт новый механизм открытия редакторов.

Связанные профили юнита разрешаются через существующий helper:

`resolveCombatLabSelectedUnitProfileLinks(...)`.

Переход выполняется через существующий product request:

`requestCombatLabGameEditorOpen(...)`.

В запрос передаётся настоящий `selectedUnitId`, а return point указывает обратно на правую вкладку юнита.

Таким образом, ПУЛЬС не создаёт отдельный registry редакторов и не открывает их через случайные DOM-селекторы.

## 9. Визуальная структура вкладки

Визуальным источником использован утверждённый HTML-прототип:

`polygon-series-v1.1-memory-v3-interface-linkage(1).html`.

Из него перенесена компактная композиция вкладки «Юнит»:

- компактная шапка выбранного объекта;
- короткий статусный блок;
- сетка из четырёх основных показателей;
- компактные строки параметров;
- три одинаковые кнопки позы с символами `● ▲ ▬`;
- отдельный блок «Приказ игрока»;
- отдельный блок «Действие сейчас»;
- строка оружия/боеприпасов;
- строка состояния тела/ранений;
- раскрываемый блок «Дополнительно».

В CSS сохранены характерные размеры и пропорции прототипа, в частности компактные внутренние отступы, четырёхколоночная сетка статистики, высота кнопок позы и акцентные левые границы блоков приказа/текущего действия.

При этом это не копия JS/runtime HTML-прототипа: перенесён presentation, а данные и команды остаются продуктовыми.

## 10. Как LIVE-инспектор подключён к приложению

В `src/combat-lab/main.ts` обычная установка `CombatLabExtension` обёрнута минимальной установкой LIVE Unit.

После создания существующего Combat Lab extension код:

1. получает уже зарегистрированные `CombatLabWorkspaceServices`;
2. получает общий right-panel seam;
3. создаёт `CombatLabLiveUnitInspector` внутри существующего `unit` host;
4. подписывается на существующий selection;
5. подписывается на draft — для обновления role label;
6. подписывается на существующий application ticker для live readback;
7. при `destroy()` снимает все добавленные подписки и уничтожает inspector, после чего уничтожает исходный extension.

Новый глобальный runtime, новый таймер или второй application loop не создавались.

## 12. Что проверяют добавленные smoke-тесты

### `combat_lab_live_unit_ui_contract_smoke.mjs`

Статически проверяет ключевые архитектурные границы:

Проверка построена на настоящем `CombatLabVisualSession` и настоящем бойце встроенного сценария.

- снимок получает здоровье/мораль/подавление/усталость из реального юнита;

- при отсутствии оружия presentation не синтезирует fallback weapon;
- штатная posture-команда принимается через `executeInteractive`;
- сразу после принятия команды UI-снимок не подменяет фактическую позу;
- после шагов реальной симуляции readback видит завершённый переход в новую позу.

## 16. Точка интеграции для ЛИНЗЫ

После принятия ПУЛЬСА ЛИНЗА должна подключаться к существующему `CombatLabRightPanelSeam`, а не менять selection architecture.

Ожидаемая схема:

```text
один SimulationState.selectedUnitId
          ↓
один существующий selection controller
          ↓
CombatLabRightPanelSeam
          ├─ unit      → ПУЛЬС
          ├─ info      → ЛИНЗА
          ├─ attention → ЛИНЗА
          └─ memory    → ЛИНЗА
```

При этом каждая вкладка отвечает только за собственный presentation/read-model и допустимые product write paths.

---

## 17. Точка интеграции с КАРТОЙ и ПЕШКОЙ

ПУЛЬС уже принимает selection как внешний продуктовый факт и не зависит от того, как именно выглядит боец.

После подключения настоящей карты и нового знака бойца целевая цепочка должна стать:

```text
Pixi map
→ настоящий PixiUnitRenderer/token
→ штатный выбор бойца
→ SimulationState.selectedUnitId
→ тот же UnitModel
→ ПУЛЬС / «Юнит» LIVE
```

КАРТА и ПЕШКА не должны обходить этот selection path ради собственного UI.

## 18. Короткий handoff следующему проверяющему

При review PR #285 в первую очередь нужно доказать на полном checkout:

1. проект компилируется и собирается;
2. focused presentation smoke реально исполняется;
3. выбранный на карте настоящий боец появляется во вкладке `Юнит`;
4. при смене selection панель переключается на новый `UnitModel`;
5. posture command проходит через штатный command path;
6. UI не меняет позу до фактического readback;
7. отказ команды показывает `reasonRu`;
8. linked profile navigation открывает существующие редакторы;
9. внешний вид сравнен свежим browser screenshot с утверждённым HTML;
10. seam не конфликтует с реализацией ЛИНЗЫ.

Если эти проверки пройдут, ПУЛЬС закрывает свою часть критерия волны: **выбрать настоящего бойца → увидеть реальные LIVE-данные → штатно изменить позу → увидеть фактический readback**.
