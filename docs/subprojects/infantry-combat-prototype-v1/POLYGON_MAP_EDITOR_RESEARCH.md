# 1. Краткий вывод

## Что реально существует

В production существует рабочая модель карты и редактор сцены:

- карта с размером, размером клетки и числом метров на клетку;
- ячеечный слой поверхности `surfaceMaterialId`;
- ячеечный слой растительности `vegetationMaterialId`;
- дискретная высота клетки `-2…4`;
- отдельный массив объектов карты `map.objects`;
- отдельные массивы юнитов и зон угрозы;
- создание, выбор, перемещение, изменение размера, поворот и удаление объектов;
- создание и перемещение юнитов;
- создание, перемещение и изменение зон угрозы;
- кисти высоты и растительности;
- видимость слоёв объектов, юнитов и угроз;
- полная загрузка и выгрузка сцены в JSON;
- реестр профилей местности с физическими свойствами материалов;
- частичное обновление отрисовки через ревизии и грязные области.

## Что существует только в production

Только production имеет канонические клетки карты, физические свойства материалов, реальные `MapObjectKind`, игровую проходимость, влияние карты на обзор, огонь, укрытия, маршрутизацию и тактический рельеф, а также полноценную сериализацию сцены и рабочие ручки преобразования.

## Что существует только в автономном прототипе

Только HTML Полигона имеет будущие подвкладки `Поле / Рельеф / Покрытие / Дороги / Здания / Предметы`, отдельную UX-модель объектов программы `точка / область / маршрут / сектор`, единое пространство Полигона и упрощённый формат `real-wargame-polygon-prototype-v0`.

## Чего пока нет

Не найдено как законченная механика:

- рабочее изменение размера карты;
- кисть произвольных поверхностей в текущем production-редакторе;
- самостоятельная линейная модель дороги;
- каталог зданий или редактирование стен, дверей и помещений;
- общий список объектов сцены;
- пользовательский undo/redo;
- прямое дублирование выбранного объекта;
- ссылочная целостность между программой и объектами карты;
- правила уменьшения карты;
- утверждённая модель данных автономного редактора карты.

## Что можно переиспользовать

Концептуально можно переиспользовать реальные ID материалов и профилей, разделение поверхности/растительности/высоты, набор `MapObjectKind`, свойства объектов и их значения по умолчанию, устойчивые ID, операции выбора и преобразования, scene envelope, import/export и отдельные слои отображения.

## Что требует нового UX

Новый UX нужен почти для всей вкладки: компактные инструменты слоёв, понятные названия материалов, единый инспектор, подробный редактор, безопасное удаление ссылочных объектов, история действий и строгая граница между объектами карты, программой и участниками эксперимента.

# 2. Текущий production-редактор

## 2.1. Компоновка и режимы

Рабочая оболочка устанавливается так:

```text
GameApplication
→ installGameEditorWorkbench
→ installSceneExportControls
→ installTacticalWorkspace
```

Ручной контракт `TACTICAL_WORKSPACE_STAGE_7.md` задаёт два режима:

```text
Симуляция | Редактирование
```

При переходе в редактирование симуляция ставится на паузу, симуляционные панели скрываются, справа открывается редактор сцены. Основной UI находится в `src/ui/GameEditorWorkbench.ts`.

Вкладки:

```text
Предмет
Боец
Угроза
Рельеф
Сцена
```

Карта остаётся главным рабочим пространством, правая панель задаёт инструмент и параметры.

## 2.2. Владение вводом карты

Источник указательных событий — `src/input/BoardInputController.ts`.

```text
указатель на canvas
→ BoardInputController
→ проверка editor.enabled и editor.tool
→ MapPaint / GameEditorPlacement / SimulationStateLegacy
→ изменение map / units / pressureZones
→ MapRuntimeState отмечает ревизию и грязную область
→ renderer и gameplay-потребители читают обновлённую модель
```

Высота и растительность рисуются непрерывно при движении зажатого указателя. Размещение использует `placeConfiguredEditorEntity()`. Выбор и преобразование проходят через `begin/update/finishEditorPointerAction()`. `Escape` отменяет операцию и возвращает выбор, `Delete` удаляет выбранную сущность. Отдельного production-контекстного меню редактора не найдено.

## 2.3. Вкладка «Предмет»

**Назначение:** создание и изменение отдельного `MapObject`.

**Сценарий:** выбрать тип и параметры, включить размещение, кликнуть на карте, затем перетаскивать объект, ручки размера или поворота; свойства можно применить из панели или удалить объект.

**Основные файлы:**

```text
src/ui/GameEditorWorkbench.ts
src/core/editor/GameEditorDrafts.ts
src/core/editor/GameEditorPlacement.ts
src/core/simulation/SimulationStateLegacy.ts
src/core/map/MapModel.ts
src/core/map/MapObjectGeometry.ts
src/core/map/MapRuntimeState.ts
src/rendering/PixiMapRenderer.ts
```

**Источник истины:** `state.map.objects: MapObject[]`.

Черновик создания содержит имя, тип, размеры, поворот, высоту для линии видимости, защиту, надёжность укрытия, маскировку, пробиваемость и допустимую позу.

`placeConfiguredEditorEntity()` создаёт `editor_object_N` и переносит параметры в `state.map.objects`. Объект можно перемещать, менять размер и поворачивать. Удаление фильтрует массив по ID или удаляет цель под указателем.

Операция «копировать» в текущем коде копирует параметры выбранного объекта в черновик. Подтверждённого действия «создать точную копию рядом» нет.

`SceneSnapshot` сохраняет ID, тип, координаты, размеры, поворот, LOS-высоту, защиту, надёжность, маскировку, пробиваемость, позу укрытия и подписи.

Ограничения: техническая палитра вместо каталога, общий `structure` вместо модели здания, нет списка/поиска, нет группировки, множественного преобразования, дублирования и undo/redo.

## 2.4. Вкладка «Боец»

**Назначение:** создание и настройка участника сцены.

Основные файлы:

```text
src/ui/GameEditorWorkbench.ts
src/core/editor/GameEditorDrafts.ts
src/core/editor/GameEditorPlacement.ts
src/core/units/UnitModel.ts
src/core/simulation/SceneSnapshot.ts
```

Источник истины — `state.units: UnitModel[]`, а не карта. Черновик содержит сторону, тип, предмет в руках, профиль поведения, скорость, направление, обзор, внимание, позу, стресс, подавление, боезапас, готовность оружия, черты и состояние.

Создание нормализует данные через `normalizeUnits()`. Перемещение меняет `unit.position` и сбрасывает текущий приказ. Сериализация сохраняет конфигурацию, начальное состояние, профили, знания и runtime.

Вывод: боец не должен становиться `map object`. Его свойства принадлежат участнику эксперимента; карта предоставляет размещение и выбор.

## 2.5. Вкладка «Угроза»

Источник истины — `state.pressureZones: PressureZone[]`.

Поддерживаются:

- формы `circle` и `rect`;
- режимы `area` и `directional_fire`;
- сила, подавление, стресс;
- направление, сектор, дальность, мёртвая зона и затухание;
- признаки видимости и известности источника;
- уверенность и неопределённость.

Зона создаётся через `normalizePressureZones()`, перемещается и меняет размер ручками. Это отдельная сущность сценария/эксперимента, а не объект карты и не объект программы.

## 2.6. Вкладка «Рельеф»

Основные файлы:

```text
src/ui/GameEditorWorkbench.ts
src/core/map/MapPaint.ts
src/core/map/MapModel.ts
src/core/map/MapRuntimeState.ts
src/rendering/PixiMapRenderer.ts
src/rendering/VegetationChunkRaster.ts
```

### Высота

Инструмент `paint_height` задаёт абсолютный дискретный уровень `-2…4`. Кисть круглая или квадратная, имеет размер, работает непрерывно и умеет очищать слой до 0. Результат хранится в `MapCell.height`, сериализуется в `heightMap` и используется отрисовкой, видимостью, навигацией и вычисляемым направленным рельефом.

### Растительность

Инструмент `paint_forest` использует старый выбор `0/1/2`, который преобразуется в канонические ID:

```text
0 → none
1 → sparse_forest
2 → dense_forest
```

Источник истины — `MapCell.vegetationMaterialId`. Поле `forest` остаётся совместимым представлением старого формата.

### Важный разрыв

Кисти произвольной поверхности `surfaceMaterialId` в прослеженной цепочке production-редактора нет, хотя модель, реестр, отрисовка, сериализация и игровые потребители поверхности существуют.

## 2.7. Вкладка «Сцена»

`SceneExportControls` предоставляет «Сохранить сцену» и «Загрузить сцену». Выгрузка строится через `buildSceneSnapshot()`, загрузка — через `restoreSimulationStateFromSceneSnapshot()`.

Текущий envelope:

```text
scene-export-v10-physical-posture-action-2m-grid
```

Сохраняются:

- размер и разрешение карты;
- `environmentProfileId`;
- `heightMap`;
- совместимый `forestMap`;
- `surfaceMaterialMap`;
- `vegetationMaterialMap`;
- объекты карты;
- профили местности и движения;
- юниты;
- зоны угрозы;
- runtime и необязательный предрасчёт тактической основы.

При загрузке нормализуются карта, юниты и зоны, восстанавливаются профили/runtime, очищается выделение и пересчитываются счётчики новых ID.

## 2.8. Undo/redo

Пользовательской истории действий не найдено. `MapRuntimeState.history` хранит только ограниченную историю ревизий и грязных областей для частичного обновления отрисовки. Это не undo/redo.

## Каноническая клетка

`normalizeMap()` создаёт плоский массив `map.cells`. Канонические ссылки материала:

```text
surfaceMaterialId
vegetationMaterialId
```

Старые `terrain` и `forest` нормализуются и сохраняются ради совместимости. Они не должны становиться вторым независимым источником физических свойств.

## Обновление renderer

`MapRuntimeState` ведёт ревизии `terrain / height / forest / objects` и грязные области. `PixiMapRenderer` отдельно обновляет поверхность/высоту, сетку и объекты. `VegetationChunkRaster` делит карту на блоки 32×32 клетки, сохраняет долгоживущие canvas/texture/sprite и перестраивает только затронутые блоки. Игровая логика не читает пиксели renderer.

## Игровые потребители

- `GridNavigation` читает проходимость поверхности, сопротивление растительности, высоту и блокирующие объекты;
- `EnvironmentSensors` объединяет поверхность, растительность и объекты в оценки укрытия, маскировки и открытости;
- видимость и огонь читают высоту, объекты и профили растительности;
- направленный рельеф вычисляется из высоты и направления угроз, но не хранится как редактируемый объект;
- пространственные индексы и поля тактических позиций зависят от ревизий карты.

# 4. Реальные реестры и профили

## 4.1. `EnvironmentProfileRegistry`

Основные файлы:

```text
src/core/map/EnvironmentMaterialProfile.ts
src/core/map/EnvironmentProfileRuntime.ts
src/ui/EnvironmentProfileStorage.ts
src/ai-node-editor/EnvironmentProfileEditorPanel.ts
```

Встроенный профиль:

| ID | Название | Где хранится | Где редактируется | Где используется | Показывать в Полигоне |
|---|---|---|---|---|---|
| `default` | Стандартная местность | core registry | «Профили местности» | renderer, обзор, огонь, движение | да, по названию; ID — в данных |

Поверхности:

| ID | Русское название | Основные свойства | Безопасность показа |
|---|---|---|---|
| `field` | Поле | цвет, сопротивление, проходимость, цена | безопасно |
| `road` | Дорога | более низкое сопротивление | безопасно |
| `rough` | Пересечённая местность | повышенное сопротивление | безопасно |
| `swamp` | Болото | большое сопротивление | безопасно |
| `water` | Вода | непроходимость | безопасно |

Растительность:

| ID | Русское название | Свойства | Безопасность показа |
|---|---|---|---|
| `none` | Нет растительности | нулевой слой | безопасно |
| `sparse_forest` | Редкий лес | вид, обзор, огонь, движение | безопасно |
| `dense_forest` | Густой лес | более сильные эффекты | безопасно |

Профиль имеет независимые ревизии `presentation / visibility / fire / movement`. Видимый редактор умеет выбирать, копировать, переименовывать, сбрасывать, импортировать, экспортировать и удалять пользовательские профили. Технические ID не нужно выставлять обычному пользователю.

Реестр хранится в браузере под ключом:

```text
real-wargame.environment-profiles.v1
```

Scene export также включает snapshot реестра, поэтому сцена переносима.

## 4.2. `NavigationProfileRegistry`

Реальные встроенные ID:

```text
normal
fast
stealth
attack
cautious
retreat
direct
```

Это не палитра карты. Реестр задаёт тактическое отношение юнита к опасности, укрытию, материалам и направленному рельефу. Во вкладке карты его можно показывать только в диагностике или через выбранного участника.

## 4.3. Типы объектов карты

Формального отдельного реестра пользовательских ассетов не найдено. Каноническая палитра сейчас задана union-типом `MapObjectKind`, значениями по умолчанию в `GameEditorDrafts` и ветвлением renderer:

```text
cover, structure, ditch, logs, rock, crates,
fence, tree, post, well, bridge
```

В Полигоне их безопасно показывать по русским названиям. Не нужно обещать каталог моделей, которого нет.

## 4.4. Направленный рельеф

`DirectionalTacticalField` и связанные профили — вычисляемая тактическая производная от высоты и угроз. Это не самостоятельный слой авторинга. Пользователь меняет высоты, после чего производные пересчитываются.

## 4.5. Реестры участников

Профили поведения, движения, маршрута, внимания и мозга относятся к участникам эксперимента. Карта может показывать их влияние и размещение, но не должна владеть этими данными.

- `map.objects`;

- реальных геометрических типов зданий/дорог;
- команд истории карты.

## 5.3. Вкладка «Редактор карты»

Подвкладки существуют визуально:

```text
Поле
Рельеф
Покрытие
Дороги
Здания
Предметы
```

### «Поле»

Поля ширины и высоты работают только как интерфейсная заглушка. Браузерная проверка 120×80 → 240×160 показала, что геометрия viewport и модель эксперимента не меняются. Появляется сообщение:

```text
Размер поля применён только визуально в прототипе
```

### Остальные подвкладки

Кнопки создают общий маркер `type: 'terrain'`. «Рельеф», «Дорога», «Здание» и «Предмет» не имеют разных моделей и не меняют production-подобную карту. В проверке «Дороги» добавили тот же DOM-класс `map-marker map-marker--terrain`.

## 5.4. Декоративная центральная карта

CSS-элементы `.terrain-road`, `.terrain-stream`, `.forest-patch`, `.house` являются фоном. Они не связаны с `state`, не выбираются как реальные map objects и не сериализуются как карта.

## 5.5. Правая панель и выбор

Правая панель умеет показывать сведения о выбранном юните и некоторых программных элементах. Полноценного инспектора поверхности, клетки, высоты, растительности или `MapObject` нет.

Контекстное меню карты работает как UX-оболочка и может добавлять юниты/маркеры/программные цели, но не содержит production-команд карты.

## 5.6. Объекты программы

`pstate.points` действительно различает:

- точку;
- область;
- маршрут;
- сектор.

Программа умеет ссылаться на типы целей вроде `program-object`, `unit`, `map-object`. Это полезная граница, но `map-object` пока ссылается на декоративный маркер, а не на production-подобный объект карты.

## 5.7. Import/export

Текущий формат:

```text
real-wargame-polygon-prototype-v0
```

Сохраняются метаданные эксперимента, упрощённые маркеры и юниты. Полная модель программы и карта production-уровня не входят в надёжный scene envelope. Размер поля, клетки материалов, высоты и реальные объекты карты не сохраняются.

## 5.8. Что рабочее

- переключение основных вкладок и подвкладок;
- панели, сворачивание и изменение ширины;
- выбор и редактирование юнитов;
- существенная часть редактора программы;
- точки/области/маршруты/секторы программы;
- упрощённые маркеры;
- prototype import/export;
- встроенные self-tests.

## 5.9. Что декоративное

- дорога, ручей, лес и дома фона;
- маркеры «Рельеф/Дорога/Здание/Предмет» как доказательство модели карты;
- изменение размера поля;
- подписи инструментов карты без соответствующих данных и операций.

## 5.10. Что нельзя переносить без переделки

Нельзя сохранять общий `terrain`-маркер как универсальную сущность, декоративные CSS-дома/дорогу как данные, ложное изменение размера, смешанный список целей без ссылочной проверки и экспорт, который не сохраняет карту и программу целиком.

# 6. Разрыв между production и Полигоном

| Направление | Что есть в игре | Прямой источник данных | Что требует нового UX | Чего нет | Решение пользователя |
|---|---|---|---|---|---|
| Поле | размер, разрешение, нормализация и загрузка | `TacticalMap` и `ResolutionAwareScene` | создание/изменение размера, проверка конфликтов | рабочий editor resize | правила уменьшения и привязки координат |
| Рельеф | высота `-2…4`, кисть, очистка, renderer и gameplay | `MapCell.height`, `MapPaint` | палитра уровней, повысить/понизить, предпросмотр | непрерывная высота и рельефные объекты | оставить абсолютные уровни или добавить UX-команды поверх них |
| Покрытие | поверхности и растительность как разные материалы | `EnvironmentProfileRegistry`, клетки | две палитры, кисть, пипетка, заливка, профили | production-кисть поверхности | объединять ли в одну подвкладку и как показывать профили |
| Дороги | поверхность `road` | surface material `road` | линия/полоса как способ рисования покрытия | самостоятельная road entity, узлы, ширина, перекрёстки | материал или будущий объект дороги |
| Здания | общий `MapObject(kind=structure)` | `MapObject`, defaults, renderer | понятное «строение», размеры, поворот, свойства укрытия | каталог, стены, двери, этажи | достаточно ли прямоугольного строения |
| Предметы | остальные `MapObjectKind` | `map.objects` | категории, палитра, поиск, инспектор, дублирование | asset registry и группы | структура каталога и допустимые свойства |

Рекомендуемые честные подписи:

- `Дороги` — «Рисование дорожного покрытия», пока не появится отдельная production-модель;
- `Здания` — «Строения», если используется только `structure`;
- `Покрытие` — явно разделить «Поверхность» и «Растительность»;
- будущие механики маркировать как prototype-only.

# 7. Варианты архитектуры

## Вариант A — минимальная оболочка над production-моделью

Интерфейс почти напрямую показывает клетки, `MapObject`, юниты и угрозы.

**Плюсы:** минимальное расхождение, простые адаптеры, малая вероятность выдумать механику.

**Минусы:** технический интерфейс, тяжёлые формы, плохое соответствие компактному Полигону, слабая работа с программными ссылками.

**Оценка:** понятность 2/5; соответствие production 5/5; сложность HTML 3/5; переносимость 4/5; масштабируемость 3/5; риск дублирования 2/5.

## Вариант B — единый объектный редактор

Поверхность, высота, дорога, строение, предмет, юнит и программная точка представлены как универсальные объекты.

**Плюсы:** один список, одна панель, единообразные действия.

**Минусы:** противоречит production-модели; ячеечные слои не являются объектами; смешивает карту, программу и участников; требует искусственных оболочек и создаёт второй источник истины.

**Оценка:** понятность 3/5 сначала и 1/5 на сложных сценах; соответствие 1/5; сложность 5/5; переносимость 1/5; масштабируемость 2/5; риск дублирования 5/5.

## Вариант C — специализированные инструменты по слоям

Каждая подвкладка работает со своим типом данных: поле, высота, материалы, дорожное покрытие, строения, предметы.

**Плюсы:** соответствует production, удобен для кистей и объектов, не выдаёт клетки за объекты, хорошо переносится через адаптеры.

**Минусы:** нужно унифицировать выбор, панель свойств и ссылки; больше разных режимов.

**Оценка:** понятность 4/5; соответствие 5/5; сложность 4/5; переносимость 5/5; масштабируемость 5/5; риск дублирования 1/5.

## Вариант D — специализированные слои с единым выбором и командами

Развитие C:

- реальные данные остаются разными;
- единый `SelectionRef` сообщает, что выбрано;
- правая панель выбирает подходящий инспектор;
- все изменения проходят через прототипные команды;
- ссылки программы используют стабильные ID или именованные области;
- общий список группирует сущности, но не объединяет их модель.

**Оценка:** понятность 5/5; соответствие 5/5; сложность 4/5; переносимость 5/5; масштабируемость 5/5; риск дублирования 1/5.

## Рекомендация

Выбрать **вариант D**: специализированные инструменты по слоям с единым механизмом выбора, правой панелью, командами и ссылками. Он сохраняет production-границы, но не копирует устаревший production-UX.

# 8. Предлагаемый состав вкладки

## Левая панель

Сохранить шесть подвкладок:

```text
Поле
Рельеф
Покрытие
Дороги
Здания
Предметы
```

### Поле

- текущий размер в клетках и метрах;
- метры на клетку только как подтверждённое свойство;
- кнопка «Изменить размер»;
- выбор якоря изменения;
- предварительная проверка сущностей за новой границей;
- список конфликтов до применения.

### Рельеф

- выбор абсолютного уровня `-2…4`;
- круг/квадрат;
- размер кисти;
- нарисовать, стереть до 0;
- UX-команды повысить/понизить только как преобразование тех же дискретных уровней;
- слой высот и горизонтали.

### Покрытие

Внутренний переключатель:

```text
Поверхность | Растительность
```

Инструменты: кисть, пипетка, заливка связной области, очистка растительности, выбор активного профиля. Палитра показывает русские названия; ID сохраняются в данных.

### Дороги

До отдельного решения это быстрый инструмент нанесения `road`:

- линия или ломаная;
- ширина в клетках;
- предпросмотр полосы;
- результат — изменение surface layer;
- явная подпись «Дорожное покрытие».

### Здания

- палитра «Строение»;
- размер, поворот, имя;
- базовые свойства укрытия;
- разместить один/много;
- не показывать каталог домов, этажи и двери как существующие.

### Предметы

Категории поверх реальных `MapObjectKind`:

```text
Природа: tree, rock
Преграды: cover, fence, ditch
Хозяйственные: crates, logs, post, well
Переходы: bridge
```

Инструменты: выбор, размещение, перемещение, размер, поворот, удалить, дублировать как новая прототипная команда.

## Режимы карты

```text
Выбор
Кисть
Линия
Размещение
Пипетка
Панорамирование
```

В один момент активен один инструмент авторинга. Панорамирование и масштаб не должны менять данные.

## Единый выбор

Предлагаемый UX-тип:

```text
SelectionRef =
  | { domain: 'map-object', id }
  | { domain: 'program-object', id }
  | { domain: 'participant', id }
  | { domain: 'scenario-zone', id }
  | { domain: 'map-cell', x, y, layer }
  | null
```

Он унифицирует интерфейс, но не объединяет модели.

## Правая панель

- пустое состояние: сводка карты и активный инструмент;
- клетка: координаты, высота, поверхность, растительность;
- объект карты: имя, тип, положение, размер, поворот, игровые свойства и ссылки;
- объект программы: геометрия и использующие шаги;
- участник: краткая расстановка и переход в редактор юнита;
- зона сценария: форма и параметры угрозы.

Сложные свойства открываются в подробном модальном редакторе. Основная панель остаётся компактной.

## Контекстное меню

Контекст зависит от цели:

- пустая карта: создать объект программы, участника, строение или предмет;
- объект карты: свойства, дублировать, удалить, найти ссылки;
- программный объект: открыть программу, дублировать, удалить;
- участник: открыть редактор юнита, направление, программа;
- клетка: пипетка, локальная информация.

## Слои отображения

Минимальные переключатели:

```text
Поверхности
Растительность
Высоты/горизонтали
Объекты карты
Участники
Зоны сценария
Объекты программы
Маршруты/секторы
Сетка
Подписи
```

Скрытие слоя не удаляет данные и не меняет возможность выбора без явного правила.

## Undo/redo

Автономный прототип должен иметь ограниченный стек команд. Один мазок кисти — одна команда; перетаскивание — одна команда от начала до конца; импорт и изменение размера — составные команды. `MapRuntimeState.history` для этого использовать нельзя.

## Сохранение

Сохранять нужно всё определение эксперимента: карту, участников, программу, зоны сценария, ссылки и прототипные метаданные. Экспорт должен иметь версию формата, а импорт — миграцию и отчёт об ошибках.

## Подтверждено production-кодом

- размер и разрешение карты;
- profile ID;
- height/surface/vegetation layers;
- `MapObject` ID, kind, положение, размеры, поворот и игровые свойства;
- участники как отдельный массив;
- зоны угрозы как отдельный массив;
- устойчивые строковые ID;
- сериализация snapshot реестров.

## UX-представление

- RLE или иное компактное кодирование слоёв;
- категории предметов;
- `SelectionRef`;
- общий список с группами;
- команды истории;
- именованные map regions для ссылок;
- предупреждения и ссылки удаления.

## Временные данные прототипа

- состояние раскрытия панелей;
- положение камеры;
- активная подвкладка и инструмент;
- декоративные legacy-маркеры;
- временные preview-геометрии линии и кисти.

Эти поля не должны попадать в будущую production-сериализацию без отдельного решения.

## Требуют решения

- являются ли дороги только surface layer;
- формат изменения размера;
- точная форма building model;
- место хранения начальной расстановки;
- политика broken references;
- глубина undo/redo;
- snapshot профиля или только ID;
- представление больших карт в автономном JSON.

## Адаптерная граница

Будущий интерфейс должен вызывать команды вида:

```text
paintHeight(region, level)
paintSurface(region, materialId)
paintVegetation(region, materialId)
createMapObject(draft)
updateMapObject(id, patch)
deleteEntity(ref, policy)
resizeMap(request)
```

Автономная реализация меняет UX-state; production-адаптер позднее переводит те же команды в реальные модели. Нельзя импортировать production-компоненты в HTML и нельзя делать HTML вторым источником gameplay-правил.

# 10. Риски и открытые решения

## 10.1. Дороги

Варианты: кисть материала, линия поверх материала, самостоятельный объект дороги. Рекомендация: UX-линия, результатом которой остаётся `surfaceMaterialId=road`. Самостоятельную сущность не вводить без production-проекта.

## 10.2. Растительность

Варианты: внутри «Покрытие», отдельная верхняя вкладка, смешанная палитра. Рекомендация: внутри «Покрытие», но отдельным режимом, потому что это независимый слой.

## 10.3. Высоты

Варианты: абсолютный уровень, повысить/понизить, непрерывная высота, объекты рельефа. Рекомендация: абсолютные production-уровни; повысить/понизить — только UX-команда над ними.

## 10.4. Здания

Варианты: общий прямоугольный `structure`, каталог типов, редактор стен. Рекомендация: честно использовать «Строение» и `structure`; остальное пометить будущим.

## 10.5. Начальная расстановка юнитов

Варианты: карта владеет координатами; участник владеет координатами; отдельный placement layer. Рекомендация: данные принадлежат участнику, карта предоставляет placement layer и инструмент.

## 10.6. Уменьшение карты

Варианты: запретить при конфликтах, обрезать, автоматически сдвинуть, оставить ошибки. Рекомендация: блокировать применение, показать сущности за границей и дать явные действия перемещения/удаления. Автосдвиг не выполнять.

## 10.7. Удаление объекта со ссылками

Варианты: запрет, broken refs, каскадное удаление шагов, переназначение. Рекомендация: диалог со списком ссылок; по умолчанию запрет; разрешить явное переназначение или удаление с ошибками. Шаги программы автоматически не удалять.

## 10.8. Общий список объектов

Рекомендация: один список с группами `Карта / Программа / Участники / Зоны`, но без общей модели данных.

## 10.9. История изменений

Рекомендация: ограниченный command stack в прототипе. Нужно решить лимит, поведение после импорта и хранение больших мазков.

## 10.10. Профили местности

Варианты: только ID, полная копия реестра, ID + snapshot. Рекомендация: ID + snapshot, как в scene export, с явным разрешением конфликтов при импорте.

## 10.11. Зоны угрозы

Рекомендация: отдельный слой сценария. Редактирование происходит на карте, но данные не принадлежат карте.

## 10.12. Ссылки на ячеечные слои

Ячейки не имеют устойчивого объектного ID. Для программы использовать координату, объект программы или именованный map region. Не вводить ID каждой клетки.

## 10.13. Старые декоративные маркеры

`experiment.markers[type=terrain]` нельзя молча превратить в реальные объекты. Рекомендация: импортировать в `legacyDecorativeMarkers`, показать предупреждение и предложить ручную классификацию.

## 10.14. Конфликт deployment и кода

Deployment не проверен. До утверждения UX оркестратор должен повторить реальные браузерные сценарии и подтвердить, что развернутая версия соответствует исследованному Foundation или зафиксировать отличия.

# Приложение D. Конфликты источников

1. **Standalone title/meta.** Переданный HTML показывал v8.1, но содержал v8.2 additions. Manifest и launcher задают v8.2; точный SHA получен заменой только title/meta.
2. **`terrain/forest` против material IDs.** Старые поля остаются для совместимости. Канонические источники — `surfaceMaterialId` и `vegetationMaterialId`.
3. **Дорога.** Prototype показывает отдельную подвкладку и декоративную дорогу. Production подтверждает только материал `road`. Отдельная road entity требует решения.
4. **Здание.** Prototype показывает дома как фон. Production имеет общий `structure`, а не каталог зданий.
5. **Deployment.** Из-за блокировки нельзя подтвердить, что он соответствует Foundation и что все кодовые функции доступны в UI. До повторной проверки наиболее вероятный источник истины — production-код Foundation.
