# Оружейно-зависимое поле опасности

## Статус документа

- Тип: проектная идея / техническая концепция.
- Проект: **Real-wargame**.
- Область: восприятие угрозы, поле опасности, маршрутизация, укрытия, тактические позиции и будущая техника.
- Основная цель: научить существующий слой опасности учитывать реальную разницу между оружием, дистанцией, укрытием, готовностью к огню и типом цели без создания новой дорогой карты или параллельной боевой системы.

Связанные системы:

- `SoldierDangerField`;
- субъективные контакты и `perceptionKnowledge`;
- память об угрозах;
- route-cost и маршрутизация;
- быстрый расчёт защиты от огня;
- общая геометрия линии огня;
- тактические позиции и action ports;
- подавление;
- новая система стрелкового боя Stage 3–9;
- испытательное приложение Combat Lab;
- будущая техника и броня;
- Graph v2;
- диагностические слои.

---

# 1. Главная идея

В игре уже существует канонический слой опасности. Поэтому не нужно создавать:

- отдельную карту эффективности оружия;
- отдельную карту огневой угрозы;
- отдельную карту подавления;
- отдельную карту опасности для маршрута;
- новый полный проход карты для тактических позиций.

Нужно развивать существующий `SoldierDangerField`, чтобы величина опасности зависела не только от положения известного противника, но и от того:

- какое оружие у него известно или предполагается;
- насколько это оружие эффективно на текущем расстоянии;
- способен ли противник открыть огонь сейчас;
- насколько плотный огонь он может вести;
- находится ли точка в секторе установленного оружия;
- насколько укрытие защищает именно от этого воздействия;
- насколько оценивающий боец уверен в контакте и его вооружении.

Общая схема:

```text
субъективно известная угроза
+
компактный профиль оружия
+
расстояние и направление
+
существующая геометрия линии огня
+
существующая оценка укрытия
+
готовность оружия
=
обновлённое значение SoldierDangerField
```

Поле остаётся одним. Меняется качество его входных данных.

---

# 2. Почему простой коэффициент оружия недостаточен

Плоская оценка вида:

```text
винтовка = 1.0
ППШ = 0.8
ДП-27 = 1.4
```

не передаёт реальное различие оружия.

ППШ:

- очень опасен на малой дистанции;
- быстро создаёт плотность огня;
- хорошо подавляет;
- быстро расходует боеприпасы;
- резко теряет эффективность на дальних дистанциях.

Винтовка:

- сохраняет угрозу дальше;
- медленнее создаёт подавление;
- лучше расходует боеприпасы;
- сильнее зависит от точности одного выстрела.

ДП-27:

- особенно силён как источник длительного подавления;
- зависит от установки, сектора и помощника;
- может быть временно не готов к огню;
- после установки контролирует пространство иначе, чем переносное оружие.

Следовательно, оружие должно описываться небольшой функцией от расстояния и режима воздействия, а не одним постоянным множителем.

---

# 3. Один слой, два внутренних канала

Внутри существующей оценки опасности достаточно разделить воздействие на два канала.

## 3.1. Опасность поражения — `lethalDanger`

Показывает ожидаемую способность угрозы нанести физическое поражение.

Учитывает:

- дистанционную эффективность;
- вероятность попадания в упрощённой форме;
- пробиваемость укрытия;
- видимую часть цели;
- готовность оружия;
- направление и сектор;
- уверенность в контакте.

## 3.2. Опасность подавления — `suppressionDanger`

Показывает ожидаемую способность угрозы ограничивать действия бойца плотным огнём.

Учитывает:

- темп огня;
- длительность возможного огня;
- near miss и near impact потенциал;
- площадь контролируемого сектора;
- готовность оружия;
- примерный боезапас;
- уверенность в контакте.

После расчёта оба канала сводятся в уже существующее итоговое значение поля:

```text
danger =
    lethalDanger × lethalWeight
  + suppressionDanger × suppressionWeight
```

Снаружи система по-прежнему может публиковать один scalar danger, поэтому существующие потребители не обязаны сразу менять контракт.

Разделение двух каналов нужно внутри, чтобы:

- винтовка и ППШ не становились одинаковыми после одного усреднения;
- укрытие по-разному влияло на поражение и подавление;
- пулемёт мог создавать сильную опасность даже при невысокой вероятности быстрого попадания;
- позднее можно было учитывать технику без полной переделки поля.

# 4. Компактный профиль угрозы оружия

Для каждого опубликованного сочетания оружия и боеприпаса нужен маленький неизменяемый профиль.

Примерный контракт:

```ts
interface WeaponThreatProfileV1 {
  schemaVersion: 1;
  profileId: string;
  weaponRevision: string;
  ammunitionRevision: string;

  distanceStepMeters: number;
  lethalByDistance: readonly number[];
  suppressionByDistance: readonly number[];

  maximumThreatRangeMeters: number;
  penetrationClass: number;
  sustainedFireClass: number;
  sectorKind: 'free' | 'limited_when_deployed';
}
```

Это не новая физика и не замена баллистике.

Профиль является дешёвой аппроксимацией ожидаемого результата, полученной из:

- опубликованных характеристик оружия;
- реальной производственной симуляции;
- массовых прогонов Combat Lab;
- последующей ручной калибровки.

В игровом hot path профиль должен требовать только:

- определение distance bucket;
- чтение двух значений из массивов;
- несколько умножений;
- минимум временных объектов.

Допускается линейная интерполяция между двумя соседними значениями, если она не создаёт лишних объектов и измерена как безопасная.

# 5. Субъективность оценки

`SoldierDangerField` не должен использовать скрытое авторитетное состояние неизвестного противника.

Источником остаются существующие субъективные данные бойца:

- текущие контакты;
- remembered threats;
- уверенность;
- возраст памяти;
- предполагаемая позиция;
- известный или предполагаемый класс оружия;
- известное направление стрельбы;
- наблюдавшаяся установка пулемёта;
- известные события входящего огня.

Возможные уровни знания оружия:

```text
exact_weapon
weapon_class
automatic_fire_source
small_arms_unknown
unknown_threat
```

Примеры:

- боец увидел винтовку — используется точный винтовочный профиль;
- боец слышал автоматический огонь — используется профиль класса автоматического оружия;
- боец видит силуэт, но не оружие — используется консервативный общий профиль стрелкового оружия;
- контакт существует только в памяти — профиль ослабляется уверенностью и временем;
- контакта нет — источник не появляется в субъективном поле опасности.

Нельзя позволять danger layer определять реальное оружие по `unitId`, если наблюдатель этого не знает.

---

# 6. Использование существующей геометрии и укрытий

Новый расчёт не должен создавать второй трассировщик и второй evaluator укрытий.

Нужно использовать уже существующие:

- подготовленную геометрию угрозы;
- общий line-of-fire контракт;
- каноническую геометрию объектов карты;
- posture-aware exposure;
- быстрый allocation-bounded scalar расчёт защиты;
- существующие revision keys и кэши геометрии.

## 6.1. Поражение

Укрытие сильнее влияет на `lethalDanger`:

```text
residualLethal =
  baseLethal
  × exposure
  × penetrationTransmission
```

Где `penetrationTransmission` вычисляется существующим быстрым путём защиты с учётом класса боеприпаса или компактного penetration class.

## 6.2. Подавление

Подавление может частично проходить даже при невозможности прямого поражения:

```text
residualSuppression =
  baseSuppression
  × suppressionTransmission
```

Например, каменная стена почти полностью закрывает поражение, но интенсивный огонь по стене всё равно может создавать опасность высовывания, near-impact события и психологическое давление.

При этом нельзя выдумывать подавление без связи с принятой системой Stage 8. Коэффициенты должны калиброваться по физическим near miss, near impact и direct hit результатам.

---

# 7. Готовность оружия

Поле опасности не должно пересчитывать полный lifecycle боевого действия.

Достаточно компактного коэффициента `fireReadiness`.

Примерная классификация:

```text
1.00 — оружие готово открыть огонь;
0.70 — требуется короткая подготовка;
0.35 — идёт длительная подготовка или установка;
0.10 — оружие временно почти не способно воздействовать;
0.00 — огонь невозможен.
```

Источники:

- reload state;
- deploy/undeploy state;
- доступность weapon channel;
- наличие боеприпасов;
- capabilities бойца;
- сектор установленного оружия;
- тяжёлое ранение;
- допустимая поза.

Не нужно инвалидировать поле после каждого отдельного патрона.

Боезапас для danger field можно представить грубыми классами:

```text
empty
low
ready
abundant
unknown
```

Точный остаток остаётся частью production weapon state и используется реальной физикой боя.

---

# 8. Связь с существующим route-cost

Маршрутизация уже использует `SoldierDangerField`.

Поэтому после улучшения канонического поля route-cost автоматически начнёт учитывать:

- разную угрозу ППШ и винтовки на расстоянии;
- сильные сектора ДП-27;
- падение опасности вне сектора установленного пулемёта;
- снижение угрозы за подходящим укрытием;
- старение remembered threats;
- неизвестный или предполагаемый класс оружия;
- временную неготовность угрозы к огню.

Новый route-cost layer не нужен.

Нельзя:

- повторно строить оружейную карту внутри worker маршрута;
- независимо пересчитывать укрытия для маршрута;
- дублировать perception snapshot;
- создавать новый revision key, противоречащий каноническому danger snapshot.

Worker должен по-прежнему получать компактный подготовленный snapshot существующего поля.

# 9. Связь с тактическими позициями

Поле опасности отвечает на вопрос:

> Насколько опасно бойцу находиться в этой точке относительно известных угроз?

Оно не должно превращаться в полную карту собственной огневой эффективности.

Для оценки огневых позиций нужен дешёвый точечный запрос только для уже отобранных кандидатов:

```ts
interface FireOpportunityQueryV1 {
  shooterUnitId: string;
  candidatePosition: Vec2;
  candidatePosture: Posture;
  targetContactId: string;
}

interface FireOpportunityEstimateV1 {
  lethalOpportunity: number;
  suppressionOpportunity: number;
  timeToFirstEffectClass: number;
  ammunitionEfficiency: number;
  sectorValidity: number;
  confidence: number;
}
```

Такой evaluator:

- использует те же `WeaponThreatProfile`;
- использует ту же line-of-fire геометрию;
- использует тот же быстрый cover scalar;
- вызывается только для bounded набора кандидатов;
- не создаёт full-map поле;
- не запускает баллистическую симуляцию.

Итоговый выбор позиции сможет совместить:

```text
защита позиции
+
опасность маршрута
+
опасность самой позиции
+
собственная огневая возможность
+
время занятия позиции
+
требуемая поза
+
сектор оружия
```

Это напрямую связывает идею с `GOOD_POSITIONS_AND_AMBUSH_SITES.md`, не создавая параллельную систему.

# 10. Связь с Combat Lab

Combat Lab должен стать источником калибровки компактных профилей.

Один и тот же производственный сценарий можно прогонять по матрице:

```text
оружие
×
боеприпас
×
дистанция
×
поза стрелка
×
поза цели
×
движение
×
тип укрытия
×
режим огня
×
seed
```

Собираемые результаты:

- время до первого физического воздействия;
- вероятность попадания;
- ожидаемые ранения;
- rounds consumed;
- suppression events;
- maximum suppression;
- продолжительность устойчивого огня;
- влияние укрытия;
- влияние установки пулемёта;
- влияние помощника.

Затем сравниваются:

```text
предсказание WeaponThreatProfile
против
фактического распределения Combat Lab
```

Игровой danger field остаётся дешёвым, а точность профилей улучшается offline.

Нельзя запускать тысячи реальных симуляций внутри обычного игрового тика.

# 11. Расширение на технику

Архитектура должна позволять позднее учитывать технику без создания отдельного поля опасности.

Можно добавить компактный класс цели:

```ts
type ThreatTargetClass =
  | 'infantry'
  | 'soft_vehicle'
  | 'light_armor'
  | 'medium_armor'
  | 'heavy_armor';
```

И небольшую матрицу совместимости:

```text
weapon threat profile
×
target class
=
lethal compatibility
+
suppression compatibility
```

Пример:

- ППШ против пехоты — высокая угроза;
- ППШ против грузовика — ограниченная угроза экипажу и открытым элементам;
- ППШ против брони — почти нулевая lethal-угроза;
- противотанковое оружие — высокая угроза технике, но иной профиль против пехоты.

Точная броня, угол, рикошет и повреждение узлов остаются производственной физикой реального попадания.

Danger field использует только быстрый ожидаемый класс воздействия.

# 12. Кэширование и инвалидация

Поле не должно перестраиваться на каждый боевой event.

Подходящие причины изменения prepared threat:

- существенное перемещение угрозы;
- изменение субъективной позиции контакта;
- изменение стадии или уверенности контакта;
- распознавание нового класса оружия;
- изменение weapon/ammo revision;
- смена portable/deployed state;
- изменение сектора установленного оружия;
- смена coarse readiness class;
- смена coarse ammunition class;
- изменение позы;
- изменение capabilities;
- изменение геометрии карты;
- изменение профиля оценивающего бойца.

Не должны сами по себе инвалидировать full field:

- каждый выпущенный патрон;
- каждый кадр анимации;
- каждый projectile step;
- визуальное включение или выключение overlay;
- чтение поля маршрутизацией;
- чтение поля UI.

Кэш должен иметь:

- явного владельца;
- стабильный revision key;
- bounded размер;
- детерминированную инвалидизацию;
- отсутствие асинхронного применения stale result;
- симметричный teardown.

# 13. Жёсткие требования производительности

## Обязательно

1. Использовать один существующий `SoldierDangerField`.
2. Не создавать новый full-map слой.
3. Не добавлять второй renderer опасности.
4. Не запускать projectile simulation при оценке клетки.
5. Не выполнять отдельный raycast для каждой клетки и каждой угрозы, если уже существует подготовленная геометрия.
6. Переиспользовать текущий быстрый cover scalar.
7. Переиспользовать существующие threat geometry caches.
8. Использовать маленькие immutable lookup tables.
9. Не выделять массивы и maps в per-cell hot path.
10. Ограничивать число субъективных контактов существующим perception budget.
11. Сохранять существующий compact snapshot для route-cost worker.
12. Выполнять fire-opportunity расчёт только для bounded списка кандидатов.
13. Не добавлять постоянный timer или background loop.
14. Не загружать диагностические данные, когда слой выключен.
15. Измерить before/after на существующем danger performance harness.

## Целевой характер стоимости

На одну threat/cell оценку ожидаются:

- distance bucket;
- два чтения lookup table;
- несколько scalar multiplication;
- чтение подготовленного cover/geometry результата;
- отсутствие heap allocation.

Общая сложность должна оставаться в текущем классе сложности существующего danger field, без появления:

```text
units × threats × map cells × ballistic samples
```

# 14. Предлагаемый поток данных

```text
PerceptionSystem
        ↓
perceptionKnowledge / remembered threats
        ↓
PreparedThreatSource
        ├─ subjective position
        ├─ confidence and age
        ├─ known/estimated weapon class
        ├─ readiness class
        ├─ deployment state and sector
        └─ shared prepared geometry
        ↓
WeaponThreatProfile lookup
        ↓
lethalDanger + suppressionDanger
        ↓
existing cover / exposure attenuation
        ↓
SoldierDangerField scalar
        ↓
    ┌──────────────┬───────────────┬─────────────────┐
    ↓              ↓               ↓
route-cost      UI overlay      tactical scoring
```

Graph v2 не должен пересчитывать эту физику.

Он должен получать простые опубликованные значения:

- current danger;
- route danger;
- strongest threat;
- expected suppression pressure;
- candidate fire opportunity;
- объясняющие причины.

# 15. Этапность реализации

## Этап A. Combat Lab и измерения

- создать визуальные и headless сценарии;
- собрать реальные результаты оружия по дистанциям;
- не менять danger field.

## Этап B. Компактные профили

- ввести версионированный `WeaponThreatProfile`;
- начать с винтовки, ППШ и ДП-27;
- проверить lookup и детерминизм.

## Этап C. Интеграция в `SoldierDangerField`

- добавить lethal/suppression внутренние каналы;
- сохранить внешний scalar контракт;
- использовать субъективное знание оружия;
- переиспользовать cover и geometry caches.

## Этап D. Route-cost parity

- доказать, что маршрут читает тот же обновлённый danger snapshot;
- не добавлять новый worker field;
- проверить отсутствие дополнительных full-map builds.

## Этап E. Точечная оценка огневой позиции

- добавить bounded `FireOpportunityEvaluator`;
- использовать только на кандидатах тактических позиций;
- связать с существующим ranking.

## Этап F. Graph v2

- публиковать готовые scalar diagnostics;
- не переносить расчёт оружейной эффективности внутрь нод.

## Этап G. Техника

- добавить target classes и compatibility matrix;
- не менять базовую архитектуру поля.

---

# 16. Что система не должна делать

Система не должна:

- создавать новую карту эффективности оружия;
- заменять `SoldierDangerField`;
- создавать вторую модель укрытий;
- читать скрытое оружие неизвестного контакта;
- симулировать пули для каждой клетки;
- запускать массовые прогоны во время игры;
- строить точную вероятность ранения в hot path;
- определять поведение вместо Graph v2;
- автоматически выбирать цель;
- автоматически выбирать позицию;
- менять production ballistics;
- использовать UI как источник истины;
- пересчитывать full field из-за каждого патрона;
- создавать неограниченные diagnostic buffers;
- ослаблять существующие performance thresholds.

---

# 17. Диагностика

Для выбранной клетки и strongest threat полезно показывать:

```text
итоговая опасность;
lethal contribution;
suppression contribution;
предполагаемый класс оружия;
дистанционный коэффициент;
confidence контакта;
memory attenuation;
fire readiness;
sector validity;
cover attenuation;
exposure attenuation;
причина ограничения дальности;
revision key;
cache hit/miss.
```

Эти значения должны быть диагностикой уже вычисленного результата, а не запускать отдельный подробный расчёт всей карты.

---

# 18. Критерии правильного направления

Идея считается архитектурно подтверждённой, если будущий прототип доказывает:

- ППШ, винтовка и ДП-27 создают разные формы опасности по дистанции;
- установленный ДП-27 создаёт направленный сектор;
- укрытие снижает lethal danger сильнее, чем suppression danger;
- неизвестное оружие не раскрывается через скрытое состояние;
- remembered threat постепенно ослабевает;
- route-cost использует тот же канонический danger;
- не появляется новый full-map build;
- выключенный overlay не меняет стоимость симуляции;
- reverse unit order не меняет результат;
- одинаковые revisions дают одинаковое поле;
- per-cell hot path не выделяет память;
- существующие performance thresholds не ослаблены;
- профили можно откалибровать по Combat Lab без изменения runtime-контракта.

---

# 19. Итоговое решение

Основное направление:

```text
не создавать WeaponEffectivenessField;
не создавать новую danger map;
не создавать новую систему укрытий;

расширить существующий SoldierDangerField;
добавить компактный WeaponThreatProfile;
считать два внутренних канала: lethal + suppression;
использовать субъективные контакты;
переиспользовать существующую геометрию и cover scalar;
сохранить текущую route-cost интеграцию;
оценивать собственные огневые возможности только точечно;
калибровать профили через Combat Lab;
позднее расширить тем же контрактом на технику.
```

Это решение связывает новую стрелковую физику с уже существующими слоями игры и сохраняет главное ограничение проекта: высокая тактическая выразительность без дорогих параллельных вычислительных систем.
