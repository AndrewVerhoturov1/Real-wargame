# GitHub + Orca как цикл между мощным Web Chat и локальным оператором

## Статус

Проектная идея для проверки. Это **не замена** текущим каноническим правилам разработки, а возможное расширение существующей оркестрации.

Цель: оставить мощную модель в обычном Web Chat владельцем анализа и продукт-кода, а локального агента в Orca использовать как постоянного оператора: запуск, локальная проверка, браузер, скриншоты, тесты и разрешённый пользователем деплой. GitHub становится общей памятью и каналом передачи состояния.

## Предлагаемый цикл

```text
пользователь / мощный Web Chat
→ GitHub Issue или связанная задача
→ Orca Task Sources создаёт/открывает отдельный workspace/worktree
→ локальный агент читает AGENTS.md и нужные skills
→ получает точный feature SHA из GitHub
→ запускает проверки и локальный preview
→ при разрешённой визуальной проверке делает скриншоты реального приложения
→ пишет в GitHub: SHA, проверки, ошибки, скриншоты, что нужно проверить человеку
→ пользователь проверяет результат
→ мощный Web Chat читает GitHub, анализирует diff + доказательства + замечания пользователя
→ правит код на той же feature-ветке и публикует новый SHA
→ локальный агент снова проверяет
→ цикл повторяется до принятия
```

Главная экономия: не использовать Vercel для каждой промежуточной итерации. Локальный агент может проверять `localhost` и передавать внешнему Web Chat снимки и отчёт через GitHub. Внешний деплой остаётся отдельным явным действием пользователя и нужен в основном как контрольная точка или финальная проверка.

## Что стоит хранить в GitHub

Для каждой длинной задачи достаточно одного Issue и одной feature-ветки. В Issue/PR можно фиксировать:

- `base_commit` и текущий `current_commit`;
- короткое текущее задание;
- фактически выполненные проверки;
- ссылки/пути на свежие скриншоты для этого SHA;
- ошибки браузера/консоли;
- замечания пользователя после живой проверки;
- следующий запрос мощной модели к локальному оператору.

Issue не должен становиться обязательным для каждой мелкой правки — использовать его именно там, где нужен многосессионный цикл между несколькими агентами.

## Живой тест №1 — UI без Vercel

Взять небольшую реальную визуальную задачу, например изменение панели Полигона.

1. Мощный Web Chat создаёт feature-ветку и вносит правку через GitHub.
2. Создаётся Issue с целью и ссылкой на текущий SHA.
3. В Orca открыть Issue через `Task Sources → GitHub`.
4. Локальный агент получает этот SHA, запускает приложение локально и выполняет проверки.
5. После явного разрешения на визуальную проверку агент открывает реальное приложение в браузере, делает 2–4 контрольных PNG (например desktop, mobile, открытая панель, выбранный юнит) и публикует отчёт/ссылки в GitHub.
6. Пользователь смотрит локальный результат и оставляет замечание в Issue.
7. Мощный Web Chat читает Issue + diff + скриншоты, исправляет код на той же feature-ветке и публикует новый SHA.
8. Orca повторяет проверку нового SHA.

Критерий успеха: минимум две итерации прошли без Vercel, а внешний Web Chat смог принять следующее решение только по GitHub-состоянию и свежим визуальным доказательствам.

## Живой тест №2 — Vercel только как контрольная точка

Взять задачу, где внешний доступ всё-таки нужен.

1. Сначала провести несколько итераций по схеме теста №1 только локально.
2. Когда версия выглядит готовой, пользователь явно пишет команду на деплой.
3. Локальный агент Orca по штатному skill вручную деплоит **точный текущий SHA** на Vercel, ждёт `READY`, проверяет обязательные страницы и публикует URL + SHA в GitHub.
4. Пользователь тестирует внешний Preview и оставляет замечания в Issue.
5. Мощный Web Chat анализирует замечания, код, логи и скриншоты и делает исправление на той же feature-ветке.
6. Новый деплой не происходит автоматически: сначала снова локальная проверка; следующий Vercel Preview — только после нового явного запроса пользователя.

Критерий успеха: Vercel используется один раз на несколько локальных итераций, а локальный агент полностью снимает с внешнего Web Chat работу по запуску, ожиданию, браузерной проверке и сбору доказательств.

## Что потребуется для более полной автоматизации

Если эксперимент окажется удобным, следующим шагом можно отдельно исследовать небольшой мост:

```text
новый комментарий/статус в GitHub
→ Orca понимает, какой workspace относится к задаче
→ локальный агент получает новую команду
→ после выполнения сам публикует отчёт обратно в GitHub
```

До проверки двух ручных сценариев выше такой мост лучше не строить: сначала нужно доказать, что сам процесс действительно удобнее текущего.
